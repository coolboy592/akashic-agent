## 3. 执行骨架：一次请求怎样完成

### 3.1 先区分三件事

**保存了什么、正在做什么、模型看到了什么，是三个不同的问题。** 消息日志保存用户输入、模型输出、工具结果和暂停等事实；运行任务负责本次执行及其权限；模型请求则从历史和材料中选取、组织本次需要的信息。运行任务结束后，日志仍然保留；请求使用了摘要，也不代表原文被删除。

“会话”表示消息归属。“一轮工作”按最终回答或明确放弃来分段，其中可能有多次模型请求和工具调用，也可能包含用户中途补充的输入。系统通过读取日志得到这个分组，不再维护另一份对话正文。同一会话还可以容纳不同来源，是否需要回复、旧输出是否过期，要在对应来源内判断。

这层区分服务于一个实际目标：遇到中断时，系统能根据已保存的事实判断下一步，而不必猜测上一个进程执行到了哪里。

### 3.2 用一次查询讲正常流程

以下是说明执行顺序的例子，不代表新增工具能力：用户提出一个需要工具查询的问题，工具返回资料，助手据此回答。

```text
┌─────────────────────────────────┐
│ 保存用户问题，确认输入已接纳     │
└────────────────┬────────────────┘
                 ▼
┌─────────────────────────────────┐
│ 读取历史，准备材料和可用工具     │◄──────────────┐
│ 组装请求，交给模型判断下一步     │               │
└───────┬────────────────┬────────┘               │
        │ 需要调用工具   │ 可以直接回答           │
        ▼                ▼                       │
┌────────────────┐ ┌───────────────────────┐      │
│ 保存调用请求   │ │ 保存最终回答          │      │
│ 检查权限并执行 │ │ 按渠道策略发送并记回执│      │
│ 保存工具结果   │ └───────────────────────┘      │
└───────┬────────┘                                │
        └──────── 将结果用于下一步判断 ───────────┘
```

**第一步，先保存问题。** 系统接收到输入后，先写入消息日志，再确认接纳。此时用户的问题已经保存，但回答尚未生成。回复程序根据日志判断哪些输入仍需要处理，再准备模型和工具等执行资源。

**第二步，为这次判断准备材料。** 把稳定指令、对话历史、可用摘要、动态记忆等组织成请求，同时提供当前允许模型看到的工具说明，并预留回答所需的容量。模型得到的是本次请求视图。

**第三步，模型选择回答或调用工具。** 模型不会直接执行外部操作。如果它提出调用，系统先核对工具是否属于本次可用集合，再保存具体工具身份和参数；后续执行以这条已保存的请求为依据。如果模型产生有效内容且没有工具调用，正常回复就可以结束；空响应会报错，不能当作完成。

**第四步，执行工具并保留结果。** 执行层准备参数、检查权限，记录开始状态，然后调用工具。返回结果与对应回执一起保存。当前循环逐个处理工具调用；这些结果在下一次请求中与原调用配对交给模型，模型据此决定继续查询还是回答。恢复执行时，也会先处理日志中尚未结算的调用，再发起新的模型判断。

**第五步，保存回答，再处理送达。** 最终回答写入日志后，本次推理结束。需要向外部渠道发送时，再固定目的地、发起投递、记录是否送达。保存成功和渠道确认成功分别记录。

这个例子的核心事实只有四条：**用户问题 → 模型提出的工具请求 → 工具结果 → 最终回答**。保存这些事实足以追踪一次工具循环，但不能据此声称保存了模型完整的内部思维过程。

### 3.3 四条简历能力怎样接到这里

记忆为第二步提供历史材料，也可以在第三步之后通过工具补充证据；工具发现决定本次有哪些工具说明进入请求；上下文管理控制请求能否装进模型窗口。评测需要观察这条链路最终回答得如何，主动交互则还需解决何时触发、是否调查和是否发送的问题。记忆详见第 7 节，工具与上下文见第 8 节，评测见第 9 节，主动交互见第 10 节。

学习时先按上面的五步复述，再用下一节解释异常情况。需要看代码时，按文末“附录 A”的顺序回查对应实现即可。

## 4. 关键设计：遇到问题时，系统具体怎么处理

以下实现逻辑已对照当前源码；设计收益与代价是基于实现的工程分析，不等同于已经做过性能对比实验。

### 4.1 为什么先保存输入，再启动回复？

**场景：** 模型回答可能很慢，处理期间还可能收到补充问题。如果接纳输入一直等到回答完成，用户很难区分“问题没收到”和“正在处理”。

系统先把输入保存下来，再由回复程序查看日志：哪些输入之后还没有最终回答，哪些被暂停或失败状态挡住。对需要处理的输入启动任务，任务结束或重启后再依据日志判断后续动作。逻辑上的一轮工作也从这些消息分组得到，不另外复制正文。

这样，输入是否保存、是否还需回复都有持久依据。代价是必须分别表达等待、执行、暂停和失败；读取历史判断状态也有开销，不能因为逻辑清晰就宣称历史再长都没有成本。

**口播抓手：** “我把输入接纳和回答执行分开，先保证问题有记录，再根据日志驱动回复。接纳成功表示收到了，不表示已经回答。”

### 4.2 为什么模型提出工具调用后，还要先保存调用请求？

**场景：** 模型刚决定调用某个工具，程序就中断了；或者这份决策已经被用户的新输入作废。如果立即执行，可能出现外部操作发生了，但本地找不到对应请求的情况。

系统先固定这次要调用的工具身份和参数，检查这份输出仍有提交权限，再保存调用请求。执行循环只处理已经保存的请求。工具执行层进一步准备最终参数、检查授权、记录开始状态，然后才进入真实工具。工具结束后，结果正文与执行回执一起提交。

这里有两个检查：模型只能选当前展示并允许选择的工具；真正开始执行前还要检查授权和任务是否仍有效。前者限制选择范围，后者约束实际效果。

这样能把“模型想做什么”和“实际做到了哪一步”对应起来。代价是需要管理请求身份和执行进度。当前逐个执行工具，顺序容易追踪，但独立查询也不能在这条循环中并行加速。

**口播抓手：** “模型负责提出行动，程序负责确认并执行。我先保存调用意图，再执行并保存结果，避免未提交的草稿产生外部效果。”

### 4.3 工具超时后，怎样避免重复操作？

**场景：** 外部操作可能已经成功，只是返回结果时连接断了。此时超时不能证明“什么都没发生”。

恢复时，系统先读这次调用已有的执行记录。若已保存最终结果，就直接使用；若只知道操作已经开始，则用原调用身份查询工具：

1. 能查到结果，就记录并使用该结果。
2. 查不到，但工具明确支持同一调用身份的幂等重发，才允许在重新检查权限后重发。
3. 查不到，也没有这种幂等保证，就标记“效果未知”，停止这段工作的自动推进。

“幂等”在这里指同一调用身份重复提交不会重复产生效果。程序不能替一个不支持此协议的外部工具凭空提供保证。已经记录为效果未知的调用也不会因为来了新输入就自动重跑。

这项设计避免把不确定性伪装成成功或失败；代价是某些故障需要进一步核对，无法保证所有任务都自动恢复，更不能笼统承诺外部操作恰好执行一次。

**口播抓手：** “重试前先判断效果是否可确认。查询不到且不支持幂等的操作，我会保留未知状态，避免为了继续执行而重复产生副作用。”

### 4.4 用户补充输入时，怎样阻止旧回答继续做事？

**场景：** 模型正在处理旧问题，用户补充了新条件。即使发出取消信号，模型服务也可能继续返回旧回答或旧工具请求。

系统先保存新输入，再撤销旧任务的执行权限。旧任务的输出写入权限随之失效；提交输出时，还会比较当前同来源日志的位置是否与推理所依据的位置一致。位置变化说明决策依据已经过时，旧输出不能再提交。真正开始新工具效果之前，也检查任务仍有效、没有新输入或控制消息使它过期。

已经开始的工具另行处理：普通取消通常仍等待它结算，保存真实结果后，再让后续回复结合新输入继续判断。明确放弃工作时有专门的工具终态处理来解除等待，但这不代表已经发生的外部操作被撤销。

收益是正确性不依赖模型服务立即响应取消；代价是慢工具可能延迟下一次回复。面试时应区分“停止旧决策”和“撤销外部效果”。

**口播抓手：** “我不仅发取消信号，还收回旧任务的提交和执行权限。已经发生的工具效果则单独结算，不能把取消当作回滚。”

### 4.5 历史太长时，怎样压缩而不破坏执行逻辑？

**场景：** 历史、记忆材料和工具说明加起来可能超出窗口。如果随便删掉一部分历史，模型可能只看到工具结果，却看不到它对应的调用。

系统先取得材料，再组装请求并估算容量，同时为输出预留空间。容量不足时，由摘要能力生成或更新更小的历史表示，再重新组装。摘要覆盖范围必须保持已结算的工具调用与结果配对，不能从中间切开；完整消息仍保存在日志里。

本地估算可能与模型服务的实际计算不一致。服务端若仍报容量超限，程序可以强制缩减摘要后再试一次；摘要没有变化就不继续重试。这个重试针对容量问题，不是所有模型错误的通用重试策略。

稳定指令与检索数据也分开处理：历史、摘要和动态材料不会被提升为系统指令。这有助于约束资料中的指令，但不能仅靠角色设置就保证消除提示词注入。

代价是摘要可能遗漏细节，压缩也增加处理开销。为什么还需要按需检索和原文取证，正可以从这个限制引出；具体记忆链路见第 7 节。

**口播抓手：** “压缩的是模型本次看到的历史表示，原始消息仍保留。缩减时要保住工具调用与结果的配对，容量错误的重试也有明确上限。”

### 4.6 怎样限制循环，又避免留下半途的工具调用？

系统按当前同来源、尚未结束的工作中已经保存的模型输出计步。默认回复预算为 40 步，配置为 0 时不设这个上限。用户中途补充输入不会自动把预算清零，因此不能靠不断补充输入让同一段工作无限续跑。

检查预算之前，先处理已经保存的工具请求。即使上一轮恰好用完最后一步，也要先让对应工具得到结果，再停止发起下一次模型判断。达到上限会留下失败控制记录，等待后续输入或控制；它不表示任务已经成功完成。

预算限制执行规模，但也可能使复杂任务在得出答案前停止；上限如何选择需要结合任务难度与成本，当前默认值不是效果最优的证明。

### 4.7 为什么回答完成和发送成功分开记录？

**场景：** 答案已经生成并保存，但发送到外部渠道时失败。若把它当作推理失败重新回答，会多花模型成本，还可能得到不同内容。

系统先保存最终回答，清理本次回复资源，再按原输入确定发送目的地并启动投递。投递独立记录回执，后来的输入不会改写旧回答的目的地。发送失败不把已经保存的回答改成推理失败；发送能否恢复，需要看渠道能力和真实回执。

这让故障定位更明确：回答没生成、回答已保存、渠道尚未确认送达，可以分别判断。代价是要管理额外的发送状态。内部会话或没有可见内容的消息，也不一定需要对外发送。

### 4.8 约 2 分钟执行骨架口播

> 我用一次带工具查询的请求来解释。系统先保存用户问题，再启动回复，这样输入接纳不会一直等待模型回答。回复时，把历史、记忆等材料和当前可用工具组织成请求，让模型选择直接回答还是调用工具。
>
> 如果需要工具，模型只是提出调用意图。程序先检查并保存具体工具和参数，然后在执行前检查权限、记录开始状态，再调用工具。结果保存后交给模型继续判断，直到形成最终回答。
>
> 这里有两个我认为值得展开的设计。第一个是处理用户中途补充输入。旧模型请求可能无法立即取消，所以除了发取消信号，还要收回旧任务的写入权限，并检查决策依据是否已经变化，避免旧工具请求继续生效。已经开始的工具则需要结算，取消不能等同于撤销外部操作。
>
> 第二个是工具失败后的恢复。超时可能只是结果没传回来，所以恢复时先查原调用的回执。查不到时，只有支持同一调用身份幂等重发的工具才可以重发；否则保留效果未知，停止自动推进。
>
> 对长对话，系统缩减的是本次请求里的历史表示，原文仍保留，而且工具调用和结果必须配对。最后，回答保存与渠道送达分别记录，发送失败就能定位在投递环节。这些边界让执行过程可追踪，也为后续记忆和工具能力提供了清晰的组合位置。

本段描述项目实现。个人主导范围沿用已确认的简历，不因讲清某项设计就自动把它归为个人原创。

## 7. 记忆链路：怎样把历史变成本次回答的证据

本阶段从回答侧展开：自动提供历史材料 → 按需补搜 → 核对原文与出处 → 解释候选如何产生。学习与持久化只讲到理解检索所需的边界。实现仍以首轮源码基线为准，未运行真实模型实验。

### 7.1 先说明记忆解决什么问题

模型只能根据当前请求中可见的信息回答。用户几周前说过的话，即使保存在会话日志里，也不一定进入本次窗口。长期记忆的任务是从已保存历史中找到与当前问题有关的材料，并把可核对的内容送进请求。

这里要区分三个对象：**原消息保存说过什么；记忆图组织哪些历史可能相关；本次召回记录保存这一次找到了什么、实际呈现了什么。** 图上的一个学习节点可以对应多条输入与最终回答，不等于一条独立的、已经验证正确的用户事实。

例如，用户先说“出差时尽量选早班”，后来补充“下周那次例外，要下午出发”，现在问“下周怎么安排”。这是理解检索与冲突判断的示意，不是本轮测试结果。系统需要找到相关历史、保留原话，模型才能判断哪句话是一般偏好、哪句话是特定行程的例外；只拿“喜欢早班”的摘要可能答错。

### 7.2 当前真正的证据流程

```text
┌─────────────────────────────────────┐
│ 当前未结束工作中的用户输入          │
│ 固定消息范围，形成查询文本与向量    │
└──────────────────┬──────────────────┘
                   ▼
┌─────────────────────────────────────┐
│ 向量直召回 + 图关联补全             │
│ 选择历史节点、排除重复、保留来源    │
└──────────────────┬──────────────────┘
                   ▼
┌─────────────────────────────────────┐
│ 从原消息读取可见文本                │
│ 按字符预算放入请求，记录实际呈现项  │
└──────────────────┬──────────────────┘
                   ▼
┌─────────────────────────────────────┐
│ 模型判断材料是否足够                │
│ 不足时可主动组织查询，再次召回      │
│ 补搜同样返回原消息正文与出处        │
└──────────────────┬──────────────────┘
                   ▼
┌─────────────────────────────────────┐
│ 依据实际可见证据回答；存在冲突时    │
│ 区分条件与适用范围，必要时向用户核对│
└─────────────────────────────────────┘
```

最后一步中的证据比较与询问是面试中应说明的回答策略，不是已验证的确定性冲突解决算法。自动注入与主动补搜是两种查询触发方式，底层复用图查询和材料呈现逻辑。

**与简历旧口径的差别：** 当前这两条路径已经从原消息读取可见正文，不是先返回摘要，再强制调用另一个工具取得原文。“自动注入—按需补搜—原文取证”适合解释三个职责，不能直接说成当前每次都会按顺序调用的三个工具。

### 7.3 自动注入：如何知道这次应该找什么？

系统先固定本次请求的完整消息前缀，再找出当前来源尚未结束的工作，并取出其中的用户输入。这样用户在查询过程中又发来一句补充，也不会悄悄混进已经开始的这次查询；后续回复使用新的消息范围重新判断。

如果这一段包含多条输入，文本按顺序连接。每条非空输入取得固定的 embedding，已有向量复用，缺少的才计算并保存；多输入向量取均值后归一化，形成当前线索。embedding 将文本映射为数值表示，帮助找到措辞不同但语义接近的历史；它不是事实真伪判定器。

之后，用这组文本与向量查询已经发布的记忆图。查询命中历史节点后，从原消息读取可见文本，带上消息身份、来源、作者和召回通道，作为历史资料进入模型请求。没有可查询的有效输入时不注入；图为空时可以得到有记录的空命中。

这样模型无需先主动调用工具就能看到一批相关历史。代价是自动查询可能带入不相关材料，多条输入求均值也可能弱化某个细节。因此仍保留模型主动组织查询的补搜能力，不能把自动注入当成一次必然充分的检索。

### 7.4 按需补搜与原文出处：怎样支撑回答？

当模型认为材料不足时，可以提出更具体的查询，调用记忆召回工具。工具固定查询文本、模型绑定和呈现预算，把新查询嵌入后，在一致的图快照上检索，再按同样的逻辑返回原消息可见正文。

工具同时保存这次查询的身份、图版本、来源和实际呈现的消息列表。后续整理内容引用时，要核对记录确实来自当前工作的实际 Akasha 工具调用，并与对应调用身份一致；不能只看到一段“这是召回结果”的文字就把它当作合法出处。

如果这次调用需要恢复，优先读取原查询记录，按原规则还原材料，不重新用最新记忆图检索。否则同一个工具调用在重启前后可能给出不同证据。原出处无法还原时明确报错，不用当前结果冒充原结果。

这条链路解决“答案引用了哪次查询实际看到的哪些消息”。它不自动证明引用足以支持结论，也不意味着最终前端引用样式已经在本阶段验收。

当前主链已核实的是**回源读取正文与引用传递**。仓库内仍有旧版独立原文读取工具文件，但本轮未找到它在当前回复主链中的注册消费者，也未核实独立关键词历史搜索工具已接入。因此口播不承诺必须依赖它们完成第三次取证，也不承诺任意指定消息都能通过当前召回接口直接读取。

### 7.5 去重和预算：找到的记忆是否都会让模型看到？

不会。系统先选历史节点，再映射回该节点实际学习过的消息成员。两条通道重复命中的节点先去重，避免同一段历史在两个通道重复占用材料预算；不同节点中语义相近的陈述，不因此被自动合并成唯一事实。

材料呈现时逐条读取消息的可见文本，加上来源信息，检查这一整条能否装进剩余字符预算。能装下才加入；装不下就跳过该条，继续考虑后面的消息。它不是把每条消息截断成一个固定长度摘要。可见文本也不等于所有附件、工具结果和内部字段都被原样展开。

所以系统分别保留“检索命中的成员”和“预算内实际呈现的消息”。只有后者获得本次材料中的引用信息。假设命中了两段历史，但预算只能放下一条用户消息，文档和诊断都不能声称模型看过另外几条回答。

还有一个实现细节：查询的 limit 不是最终展示消息总数。直召回最多取较小的一组，图补全另有上限，一个节点又可能包含多条消息，最终还受字符预算限制。面试中先说明分层预算，具体常数留给源码核对。

这一设计控制上下文开销并保留证据边界；代价是长消息可能整条落选，同一段问答也不保证全部进入本次材料。应把“没有检索到”和“检索到了但没呈现”分开分析。

### 7.6 两条召回通道分别做什么？

**向量直召回直接比较当前线索与历史问答。** 对每个未被显式抑制的历史节点，分别比较其用户文本向量和回答文本向量，取较高的点积分数作为该节点分数，优先选分数高的节点。当前直召回最多取五个节点，也受查询 limit 限制。代码在这里遍历历史节点计算分数，不能把它描述成已经接入某种近似最近邻索引。

**图关联补全利用历史之间的联系寻找补充材料。** 引擎从当前线索和相关上下文中形成起始证据，综合语义相似度、词项匹配及时间连续性等信号，判断是否需要依赖前文。然后把起始权重沿图中关系传播：每次优先处理尚未传播的较大权重，一部分留在当前节点，一部分沿关联继续传播，剩余总量足够小时停止。最后结合关联群组和上下文路线选出补全候选。

可以把它理解为：先找到问题指向的历史，再利用已学习的联系补上只看当前措辞容易漏掉的内容。这里的“图”并非可以直接等同于人工抽取的实体—关系知识图谱；“补全”返回历史节点，不是让模型凭空补写记忆。

两条通道并不只是“向量前五名再找它们的邻居”：图通道有自己的起始证据与读取过程。宿主分别接收直召回与补全结果，先保留直召回节点，再排除补全中与其重复的节点；每条通道内部按历史开始时间从近到远展示。

收益是直接相关与关联相关的材料都能进入候选；代价是图状态和查询计算更复杂，也可能引入较弱关联。是否比单独向量检索更有效，需要后续对照评测。本阶段不展开传播公式与全部群组选择规则。

### 7.7 新旧事实冲突时，系统做了什么、没做什么？

当前召回把相关历史及出处提供出来，并在通道内按时间排序；这不能直接推出“新消息永远覆盖旧消息”。上面的行程例子中，一般偏好和特定例外可能同时成立，必须看原话的条件和适用范围。

在回答层，应比较实际呈现的证据：是否针对同一个对象、是否有明确更新、是否只是临时条件。如果证据不足，就继续检索或向用户确认。这里没有核实到一套自动合并事实、标注失效时间并裁定冲突的完整机制。

也不能把内部选择函数具有时间筛选参数，写成用户可直接使用的召回能力：当前显式召回公开参数是查询文本与数量限制，没有独立时间过滤字段。时间线索可以写入查询，但不等同于结构化过滤保证。

**口播抓手：** “我保留原消息和查询出处，让模型有条件核对新旧信息；时间排序只是呈现顺序，冲突还要结合适用范围判断，不能直接把分数最高或最近的一条当真值。”

### 7.8 查询和学习为什么分开？

一次召回只是读取当前图中的关联。如果每查一次就自动强化相关历史，模型多搜几次可能改变后续记忆，使诊断和恢复更难解释。

当前图查询使用临时读取状态，完成后恢复原图。正式学习由另一条消息消费流程负责：读取可学习会话和允许来源中的已完成问答，取得完整用户输入与最终回答的向量，再更新图和消费出处。未完成、已放弃或明确禁止学习的样本不会按正常问答进入学习。重复通知通过已经消费的结束消息身份识别，不重复学习同一样本。

查询不推进学习图，但整个查询过程不是完全零写入：自动查询会补存缺失的当前输入向量，并保存召回出处；显式补搜也会保存查询记录。在线学习、查询和关闭共用串行边界，避免读到修改到一半的图。

模型与向量空间也需要固定。即使两个 embedding 模型维度相同，空间含义也未必一致，不能混进同一张既有图；不匹配时报告不可用或错误，需要明确重建处理。本阶段只核实此边界，不执行重建。

旧说明里的“自动检索 ticket 直接由本轮提交消费”不能原样套用：当前消息消费者学习时传入空 ticket，由引擎在提交时重新检索；回答期间保存的召回记录保留的是当次证据。查询只读与正式学习的分离仍然成立，宿主连接方式已经变化。

### 7.9 哪些属于宿主集成，哪些属于上游引擎？

宿主负责把消息组织成查询和学习材料，管理模型空间、自动注入、工具调用、来源引用、展示预算和消息消费。引擎承担记忆图、特征证据、传播、关联补全及学习更新等算法职责。

仓库的上游身份文件记录了 `akasha-v2-engine` 的固定提交与内容标识，本阶段据此识别算法来源，但没有取得该上游版本做逐文件差分或镜像一致性验证。因此可以沿用简历中的“集成并改造”，结合已核实的宿主链路讲设计；不能只因为算法代码位于本仓，就说整个图记忆算法都是个人从零实现，也不能凭身份文件列出个人的精确上游改动清单。

### 7.10 约 2 分钟记忆口播

> 这部分解决的是历史虽然保存了，但不一定进入当前模型窗口的问题。我把原消息作为可核对的内容，把记忆图用于找相关历史，再保存每次查询实际呈现了哪些证据。
>
> 回答前，系统会取当前工作中的用户输入形成查询线索；多次补充输入一起参与。检索有两条通道：向量直召回找语义直接相关的历史，图关联补全利用历史之间的联系补充候选。两边按节点去重后，再回到原消息读取正文，按预算放进请求。
>
> 一个关键点是，检索命中不等于模型真的看到了。消息太长可能放不进去，所以我们分别记录命中成员和实际展示消息，后续引用依据实际展示内容。如果材料不足，模型还可以自己组织更具体的问题再召回。
>
> 当前实现中，自动注入和补搜都已经读取原消息可见正文并保留出处，因此“原文取证”不一定是第三个独立工具调用。恢复同一次召回时使用原记录，也不会换成最新图的另一批结果。
>
> 另外，查询不会推进学习图，正式学习由完成问答后的消息消费流程处理。保留出处也不代表自动解决了事实冲突：最近的一条可能只是临时例外，回答还要比较适用范围。效果上，需要通过端到端评测验证这些机制是否帮助答对，本阶段我只陈述已核实的实现，不给未经验证的提升数字。

贡献用语仍以原简历为准。上面关于宿主机制的解释不能替代个人修改记录，也不能把图补全的直觉收益说成已完成消融实验。

## 8. 工具发现与上下文管理：怎样让请求装得下，又保留行动依据

本阶段按“工具进入目录 → 按需展示 → 检查调用 → 组织材料 → 缩减历史”的顺序展开。工具数量与历史长度都会占用模型输入，但处理方式不同：前者选择本次需要的工具说明，后者选择或摘要历史。两者最终一起接受请求容量检查。

### 8.1 先区分目录、可见工具与执行权限

工具的 Schema 是告诉模型“工具做什么、接受哪些参数”的结构化说明。系统注册了一个工具，不代表每次请求都必须把它的完整说明交给模型；模型看到了说明，也不代表任何参数下都能执行。

当前链路分三层：**注册目录记录可用能力；本次菜单选择交给模型的工具说明；执行层在实际调用前检查权限。** 例如工具已经安装，但不在本次回复允许的目录中，就不能靠搜索把它找出来；被允许但尚未展示的工具，可以通过发现工具选择；最终执行仍需检查任务和授权是否有效。

注册时保存名称、描述、参数说明和真实入口，同时声明是否常驻、能否预加载、是否必须搜索以及风险类别。注册表检查基础格式，具体目标负责参数校验。文件、命令和 Web 等标准工具通过当前普通工具合同进入目录。

这使发现和执行可以分别演进：搜索负责帮助模型找到能力，授权负责约束动作。代价是需要维护准确的描述与策略标记；不清楚的描述会直接影响搜索结果。

### 8.2 一次按需发现具体怎样发生？

假设某个允许使用的工具还没有出现在本次模型请求里，用户提出了相关需求：

```text
┌──────────────────────────────────────┐
│ 程序确定本次允许目录并固定候选身份   │
│ 初始展示常驻工具和可预加载的近期工具 │
└───────────────────┬──────────────────┘
                    ▼
┌──────────────────────────────────────┐
│ 模型发现缺少所需工具，发起工具搜索   │
│ 按名称、提示、描述匹配，返回选择记录 │
└───────────────────┬──────────────────┘
                    ▼
┌──────────────────────────────────────┐
│ 校验选择确实来自该次发现调用的候选   │
│ 按菜单容量加入下一次请求的工具说明   │
└───────────────────┬──────────────────┘
                    ▼
┌──────────────────────────────────────┐
│ 模型提交具体调用 → 执行前再次授权    │
│ 工具结果回到后续推理                 │
└──────────────────────────────────────┘
```

搜索前先固定本程序允许的候选及其绑定身份，表示“本次选择的是哪一个真实实现”。搜索结果除了给模型阅读的描述，还保存结构化的选择记录。菜单只接受来自真实发现调用、且属于原候选集合的选择；普通工具不能伪造一段文本让另一个工具获得可见资格。

下一次组装模型请求时，再根据日志里的成功选择刷新菜单。搜索命中不等于一定全部展示：若常驻工具占满容量，选中的候选也可能装不下；被挤出的工具不能仅凭名字继续调用。

这条流程减少了每次输入中不必要的 Schema，但增加了一次发现调用，以及选择结果自身的文本开销。是否节约总 token、是否增加延迟，取决于任务实际使用了哪些工具，不能只比较初始请求大小。

### 8.3 搜索怎么排序？为什么不能叫语义检索？

当前工具搜索是确定性词项匹配。可以精确指定一个名称或一组名称；一般查询则拆成词项，中文还考虑字符、双字组合和子串，在工具名称、搜索提示及描述中匹配并加权。名称匹配权重通常高于描述，同分按名称得到稳定顺序。搜索也可先按风险类别过滤候选。

这条实现没有在此使用 embedding 或让另一个模型给工具评分。好处是可解释、结果稳定且不增加检索模型调用；限制是同义表达可能找不到，宽泛字符匹配也可能引入噪声。失败时可以改关键词或精确选择已有名称。

风险过滤只缩小搜索结果。把查询限制为只读工具，不会替代执行层授权，也不会把一个工具本身变成只读。

### 8.4 “当轮解锁”和“常用预加载”准确指什么？

当前选择随同来源尚未结束的工作保留，可以跨多次模型请求，不是只对某一次模型调用生效。最终回答或明确放弃形成边界后，旧的搜索选择不直接解锁下一段工作；迟到的旧搜索结果仍可保存，但不会影响新段菜单。

后续工作可以依据历史实际调用，预加载允许预加载的近期工具。菜单按日志顺序维护最近使用关系，并在容量不足时优先保留近期项。这更接近“近期使用预加载”，不是统计调用次数后选最热门工具。要求重新搜索的工具不会通过历史预加载绕过该要求。

常驻工具优先占位，剩余空间给动态选择。常驻集合本身超过模型允许数量会明确报错；有必须搜索的工具却未配置发现能力，也会被拒绝。没有发现能力时，菜单会展示本次允许目录，不应把按需暴露描述成无条件成立。

数量上限与 token 预算也是两回事：十个参数复杂的工具可能比几十个简单工具更大。菜单限制数量，后续完整请求估算仍包含这些 Schema 的容量。

**口播抓手：** “我把已注册、当前可见和允许执行分开。按需发现决定下一次给模型哪些说明，近期预加载减少重复搜索，执行权限仍在调用前检查。”

### 8.5 MCP 接入可以讲到什么程度？

MCP 在项目中提供远端工具连接、目录获取和调用协议能力。仓库可追到客户端建立连接、读取工具名称和参数说明，以及通过固定运行代际的路由调用远端工具；也存在把 MCP 工具挂到旧工具注册表的路径。

但当前回复使用普通工具目录。本轮在相关运行装配与插件注册中，没有找到旧 MCP 注册表自动桥接到该目录的完整证据。因此应分别陈述：标准工具注册、发现和菜单链路已经核实；MCP 连接与旧目录挂载已经定位；“当前回复自动统一发现全部本地与 MCP 工具”仍待验证。

这不是判定 MCP 完全不可用，而是证据不足以支持更强的当前版本声明。面试可讲协议适配的职责与已读到的路径，不把两套目录都存在当成已经打通。原简历不在本阶段改写。

### 8.6 稳定指令、历史与动态材料怎样组织？

程序先固定本次材料贡献者，再收集稳定指令、摘要、动态提醒及引用。只有获得明确配置授权的贡献者能提供高权限提示词，摘要也只有一个指定发布者。相同引用若携带冲突出处会报错，不能由后来的材料静默覆盖。

收集后按优先级及稳定身份排序呈现。这里的优先级只决定排列位置，不等于权限高低，也不表示实际准备步骤必须按这个顺序运行。

请求中先放稳定系统指令，再放带出处的摘要、投影后的历史和动态提醒；工具 Schema 随请求单独提供。摘要和检索资料作为数据处理，历史投影不能生成 system/developer 权限。最终模型格式由模型适配层处理，避免上层自己重造 provider 的工具调用身份。

稳定排序有利于请求结构可预测；把易变化材料放在后部，也为可复用前缀创造条件。但这不保证 provider 一定命中缓存：模型、内容、工具说明、缓存规则等都可能影响结果。

代价是材料协议与权限需要显式管理。角色隔离也不是提示词注入的完整解决方案，实际工具权限仍要独立约束。

### 8.7 什么时候开始压缩？先保留什么？

完整请求先估算输入容量，再加上预留输出，与模型窗口比较。即使尚未硬超限，当前摘要插件在输入估算达到窗口约 74% 时也会考虑缩减；这是代码中的软水位，不是实验证明的最佳比例。模型窗口未知时，该插件不会假设一个窗口继续压缩。

首次没有摘要时，系统从最近的完整单元向前扩展，选择同时满足软水位和硬容量的近期窗口，当前未结束工作在这次窗口选择中作为整体保留。**窗口外更早的消息仍在日志里，但不一定进入首份摘要。** 后续在已有摘要覆盖范围基础上继续向后扩展，不能撤回已覆盖来源。

选定窗口后，程序寻找合法的旧前缀用于摘要，同时保留近期原文。近期预算按实际模型投影估算，默认目标为 20,000 token；它不是严格截成恰好 20,000 token，也不是按消息条数保留。如果找不到既保持结构、又满足近期保留要求的切点，就明确失败。

完整性具体包括：已完成的交互单元和交错来源不能从中间拆开；工具调用与结果必须结算配对。长时间未完成的工作可在已结算工具批次之后压缩旧部分，因此不能笼统说“任何未完成工作永远不压缩”。

这使请求缩减有清晰边界，但过大的当前工作、单组资料或固定材料仍可能装不下。系统不会靠任意截断来假装压缩成功。

### 8.8 摘要怎样生成、验证和保存？

生成时把旧摘要与本次新增的历史分组一起交给模型，要求保留目标、约束、进度、决策、下一步和关键上下文，并区分用户原话、助手判断和工具结果。工具协议的内部重放字段不作为摘要正文材料，已放弃调用的迟到结果也不能借摘要重新进入当前推理。

资料太多时，先寻找摘要模型能容纳的最大完整分组前缀，分批更新摘要。如果服务端仍报超限，就缩小本批分组重试；单个完整组都装不下则失败，不切碎原文。摘要输出必须符合规定标题、不能返回工具调用，并保留成功模型调用记录。

得到摘要后，用它替换本次历史表示，再估算**整个业务请求**，包括工具和其他材料。只有输入确实变小、回到软水位内且满足输出预留，才发布摘要。格式正确只是结构检查，不能证明摘要没有语义遗漏。

发布新摘要时保存覆盖消息身份、父摘要、生成代次、调用出处以及前后容量估算，并在同一事务里推进当前摘要指针。旧摘要内容不原地改写；若另一条发布已经推进父版本，过期结果不能覆盖它。原消息和工具结果仍保留，已使用的旧摘要也有独立读取出处。

这便于回查“那次请求使用的是哪份摘要”，代价是摘要记录需要持久管理，而且多次总结仍可能累积信息损失，必须通过原文和后续评测核对。

### 8.9 两种容量重试为什么要分开讲？

| 场景 | 当前处理 | 边界 |
|---|---|---|
| 业务模型请求超限 | 用同一批已取得材料更新摘要后重建请求；provider 容量拒绝最多再试一次 | 摘要必须有变化，不重新获取动态记忆来替换本次证据；重试仍失败就上报 |
| 摘要模型容纳不下待总结资料 | 缩小本批完整分组，分批更新摘要 | 单组也超限就失败；属于有限分组上的缩减，不等于业务请求无限重试 |
| 摘要生成出现可恢复错误 | 在主模型与已固定默认模型不同的情况下，尝试默认模型 | 仅覆盖明确列出的错误；不能把无效请求等任意错误都吞掉 |

如果工具说明或其他固定材料本身过大，仅压缩历史也解决不了。这是为什么工具发现和历史压缩要配合，而不能把一个“自动压缩”开关当作全部容量管理。

### 8.10 token 与缓存数据能证明什么？

当前模型驱动解析 provider 返回的输入 token、缓存输入 token 等用量，模型调用记录保存可获得的 usage、耗时和失败状态。失败或取消时不知道真实用量，就保留未知，不把它记成零费用。摘要记录的前后 token 则是容量估算，不能直接当作账单节约。

若要分析缓存比例，可以在口径一致、字段完整的调用集合中，用缓存输入 token 总量除以输入 token 总量；这是一种建议的分析方法，本轮没有核实独立“缓存命中率报表”已实现。不要把缓存调用次数占比与缓存 token 占比混为一谈，也不要把字段缺失当成没有缓存。

评估这套机制应同时观察回答质量、发现和摘要新增调用、总输入输出、延迟及实际价格口径。本轮没有运行成本对照，不能宣称节省了某个百分比；缓存命中也不是回答正确的证据。

### 8.11 约 2 分钟口播

> 这部分解决的是工具增加和对话变长后，请求越来越大的问题。我把工具注册、当前可见和实际执行权限分开：目录可以保存很多能力，但每次只向模型展示常驻工具和选中的工具说明。
>
> 模型需要尚未可见的能力时，会先调用发现工具。当前搜索按名称、提示和描述匹配，结果保存成有出处的选择记录，下一次请求再按容量载入。近期使用的工具可以预加载，但要求重新搜索的工具不能绕过规则。搜索到也不代表获得任意执行权限，调用前仍要授权。
>
> 上下文方面，稳定指令、摘要、历史和动态记忆有各自的位置与权限。系统估算完整请求，并给回答预留容量。接近窗口水位时，选择合法的历史前缀生成摘要，同时保留近期原文，工具调用与结果不能从中间拆开。
>
> 摘要生成后还要放回完整请求重新估算，确认真的变小且装得下，再连同覆盖范围和生成出处一起保存。原消息保留，旧摘要也不原地改写。首次选择的是能装下的近期窗口，所以不能说所有早期历史都进了摘要。
>
> 这些机制减少不必要输入，但搜索和摘要自身也有成本。我会看实际调用用量、缓存字段和延迟，并结合质量评测判断收益；目前不能只凭机制就给出节省比例。MCP 进入当前回复目录的完整桥接证据也需要单独核实，不能把已有协议客户端直接等同于已经全部打通。

### 8.12 追问与学习验收

| 追问 | 应能解释的处理逻辑 |
|---|---|
| 搜索出了工具为什么还不能调用？ | 允许目录、当前展示、容量和执行授权是不同检查；命中可能装不进菜单。 |
| 模型怎么知道新工具能用了？ | 真实发现结果保存结构化选择，下一次请求刷新 Schema；普通结果不能伪造选择。 |
| 预加载是不是热门工具推荐？ | 当前依据近期实际使用关系，受预加载策略约束，不是频次统计推荐。 |
| 稳定提示词为什么有助于缓存？ | 结构和前缀更可预测，但缓存是否命中取决于实际请求与 provider；必须看用量。 |
| 压缩能保证不丢事实吗？ | 保留原文与来源，约束切分和格式，但摘要仍可能漏语义，需回源和质量验证。 |
| 首份摘要是否覆盖全部历史？ | 不一定；先选近期可容纳窗口，窗口外更早历史仍存储但可能不进入首份摘要。 |
| 一个工具结果太大怎么办？ | 不能拆合法分组时明确失败；本轮未证明所有大结果都有自动截断或外置方案。 |
| 为什么不简单重试模型？ | 相同超限输入再次发送通常无助于容量；必须先改变历史表示，并限制重试范围。 |

验收标准：能讲清一次“搜索后再调用”的过程；区分数量上限、字符预算和 token 预算；说明首次窗口、摘要切点、发布校验与两种重试；能够指出质量和成本还需要什么实验，而不只罗列组件。

## 9. 端到端评测：怎样判断 Agent 最终答对，以及失败在哪一步

本节正文以 `d565ca44356b5d52fe8d00f8cb008c14fff56c0b` 为历史评测基线。它是 2026-09-07 消息运行架构切换前的最后一个提交：LongMemEval、PersonaMem、旧执行循环、旧会话管理、记忆召回、消息搜索、原文读取与旧工具轨迹接口在同一版本中存在，runner 可以沿这些接口串成完整链路。README 还保存了运行方法和定性观察，说明这不是只有目录的方案草稿。

证据强度仍需准确限定：仓库没有提交正式数据、逐题结果、汇总结果或轨迹，历史评测测试也只覆盖数据与指标局部。因此可确认的是**历史接口闭合，并有运行说明与观察文字作为间接旁证**；仓库内缺少本次可复现的完整运行证据，不能对外补充效果数字。当前 HEAD 的迁移失配只在 9.8 说明，不反向改写以下历史实现。

### 9.1 为什么不能只测“召回到了没有”？

长期记忆最终服务的是回答。一次检索命中了标准答案相关消息，只能说明候选找到了；候选还可能因为展示预算没有进入请求，也可能已经进入请求但模型误解了新旧关系，最后仍然答错。

所以端到端评测观察的是一条更长的信息流：

```text
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│ 历史是否写入  │ →  │ 相关证据是否  │ →  │ 证据是否进入  │
│ 本题环境      │    │ 被工具找到    │    │ 模型可见材料  │
└──────────────┘    └──────────────┘    └──────┬───────┘
                                               ▼
                                      ┌────────────────┐
                                      │ Agent 是否用对，│
                                      │ 最终答案是否正确│
                                      └────────────────┘
```

它适合回答“整套 Agent 在历史问答中能不能完成任务”，不直接等于记忆引擎的纯检索排名。若要单独评价候选排序，还需要标准证据集合以及 Recall@k、MRR 或 NDCG 等检索指标；历史两套 runner 没有计算这些指标。

### 9.2 两套数据怎样变成可执行样本？

**LongMemEval 走开放式问答。** loader 读取问题、参考答案、提问时间、历史分段及各分段日期。主 runner 只保留 `single-session-user`、`single-session-preference`、`knowledge-update`，也就是用户事实、用户偏好和知识更新三个指定子集。问题在问答阶段提交，参考答案只在评分阶段读取；数据里的历史 session 身份、答案 session 身份和单条消息的答案标记不参与 runner 的分支决策。

“多段历史”不能说成“多会话评测”。同一道题的所有历史分段按数据提供的顺序持续追加到该题唯一的历史会话 `lme:<question_id>`，每段消息使用对应日期；分段身份没有用来创建多个独立会话。每道题本身有独立 workspace，所以历史源码证据支持的是**题目之间隔离、题目内部合并历史**，不支持“验证了跨多个独立会话的隔离和检索能力”。

**PersonaMem 走选择题。** loader 把问题 CSV 与共享上下文 JSONL 按 `shared_context_id` 连接，只取题目声明边界之前的内容；system 文本被整理成 `persona_profile`，用户和助手消息被切成若干对话段。问题与全部选项进入问答，正确标签和正确选项只用于本地评分。

persona profile 的边界要单独记住：**数据中存在，loader 确实读取，但没有进入 Agent 上下文。** PersonaMem 最初的运行时包装函数接收 `persona_profile`，函数体只把它赋给占位变量，随后仍直接创建 LongMemEval runtime；2026-07-24 删除这个未使用参数只是清理无效接口，不代表语义曾从“已注入”变成“未注入”。历史 runner 的回答主要依据切分后的对话历史、问题和选项。

两套数据最终都形成三个相互分开的对象：供回放的历史、只在问答阶段发送的问题、只在评分阶段读取的标准答案。这种拆分降低直接答案泄漏，但仍需用真实运行记录证明 prompt 和工具材料没有从其他路径带入评分字段。

### 9.3 历史基线中，一道题怎样运行？

历史实现不是直接调用一次模型，而是复用当时的完整 Agent 执行入口：

```text
┌──────────────────────────────┐
│ 为题目创建独立 workspace      │
│ 初始化旧运行时与模型绑定      │
└───────────────┬──────────────┘
                ▼
┌──────────────────────────────┐
│ 把历史分段依次写入本题历史会话│
│ 每段保存，最后记录回放完成状态│
└───────────────┬──────────────┘
                ▼
┌──────────────────────────────┐
│ 在本题独立 QA 会话提交问题     │
│ 旧执行循环判断回答或调用工具   │
└──────────┬───────────┬───────┘
           │直接回答   │调用工具
           │           ▼
           │   召回 / 消息搜索 / 原文读取
           │           │结果回到下一轮判断
           └───────────┴──────────────┐
                                      ▼
                         ┌────────────────────┐
                         │ 保存答案与工具轨迹 │
                         │ 按题型评分并写结果 │
                         └────────────────────┘
```

第一步，runner 用题目 ID 建子目录，并在其中初始化当时的生产运行时。每题获得自己的旧会话存储、记忆状态、模型注册库副本和运行实例；评测专用 `SELF.md` 要求英文短答，并引导 Agent 先召回、材料不足时搜索消息、具体事实再读取原文。

第二步，runner 不重新生成历史回答，而是把数据集给定的用户/助手消息直接写入旧会话对象。LongMemEval 的多个分段都进入本题同一个历史会话；PersonaMem 切出的多个对话段也复用同一摄入函数，进入本题自己的 `pm:<question_id>` 历史会话。每段保存后继续下一段，全部完成才写 `ingest_state.json`。

第三步，runner 在同一题目 workspace 内另建 QA 会话，把问题交给旧执行循环。循环发起真实 Agent 模型请求，自主判断是否调用当时已注册的 `recall_memory`、`search_messages` 和 `fetch_messages`；工具结果回到下一轮模型判断。外部投递被关闭，所以观察对象是回答与工具过程，不是渠道发送。

第四步，runner 从最终输出取答案，并从旧 QA 会话最后一个带 `tool_chain` 的助手消息读取工具调用链。LongMemEval 再调用默认角色模型做 Judge，同时计算 F1 与 EM；PersonaMem 解析选项标签并计算准确率。问答阶段的超时或异常被写进本题结果，不能与答错混成同一种情况；runtime 初始化或 Judge 自身异常则会向外传播，可能中断整批运行，这是历史错误处理的边界。

第五步，启用自动续跑时，本题结果写入 `result.json`，回放进度写入 `ingest_state.json`，可读工具过程写入 `trace.log`；整批完成后另写汇总 JSON。由此保存的是模型输出片段、工具请求、参数、执行结果和最终答案，不是模型不可见的完整内部思维。

### 9.4 逐题隔离和断点续跑怎样工作？

runner 为每个题目创建独立子目录，并在里面初始化运行 workspace、旧会话数据库、记忆状态、结果与轨迹。根评测目录中的模型注册库只读复制到新题目的目录；并发 worker 通过信号量限制同时处理的题数。其目标是让一道题的历史和记忆不能被下一道题直接读取。

```text
评测根目录
├── 题目 A：独立消息、记忆、结果、轨迹
├── 题目 B：独立消息、记忆、结果、轨迹
└── 题目 C：独立消息、记忆、结果、轨迹
```

自动续跑再按三个层次判断：

```text
本题结果 JSON 可读取？
├─ 是：整题复用，不再启动 runtime
└─ 否：回放状态标为完成？
   ├─ 是：保留消息和记忆，只重跑问答与评分
   └─ 否：数据库里已有本题部分历史？
      ├─ 是：清空本题子目录，从头回放
      └─ 否：直接从头回放
```

逐题结果保存问题、标准答案、模型答案、工具链、耗时和错误；LongMemEval 还保存 Judge 结论，PersonaMem 保存选项、解析出的标签与是否正确。F1、EM、准确率和解析率在汇总时计算。回放状态保存题目身份、完成标志和消息计数；可读轨迹另存评测提示、模型描述和工具过程。问答失败时，已完成回放和本题会话仍留在子目录；回放只完成一部分时，自动续跑删除并重建**该题子目录**，不会清理其他题目。

这里的“断点续跑”是粗粒度阶段恢复，不是从某条历史消息或某个工具调用中间继续。这样能避免重复写入半份历史，但这套判断偏信任本地文件：

- 可读取的结果 JSON 就直接复用，没有校验结果字段是否完整，也没有核对数据集、源码、prompt、配置、模型或 Judge 版本。
- 回放完成只看布尔标志，没有用保存的预计数与实际数重新核对数据库。
- 模型注册库只在本题首次创建时复制；根配置后来变化，旧题仍可能沿用旧副本。
- 只有启用自动续跑时才逐题保存结果；普通整批运行如果中途退出，已经完成的内存结果未必形成可复用文件。

因此它能减少同一冻结实验中的重复工作，但还不是可跨版本可信复用的 artifact 协议。更稳妥的做法是给每题结果记录数据摘要、题目摘要、源码提交、配置摘要、模型 revision、prompt 版本、Judge 身份和阶段终态，任一关键身份变化就拒绝静默复用。

隔离方面，源码已经控制了题目目录、运行实例、旧会话和记忆文件的直接串题风险；仍没有历史测试证明同进程多 worker 下不存在进程级单例、插件发布锁或环境变量污染。子目录还直接使用数据集问题 ID，worker 数也没有 runner 自己的硬上限。准确说法是“实现了逐题隔离结构”，不能把目录不同扩写成已经验证所有状态零泄漏。

### 9.5 Judge、F1、EM 和选项准确率分别适合什么？

| 指标 | 它怎样判断 | 适合什么 | 主要限制 | 历史 runner 实际使用 |
|---|---|---|---|---|
| Judge | 把问题、参考答案和模型答案交给默认角色模型，只接受 `yes/no` 语义判断 | 开放式答案、同义改写、数字或地点的不同表达 | 有模型偏差、随机性和自评倾向；单次二值判断没有置信度 | LongMemEval 主 runner 在问答无错误时使用 |
| F1 | 小写、去标点后按空格切词，计算答案与参考答案的词元重合 | 英文短答案的部分匹配，辅助观察“答到多少” | 同义词得分低；冗长答案可能受罚；不理解事实关系 | LongMemEval 对全部题计算，运行错误按 0 分 |
| EM | 同样规范化后要求整串完全一致 | 答案格式稳定、短而唯一的事实题 | 对等价表述非常严格 | LongMemEval 对全部题计算，运行错误按 0 分 |
| 选项准确率 | 先解析 `(a)` 等标签；也接受独立字母、完整选项文本或达到阈值的文本匹配，再与标准标签比较 | PersonaMem 的单选题 | 解析启发式可能把不规范长答案误判为某个选项；不能解释选择理由 | PersonaMem 使用，并同时报告解析率 |

LongMemEval 的历史主 runner 在问答无错误时调用 Judge；Judge 有结果的题才进入 Judge 分母，F1 和 EM 则把运行错误计为零。这两个口径不能混读：如果大量题因基础设施错误没有 Judge 结果，剩余题的 Judge 正确率仍可能看起来很高。正式报告必须同时展示总题数、有效问答数、Judge 覆盖率和错误分类。

PersonaMem 不调用 Judge，正确性来自选项标签；解析失败和运行错误都进入总题数并算错。它额外报告解析率，帮助区分“选错了”与“答案格式无法解析”，但当前没有把二者展开成更细的自动故障类别。

### 9.6 工具轨迹怎样帮助定位失败？

历史 harness 从旧助手消息中取出工具链。LongMemEval 的文本轨迹保留模型输出片段、关键参数和结果预览，逐题结果 JSON 保留工具链结构；PersonaMem 的文本日志更完整，还写入原始工具链 JSON。它们记录的是可观察执行事实，不等同于模型不可见的完整内部思维。

人工分析时可以按以下顺序判断：

| 观察到的现象 | 可以提出的归因假设 | 还要排除什么 |
|---|---|---|
| 历史没有形成可检索状态 | 摄入或学习失败 | 不能先归因为召回算法；先核对回放数和记忆消费终态 |
| 已学习，但查询没有返回相关候选 | 召回不足或查询表达不佳 | 核对标准证据是否确实在已回放边界内 |
| 检索命中相关候选，但模型可见材料中没有它 | 去重、预算或材料呈现问题 | 命中记录与实际呈现记录必须分开看；仅看候选列表不够 |
| 相关原文已经呈现，答案仍与标准冲突 | 证据理解、冲突选择或回答生成错误 | 先确认标准答案和 Judge 本身有效 |
| 答案语义正确但 F1/EM 低 | 指标与表达形式不匹配 | 用人工复核校准 Judge，而不是直接改答案 |
| 工具未调用、超时或输出无法解析 | 执行策略、运行时或格式问题 | 这不是记忆质量分，应单列 harness/infra 错误 |

轨迹为人工失败分析提供证据，可以辅助区分召回不足、材料未呈现和证据使用错误；当前没有证据表明已实现自动归因分类器。对工具调用得到的结果，可以检查它是否随工具循环回到下一次模型判断；对自动注入材料，旧 `tool_chain` 本身不够，还需要关联当时的请求材料或记忆记录。因此“支持区分”是人工分析能力，不是系统自动给错题分类。

### 9.7 收益、边界与仍缺的实验

这套评测的收益是让记忆写入、检索工具、证据呈现、Agent 决策和最终答案处在同一次实验里，比只测检索排序更接近真实 Agent 行为。代价是结果同时受模型、评测提示、Judge、上下文预算和运行基础设施影响，不能把分数变化直接归因给记忆算法。

已确认的历史边界包括：LongMemEval 把同题多段历史合并到一个历史会话，不是多会话能力验证；PersonaMem profile 没有注入；Judge 是额外模型调用，存在成本、随机性和偏差；缓存没有版本指纹；轨迹支持人工分析而非自动归因。仓库内能确认的是结果**结构**，不是结果**数值**：README 对三类题的强弱有历史观察，但没有绑定数据摘要、源码提交、模型版本和逐题产物，不能作为本轮可复核实验结论。

要让评测真正支撑面试中的效果论证，建议按以下顺序补证据，而不是立即跑全量：

1. **兼容性 smoke。** 迁移回放、问答和轨迹读取后，只用合成的两三题验证历史进入记忆、问答走统一循环、结果与终态可恢复，不调用正式全量数据。
2. **隔离与续跑测试。** 并发放入互斥事实，验证零串题；分别在回放中断、问答中断、结果损坏和版本变化时检查恢复分支与缓存拒绝。
3. **Judge 校准。** 随机抽取正确、错误、部分正确和格式不同的答案做人工双人标注，对照 Judge、F1 和 EM，并记录 Judge 模型与 prompt 版本。
4. **记忆对照。** 同一冻结样本比较无长期记忆、仅自动注入、允许显式补搜等条件；一次只改变一个变量。
5. **召回消融。** 在其他条件不变时分别关闭图关联补全或向量直召回，观察候选、实际呈现和最终正确率，不能只看总分。
6. **上下文对照。** 对长历史比较未触发与触发摘要的题，记录质量、输入输出 token、额外调用和延迟，防止把成本下降与答案正确混为一个指标。

正式结果还应冻结数据摘要、代码提交、配置、模型/embedding revision、评测提示、并发数、超时、Judge 身份和所有错误。未取得这些证据前，不给出提升百分比，也不把 README 的定性观察扩写成个人效果数字。

### 9.8 版本边界与当前维护状态

当前维护基线是 `2f0bd7feb1d457d1fb45be1a1579c6689424a1fb`。2026-09-07 的 `477ef1172bd3c25085c775e8a2848d4584a8c2d2` 把主运行链切换为 Message、Turn 与普通插件组合，并从 `CoreRuntime` 移除了旧 `loop` 和 `session_manager`。`eval/` 从 `d565ca44` 到切换提交、再到当前 HEAD 没有变化，因此保留下来的 runner 仍读取已经移除的旧对象：回放取 `core.session_manager`，问答取 `core.loop`，轨迹再从旧助手消息的 `tool_chain` 读取。

这表示**旧 runner 尚未迁入新消息运行架构**，不表示历史实现当时使用了 Message、Turn 或新插件投递对象，也不表示 LongMem 历史合并或 Persona profile 未注入是迁移造成的。迁移后的实现需要重新选择消息接纳、学习完成判断和轨迹投影入口；这些属于后续维护工作，不进入本轮历史流程叙事。

### 9.9 约 2 分钟口播

> 我做端到端评测时，不只看记忆检索有没有命中，因为命中以后还可能没有进入请求，或者模型拿到证据却用错了。我的主线是把每道题当成一个独立实验：先回放这道题的历史，再让真实 Agent 完成问答，最后按题型评分并保留工具过程。
>
> LongMemEval 用开放式问题，覆盖用户事实、偏好和知识更新。数据中的多段历史会按顺序写进这道题自己的一个历史会话，所以这里测的是题目级隔离，不把它包装成多会话能力。PersonaMem 会读取 profile 字段，但当时没有注入 Agent；它实际使用的是切分后的对话历史、问题和选项。
>
> 运行时，每题创建独立 workspace 和运行实例，先写入历史，再在单独的问答会话把问题交给当时的执行循环。Agent 会自主决定是否调用记忆召回、消息搜索和原文读取工具；工具结果回到下一轮判断，最后保存答案和工具轨迹。续跑先看逐题结果，再看历史回放是否完成；只有部分历史时就重建本题，避免重复追加。
>
> 评分上，LongMemEval 同时看语义 Judge、词元 F1 和精确匹配：Judge 容纳等价表达，F1 和 EM 提供确定性辅助口径；PersonaMem 解析选项标签，统计准确率和解析率。失败分析时，我再结合轨迹检查是没召回、材料没呈现，还是模型拿到证据却没有用对。这里是为人工归因提供证据，不是自动失败分类器。
>
> 这套评测对应简历项目实施时的历史运行架构；当前主干已经切换执行架构，旧 runner 需要单独迁移，这属于后续维护状态，不改变当时的实现事实。仓库没有保留可复核的正式结果，所以我只讲已确认的设计和方法，不补效果数字。

### 9.10 常见追问与理解自测

| 追问 | 应能解释的处理逻辑 |
|---|---|
| 为什么 Judge 对了还要看 F1/EM？ | Judge 能理解语义但有模型偏差；F1/EM 可重复但不理解同义表达，三者互补且口径不同。 |
| 为什么不能只看召回命中率？ | Agent 最终还要经历预算呈现、冲突判断和答案生成；命中不等于看见，看见不等于用对。 |
| 正确答案怎样避免泄漏？ | 历史、问题和标准答案在对象上分开；标准答案只传给评分器。仍需用冻结 prompt 与实际材料记录验证没有旁路。 |
| LongMemEval 的多个历史分段代表多会话吗？ | 不代表。分段按数据顺序写进同一道题的一个历史会话，并为消息设置对应日期；已证明的是题目级组织和隔离，不是跨独立会话能力。 |
| Persona profile 有没有进入 Agent？ | 没有。loader 读取了它，早期包装函数也接收过参数，但函数体未使用；后来删参是清理无效接口。 |
| 每题一个目录就一定隔离了吗？ | 它实现了工作区、运行实例、会话和文件边界；进程级单例、环境变量和并发污染仍需专门 smoke 证明。 |
| 断点续跑会不会复用旧结果？ | 会有风险；历史 runner 只看文件和完成标志，没有版本指纹，跨数据、代码或模型变化时可能静默复用。 |
| 知识更新答对能证明旧事实已删除吗？ | 不能；可能是新旧证据同时存在，Agent 最后选对了新值。需要单独检查记忆状态与冲突证据。 |
| 系统是否自动区分召回和生成错误？ | 没有。现有答案、评分和轨迹支持人工分析；自动分类需要独立规则、证据输入和校准。 |
| 为什么选择 `d565ca44` 作为历史基线？ | 它是切换前最后一个同时包含两套 runner、旧循环、旧会话对象和所需工具目录的提交；README 有运行旁证，但缺少可复核结果产物。 |
| 当前 runner 为什么不能代表历史实现失效？ | 切换提交移除了旧运行对象，却没有修改 `eval/`；这是当前迁移欠账，不会改变切换前的实现事实。 |

验收标准：不看源码也能画出历史基线的“题目级环境—合并回放—真实 Agent 问答—评分—人工归因”流程；能说明 LongMem 多段历史不是多会话、Persona profile 未注入、四类指标和三级续跑分支；能把当前 runner 迁移欠账放在版本维护说明，而不混入历史流程；能设计一个隔离测试和一个单变量消融，不编造现有分数或自动归因能力。

## 10. 主动交互：怎样把“值得打扰”变成可恢复的决策

本节对应简历中的主动交互策略，以当前 Message 维护基线 `2f0bd7feb1d457d1fb45be1a1579c6689424a1fb` 为事实版本。这里讨论的主要是普通 Content；Alert 和 Drift 有不同职责，不能把它们都讲成同一套“兴趣初筛—证据调查”。

简历原句可以保留，但面试时要把三个容易混淆的词说准：**触发前的兴趣质量计算、模型执行的兴趣初筛、调查后的发送决定是三层不同判断；“兴趣衰减”实际衰减的是内容 revision 的准入质量；“事件版本去重”是精确身份幂等，不是语义新闻去重。**

### 10.1 先把简历中的每个短语落到机制

| 简历短语 | 当前实现中的准确含义 | 不应扩写成 |
|---|---|---|
| 基于用户记忆的兴趣初筛 | 进入模型阶段前，候选的 preprocess 兴趣与最近已完成、可学习对话的语义兴趣合成；进入初筛阶段后，模型还会结合自动提供的记忆材料、主动规则、最近对话和已送达消息，选出 1～8 条并提出待核问题 | 只做一次 embedding 相似度过滤；或只要与历史相似就一定发送 |
| 工具辅助的证据核验 | 第二阶段只开放 `recall_memory`、`web_fetch` 和两个终态决定工具；用记忆召回核对偏好与雷点，用网页读取核对外部事实 | 已实现任意网页搜索、事实真伪证明或自动引用正确性判定 |
| 限定调查步数 | 当前调查阶段 `max_steps=20`；初筛阶段只有 1 步，必须提交结构化 `screen_content` | 20 次网页请求；步数等于工具调用次数；或所有主动职责都使用 20 步 |
| 决定发送或跳过 | 调查必须且只能形成一个成功的 `share_content` 或 `skip_content`；普通模型正文没有发送权 | 模型输出任意一段 final text 就会推送 |
| 事件版本去重 | EventMail 用稳定 `source_id + item_id + revision` 识别 Content revision；同身份同内容重放幂等，不同内容复用同身份会显式冲突 | 按标题、URL 或语义自动合并跨来源新闻 |
| 兴趣衰减和唤醒阈值 | 首次兴趣证据固化成初始质量，之后按 36 小时半衰期只衰减内容准入质量；低于 `0.02` 不贡献，总质量严格大于固定 `1.0` 且存在新到达 revision 才启动 Content 模型流程 | 用户兴趣随时间被修改或遗忘；阈值已经通过线上数据调到最优 |
| 不适合打扰时静默结束 | 模型可以带理由 `skip_content`；低于门槛、无到期职责、领取冲突或无有效唯一决定也不会产生用户消息，并保留可区分状态；无发送目标时暂停新职责准入，只继续 Content 池维护 | 存在一个已核实的免打扰时间段、在线状态硬门或统一 presence 算法 |

这张表是面试回答的边界。源码能证明这些项目行为；“主要开发者”和具体个人贡献仍以简历声明为准，不能用 Git 作者或功能存在反推归属。

### 10.2 一条 Content 主动链路怎样走

```text
来源提交 Content revision
        │  EventMail 精确身份幂等、保存不可变信封
        ▼
到期池维护：首次兴趣评分 → 固化初分 → 时间衰减
        │  有新 revision 且 pool mass > 1.0
        ├──────── 否 ───────▶ 记录 no_due / content_insufficient，不启动模型
        ▼
冻结候选页与本轮模型、工具、目标、规则、近期上下文
        ▼
兴趣初筛（1 步，只能 screen_content，选 1..8）
        │  保存阶段消息；按冻结身份领取候选
        ├──────── 无有效结果 ─▶ defer / invalidated，用户侧静默
        ▼
证据调查（最多 20 步）
  recall_memory + web_fetch
        │
        ├─ skip_content(reason) ─▶ 释放候选、零发送、内部 quiet 收口
        ├─ share_content(message, 1..5 ids)
        │                           ▼
        │                    完整消息投递并等明确回执
        │                           ├─ delivered ─▶ 领域 settlement
        │                           └─ unknown ───▶ 保留锁定与恢复事实
        └─ 缺失/重复/越界决定 ─▶ defer，零发送
```

这条链路不是“定时器一响就让模型写推送”。外层先做可重复计算的到期与质量检查，只有达到门槛才为模型支付成本；模型再分两阶段缩小候选并核验证据；最后只有结构化分享决定经过真实投递，才改变 Content 的已送达状态。

### 10.3 触发前：兴趣、衰减和阈值具体怎样计算

**第一步，冻结每个 revision 的初始兴趣证据。** Content 首次到期时，Wake 读取来源提供的 preprocess 兴趣，并调用 Akasha 的只读语义兴趣能力。后者只使用截止本轮时间前、已经完整结束且允许学习的对话；每个历史样本以用户输入为主、助手回复为辅形成向量，最多保留最近 256 个 prototype，再以候选与最相似 prototype 的相似度四次方形成 `0..0.999` 分数。缺少可用历史时返回零；provider、维度或数据错误不会伪装成零兴趣。

两种兴趣按下面的“至少一方命中”方式合成，而不是简单相加：

```text
interest = 1 - (1 - preprocess_interest) × (1 - semantic_interest)
initial_quality = -ln(1 - interest) × publication_confidence × eligibility
```

有可信发布时间时 publication confidence 为 `1.0`，没有时为 `0.03`；明确不可唤醒的条目再乘 `0.01`。这些值与语义兴趣一起按稳定 revision 保存，之后不因用户新增对话重新评分。这样同一条旧内容不会每五分钟用变化后的记忆改写过去的准入依据。

**第二步，只衰减内容质量。** 以后以发布时间，没有时以首次观察时间为起点，按 36 小时半衰期计算 freshness，再乘已保存的初始质量。这里没有修改长期记忆，也没有给用户兴趣本身设置“过期时间”。因此口播最好说“内容兴趣质量随新鲜度衰减”，不要说“用户的兴趣会衰减”。

**第三步，用固定池门槛决定是否启动模型。** 到期 pending/deferred revision 的衰减质量低于 `0.02` 时不贡献；其余直接求和。只有本轮存在尚未贡献过检查的新 revision，并且总质量严格大于 `1.0`，才进入 Content 流程。没有随机抽签或冷却期；来源多样性只调整候选页排序，不改变 pool mass。没有新到达时，旧池只继续衰减、记录和过期，不会自己反复启动模型。

Wake 另有不超过五分钟的维护循环。它记录 active、due、expired、scored、new、new mass、pool mass、threshold、below-floor 和 driver。revision 至少驻留 24 小时且质量低于 floor 后，Wake 才通过 EventMail 的精确引用接口请求逻辑过期；不可变信封和 transition 仍保留。

### 10.4 模型初筛：为什么还要第二层兴趣判断

数值门槛回答的是“这一池是否值得花一次模型判断成本”，不能理解“为什么此刻值得告诉这个用户”。进入模型流程后，Wake 固定本轮 EventMail watermark、候选页、模型选择、工具 binding、发送目标、主动规则和近期上下文，再把按衰减质量排序的最多 100 个到期候选交给初筛阶段。

初筛阶段只看兴趣，不负责验证外部事实；它只有一个模型步骤，并且只能调用 `screen_content`。有效结果必须选择 1～8 个不重复的 `candidate_id`，为每条写初步兴趣理由和下一阶段需要确认的问题。此阶段可以看到自动提供的记忆材料，也能看到固定在请求中的最近上下文：目标会话最近最多 20 条被动消息，以及七天内最多 30 条跨会话已送达的非被动消息；两类各有独立 3,000 字符预算，初筛和调查复用同一快照。

最近已送达消息只提供连续性背景，不是硬编码的重复惩罚。项目没有按相同主题、URL、相似度或发送次数直接禁止分享；相似事件是否仍有新价值交给模型结合事实、偏好、反馈、时间和上下文判断。

如果初筛没有产生唯一有效结果、引用批次外候选或阶段失败，系统不会猜一个候选继续。它会按失败是否可重试将领取标成 defer 或 invalidated，并保持用户侧安静。

### 10.5 证据调查：20 步预算约束的是什么

通过初筛的 1～8 条候选按冻结引用领取后，第二阶段进入最多 20 步的 ReAct。这个“步”是当前开放段中已经保存的模型 Output 数量预算；一个步骤可能直接给终态决定，也可能提出一个或多个工具调用，因此不能把它口播成“最多请求网页 20 次”。

调查阶段的工具集合被精确缩为：

- `recall_memory`：主动组织查询，重点确认用户偏好、雷点和相关历史；
- `web_fetch`：读取候选网页，核对外部正文；
- `share_content`：提交唯一用户正文与实际采用的 1～5 个候选 ID；
- `skip_content`：提交只用于内部审计的跳过理由。

调查阶段不再自动追加新的 Akasha 或 Markdown 记忆材料，而是让模型显式调用 `recall_memory`；但它仍保留初筛阶段已经写入同一内部 Message 会话的原请求、初筛结果、近期上下文和固定材料身份。候选、历史、网页和工具结果都按低信任材料处理，不能借正文中的指令扩大工具或发送权限。

超过 20 步会形成明确 StepLimit 失败；模型错误按 provider 的 retryable 属性分类。存储错误、工具效果未知等不能被包装成普通跳过。恢复时先读取已经保存的阶段 Input、Output、ToolCall 和 ToolResult；阶段已有终态就不再开一次模型或重做工具效果。

### 10.6 发送、跳过和静默分别改变什么

**分享。** `share_content` 必须引用冻结领取中的 1～5 个不重复候选。系统只把它的 `message` 当作用户正文，并补上本轮实际采用候选中尚未出现在正文里的合法 HTTP(S) 来源链接。整批只产生一条逻辑消息；未被引用的候选回到可用池。随后以本轮冻结的发送目标和 Sender binding 投递；只有 provider 明确返回 delivered，EventMail 才结算所选 revision。

**跳过。** `skip_content(reason)` 释放本轮领取，候选保持 pending，不执行来源 ACK，也不产生目标会话消息。由于本批新 revision 已记录为贡献过一次检查，没有新 revision 到达时不会立即重复启动；以后新内容触发新的池检查时，旧候选仍可随其当时的衰减质量参与。

**静默不是一个模糊空结果。** 低于门槛、没有到期职责、CAS 领取冲突、模型明确 skip、可重试 defer、不可重试 invalidated、触发后取消、运行失败和 delivery unknown 都有不同的 attempt 或领域状态。已接纳的内部流程在不发送时用内部 `quiet` Output 关闭，不把空文本发给用户。普通模型 final response 也没有直接发送权；只有成功的私有决定工具能授权后续投递。未配置发送目标时不启动新的职责流程，只继续五分钟 Content 池维护；这不是一次模型 skip。

**发送结果未知。** 超时或取消不能证明外部未发生。若已经进入发送但没有明确成功回执，系统不把 Content 标为 delivered，也不自动重选同一引用。被实际引用的成员保持锁定，未引用成员仍可进入后续选择；恢复继续读取原 Message、决定、目标和回执，而不是重新生成一条可能重复的通知。

### 10.7 “事件版本去重”为什么不是标题去重

来源提交前必须给出稳定的 `source_id`、`item_id` 和 `revision`。EventMail 对同一批次保存 fingerprint，对同一 revision 保存 canonical payload：

1. 同一批次、同一 fingerprint 重放，直接复用原提交回执。
2. 同一 revision、相同正文和关键属性再次出现，记为 duplicate，不增加第二条 item。
3. 同一批次或 revision 身份却出现不同内容，抛出 identity conflict；不能让新正文静默覆盖旧事实。
4. 真正的新 revision 是新事实，可独立进入池、评分和生命周期。

Wake 的 `candidate_id` 也由这三个字段生成，只能解析回本轮冻结批次。领取时还比较 snapshot_seq 与 state_version；候选在初筛和领取之间变化，CAS 会拒绝，系统静默延期而不是把决定套到新版本上。

这套机制解决的是精确重放、并发领取和恢复一致性。两个来源报道同一新闻、同一 URL 改写标题、或不同 revision 语义相同，都不会被它自动合并。近期已送达消息可以帮助模型识别边际价值，但没有核实到通用语义 deduper。

### 10.8 Content、Alert、Context 和 Drift 不共用一套决策

| 职责 | 是否触发模型 | 判断和终态 |
|---|---:|---|
| Content | 达到新到达与池阈值后才触发 | 数值准入 → 一步兴趣初筛 → 最多 20 步调查 → share/skip |
| Alert | 到期即优先处理，不走兴趣初筛 | 固定原告警 envelope，模型只提交 `share_alert`；发送前重新检查是否过期 |
| Context | 自身不触发推送 | 作为当前事实背景进入请求，可 supersede 或过期 |
| Drift | 有到期 proposal 且没有更高优先职责时触发 | 不走 Content 两阶段；用 share/skip 决定是否发送内部主动想法 |

到期职责顺序是 Alert、达到阈值的 Content、Drift。它们共享 Message、ReAct、工具回执和 Delivery 基础能力，但 EventMail 保留三类信封各自的生命周期，Drift 也拥有自己的 proposal 状态。面试时不应为了叙事整齐而说“所有主动消息都先做兴趣初筛”。

### 10.9 这套设计的收益、代价和待补数据

**收益。** 确定性池先控制模型启动频率，两阶段再把“感兴趣”和“事实可信”分开；结构化终态工具把模型建议与发送权限分开；稳定 revision、冻结快照和 Message 日志让崩溃恢复不需要猜测；真实 delivered 之后才结算，减少重复推送与假成功。

**代价。** 固定分数、floor、阈值、半衰期和步数都是策略选择，可能漏掉单条低分但重要的信息，也可能让多条普通内容相加触发；一次评分不随新偏好更新提高可复现性，却会错过用户兴趣变化；显式调查增加模型、记忆和网页调用成本；精确版本幂等不解决跨来源语义重复。

**还缺什么证据。** 仓库有当前 Message 流程测试、本地 fixture provider Gate、迁移和恢复测试，但 H5 manifest 仍把真实 provider 场景标为 pending。本轮没有运行线上或真实用户实验，也没有发送率、跳过率、误打扰率、点击/回复反馈、人工有用性、事实正确率、token、延迟或成本对照。后续补评测数据时，应至少冻结事件集、用户历史、模型和 embedding revision、规则、阈值、工具网络快照及人工标签，再分别观察：

- 数值准入的通过率和漏报；
- 初筛保留率与人工兴趣标签；
- 调查后的事实正确率、有效决定率和平均步数；
- share/skip、delivery unknown 与恢复重复发送率；
- 有用率、误打扰率及用户真实反馈；
- 去掉语义兴趣、时间衰减、近期主动历史或证据调查后的单变量消融。

在这些数据补齐前，只能说明机制与已有确定性测试，不能声称“显著降低打扰”或参数优于其他方案。

### 10.10 约 2 分钟口播

> 主动推送和被动问答不同：不是有事件就生成一段话，还要先决定值不值得花模型成本、是否真的与用户相关、事实是否可靠，以及发送结果能不能确认。我把 Content 链路分成确定性准入、兴趣初筛、证据调查和投递结算四层。
>
> 来源先把每个事件按 source、item 和 revision 写入 EventMail；同版本同内容可以幂等重放，不同内容复用同一身份会直接报冲突。候选第一次到期时，系统把来源预处理兴趣和用户已完成对话的语义兴趣合成，转成固定初始质量。之后不重算用户兴趣，只让内容质量按 36 小时半衰期下降。低于 floor 的条目不贡献，池总质量超过固定阈值且确实有新版本到达，才启动模型，所以旧积压不会自己反复唤醒。
>
> 模型侧再分两阶段。第一阶段只有一步，结合记忆、最近对话、已送达主动消息和当前候选，用结构化工具选出最多八条并写待核问题；第二阶段最多 20 步，只开放记忆召回、网页读取和发送或跳过工具。最终必须恰好提交一个 share 或 skip，普通回答文本不能直接推送。分享最多引用五个冻结候选并只产生一条消息；跳过会保留内部理由，用户侧不收到空消息。
>
> 可靠性上，每个阶段的输入、工具调用和结果都写入独立内部 Message 会话，模型、工具、候选快照和发送目标也在接纳时固定。只有渠道明确送达后才结算原事件；发送结果未知时保留原引用和回执等待恢复，不自动生成第二条。这里的版本去重是精确身份幂等，不是跨来源语义去重；所谓兴趣衰减也是内容准入质量衰减，不是用户兴趣被系统改写。目前这些机制和本地 Gate 有证据，但没有线上打扰率或效果数字，所以我不会把固定参数说成已经调优。

### 10.11 常见追问与理解自测

| 追问 | 应能解释的处理逻辑 |
|---|---|
| 为什么数值准入以后还要模型初筛？ | 数值层控制是否值得启动模型，不能理解此刻的用户语境；模型层结合记忆、近期上下文和候选内容缩小调查范围。 |
| “兴趣衰减”衰减了什么？ | 衰减的是 revision 首次评分后的内容准入质量；语义兴趣和初始质量固化，长期记忆没有被这条公式修改。 |
| 为什么只有新内容才能唤醒？ | 旧池会贡献本轮总质量，但没有新 revision 时只维护、衰减和过期，避免同一积压反复启动模型。 |
| 阈值是多少，能配置吗？ | 当前代码固定 threshold `1.0`、floor `0.02`，采用严格大于；本轮没有找到普通配置项，也没有参数最优性的效果证据。 |
| 20 步是不是 20 次网页访问？ | 不是，是调查阶段的 ReAct 输出步数上限；每步可能没有工具，也可能包含工具调用。 |
| 初筛和调查分别能用哪些工具？ | 初筛只能 `screen_content`；调查可用 `recall_memory`、`web_fetch`，并必须以一次 `share_content` 或 `skip_content` 结束。 |
| 模型写了 final response 会发送吗？ | 不会。普通正文只属于内部执行记录，只有成功的私有 share 决定进入投递。 |
| skip 会把事件删除或 ACK 吗？ | 不会。它释放领取并保持 pending；本次新到达检查已消费，无新内容时不重复唤醒。 |
| 版本去重能消除同一新闻吗？ | 只能消除同 source/item/revision 的精确重放，并拒绝身份冲突；跨来源语义重复交给上下文辅助下的模型判断。 |
| 为什么不能在超时后直接重发？ | 超时不证明 provider 未收到。delivery unknown 保留引用和回执，避免同一事件被第二次选择和发送。 |
| “不适合打扰”有免打扰硬规则吗？ | 本轮未核实统一 DND/presence 门；当前 Content 依靠规则、时间、记忆、最近上下文和模型 skip，低门槛与异常分支也会静默。 |
| Alert 也会先过兴趣阈值吗？ | 不会。Alert 是来源明确上报且可过期的信号，到期后优先处理；Content 才走衰减池和两阶段决策。 |
| 已经证明减少了多少打扰吗？ | 没有。当前能证明机制、状态边界和测试场景；真实有用率、误打扰率和成本需要后续冻结实验。 |

验收标准：不看源码也能画出“EventMail revision—确定性衰减池—一步初筛—20 步调查—结构化 share/skip—真实送达结算”流程；能区分两层兴趣、内容质量衰减和长期兴趣、精确版本幂等和语义去重、内部 quiet 和 delivery unknown；能解释 Content、Alert、Context、Drift 的不同职责，并明确现有参数没有效果最优性证据。

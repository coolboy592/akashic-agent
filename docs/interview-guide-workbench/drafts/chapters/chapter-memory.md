# 能力章：长期记忆与证据检索

> 对应简历条目：「集成并改造 Akasha 记忆引擎，融合稠密向量语义召回、BM25 词法检索与图关联补全，保留来源并对多路召回结果去重；设计『自动注入—按需补搜—原文取证』链路，使 Agent 可在摘要遗漏细节或新旧事实冲突时回源核实，支持基于历史证据回答。」
>
> 事实底稿：`packets/03-memory.md`；主张边界：`01-fact-boundaries.md`。文中实现细节均已对基线源码副本（`d565ca44356b5d52fe8d00f8cb008c14fff56c0b`，`F:/agent/akashic-agent-d565`）核实。

## 一、口述层

> 段首加粗标签与括注字数仅为排练导航，口述时不读。全文第一人称，合计约 1600 字（含英文词），对应 3～6 分钟。

**【背景与问题】**（约 240 字）

做长期个人助手，最先撞上的问题是关键事实不在当前窗口：上周说过的配置、几个月前提过的偏好，跨了会话就看不见。最直接的反应是把历史压成摘要带着，但摘要会丢原话、时间、限定条件和低频细节——恰恰是后来需要核实的那部分。第二个反应是建向量检索、按相似度取回；这在语义相近时有效，但文件名、命令、配置项这类精确词法向量不一定敏感，"与已命中线索相关的其他历史"更是相似度排序覆盖不到的。还有个更隐蔽的问题：召回的候选常只是一段摘要预览，模型不知道它来自哪条真实消息，容易把截断的预览当成事实回答。

**【我的判断】**（约 300 字）

我的判断有三条。第一，长期记忆不是把更多文本塞进上下文，而是两件事：找得到、可核实。检索信号按证据类型分工——稠密向量管语义相近，BM25 管精确词法，图关联补全从已命中线索扩展相关历史；三路不是固定权重线性融合，而是先推断起始线索、再图上补全、最后稀疏化选择压掉弱候选。第二，一次检索不该包办所有取证：turn 开始自动注入少量候选，证据不足时主动补搜，要核对原话与时间时按来源回查原文——取证成本随不确定性递增。第三，查询与学习必须分离：检索只读现有记忆，学习只在交互提交后发生，否则多搜几次就改变记忆本身，召回不可复现。对比后放弃的：单路向量覆盖不足、全自动注入噪声线性涨、摘要当事实源不可核实。

**【具体行动】**（约 400 字）

我集成并改造 Akasha 记忆引擎作为检索内核，引擎负责学习历史、图维护与带来源的读取；我的工作在宿主侧，把引擎接进 Agent 运行时闭环，落成三条路。自动注入：渲染请求时把当前消息组织成查询，按"精确回忆"与"联想"两条通道写进动态记忆区块，注入量有字符预算封顶，超限明确截断。按需补搜：注册 `recall_memory`——Agent 发现证据不足时主动补搜记忆的工具——支持意图、时间与数量上限，每条记录带证据引用与来源标识。原文取证：注册 `fetch_messages`——按真实来源身份回查原始消息原文、可扩展前后文的工具——另配一个关键词定位原始消息的搜索工具兜底。三条路分工明确：前两条给线索，只有原文取证可直接作证。再加强制引用协议：回复用了记忆条目，必须在末尾列出实际引用的条目。学习侧对齐同一闭环：交互提交后才进入 embedding 与图学习，每条召回记录保留来源身份供回查。

**【结果与复盘】**（约 300 字）

这个方向没有端到端准确率数字，能讲清的是验证方式与边界。在隔离迁移/重放验证中：4,800 对相邻 user/assistant 消息，排除 6 个中断占位得 4,794 个学习样本；9,556 条必须存在的消息 embedding 全部有效；两个不同 hash seed 下 11 个冻结查询得到相同逻辑状态，重放结果不随哈希随机化漂移。这组数字证明样本边界正确、实现可稳定重放——不是记忆准确率，也不能外推成回答正确率。单查询显式召回低于 40 条只说明规模受控，不是 token 节省率。命中率、证据进入率、正确率的分层统计与三路消融尚未做，LongMemEval 一类评测是后续计划。

**【设计取舍、踩过的坑、怎么修的】**（约 350 字）

讲两个坑。第一个：中断的交互被当成完整问答学习。学习流程按相邻消息配对时，内容精确为 `[interrupted]`——系统标记执行中断的助手占位文本——的消息也被当成正常回答写进记忆。误判是把"消息在存储里相邻"当成"交互正常完成"；占位说明执行没结束，不该进长期记忆。修复是学习前识别精确占位、整对排除，只有完整交互才进入学习，验证即 4,800 减 6 得 4,794。第二个：在线热路径上的完整数据库扫描。现象是每次记忆使用都承担一项随库规模增长的完整检查，形状指向完整性验证——根因是迁移修复级别的验证被放进了在线请求路径。修复是移除在线全库扫描，重检查移到离线 Gate 与维护流程，验证以六个 Docker Gate 全部通过收尾。边界：能讲的只是去掉热路径的不必要工作，没有延迟数字，不补造。

## 二、支撑层

### 2.1 关键机制详解

#### 三层链路的宿主侧接线

- 自动注入的挂点：`PROMPT_RENDER_EVENT`（请求提示词渲染的生命周期事件）。`_inject_memory`（提示词渲染时的自动注入监听函数）把当前消息、会话范围与时间戳组织成 `MemoryQuery`（宿主到记忆引擎的统一查询请求，含文本、意图、范围、过滤器、上限），以 `intent="context"`（上下文注入意图）查询引擎，并把渲染结果追加为 `RETRIEVED_MEMORY_SECTION`（动态记忆区块名，标记为非静态、排序后置）。
- 注入预算是双层的：条数层由查询上限控制（宿主默认 `limit` 为 8；上下文意图下补全通道走 `context_recall_limit`（上下文注入时补全通道的条数上限配置），稠密通道取"查询上限与 5 的较小值"）；字符层由 `inject_max_chars`（自动注入文本的字符上限配置）封顶，超限在完整格式化后截断并标注"已截断"字数，不做静默裁剪。
- 两条通道按字面标题渲染为两个小节：稠密通道"精确回忆"、补全通道"联想"；条目内部不额外加语义标签，命中路径信息保留在结构化字段的来源标签里（见下文 `sources`）。
- `RecallMemoryTool`（按需补搜工具 `recall_memory` 的实现）：参数含查询意图（context / answer / timeline / interest / procedure）、时间过滤（today / yesterday / recent_3d～30d / 日期与区间）、数量上限（默认 8、最大 200）；每条记录返回 `evidence`（证据引用列表：类型、引用、解析器、来源标识）与 `signals`（命中的信号说明），并附引用协议标记 `§cited:[id列表]§`（要求最终回复末尾列出实际引用条目的输出协议）。timeline 意图在 Akasha 引擎中不支持，返回带标记的空结果而非报错。
- `SearchMessagesTool`（原始消息关键词搜索工具 `search_messages` 的实现）：对原始消息做子串式定位，返回带命中词的预览（至多 50 行，截断有标注）与 `source_ref`（消息的真实来源标识）。工具描述明确了它在链路中的位置：recall 之后、原文取证之前的文本定位，预览不能直接作证。
- `FetchMessagesTool`（原文取证工具 `fetch_messages` 的实现）：接受消息 id、`source_ref`、或直接传入 recall 返回的 `evidence` 列表（自动解析出其中的来源标识），可按 `context` 参数扩展每条消息前后各至多 10 条原文。工具描述自称三条路（记忆注入 / recall / 消息搜索）中唯一可以直接作为最终证据的工具。
- 来源闭环与可观测：当轮检索若以有状态上下文查询发出，引擎通过 `wait_for_active_recall`（把当轮检索结果冻结供查询的接口）绑定 turn，供 Inspector / 移动端"这条回答受哪些记忆影响"的回看视图；该绑定只读，不修改记忆图。

#### 三路信号如何协作（非固定加权融合）

- `FeaturePool`（把全部历史 turn 的稠密向量、词频倒排表组织成连续数组的证据池）：`dense_scores`（查询向量对每轮 user / assistant 向量的稠密相似分，逐轮取两侧较大值）提供语义信号；`bm25_scores`（向量化的精确 BM25 词法分，标准饱和形式 k1=1.2、b=0.75）提供词法证据。`bm25_document_score`（对单个文档词集打 BM25 分的方法）另用于查询与上下文的词法一致性判断。
- 分数先经 `_tail_surprisal`（把原始分转换为基于排名的 surprisal 值的变换）再进入融合：融合操作在无量纲的排名证据上，而不是在余弦分数和 BM25 分数两种不同量纲的原始分上直接加权。
- `BurstAwareFeaturePool`（在 `FeaturePool` 之上支持把当前查询作为临时线索挂进历史的证据池）的 `infer_burst_seed`（用查询与活跃上下文的四路证据推断起始线索的方法）：对查询侧与上下文侧分别计算稠密、BM25 两组证据，判定当前查询与活跃上下文是否同段，并得出 `context_mass`（上下文侧应占的证据质量，由延续信念与上下文依赖度经对数几率动态组合，不是固定权重）。
- `_mix_sources`（组合证据形成起始线索的函数）分两步：查询侧四路中的稠密与 BM25 先求和、上下文侧同理，两侧各自过 `_sparsemax`（稀疏化选择：像 softmax 一样输出归一化权重，但自动把弱候选压成精确零、只保留有限支撑集）得到稀疏支撑集；两个支撑集再按动态 `context_mass` 混合归一。所以"非固定加权"体现在两层：同侧的稠密与 BM25 是求和后稀疏化而非配权；查询与上下文之间的权重来自证据推断。
- `read_pattern_completion`（在准备好的记忆图上执行模式补全的读取函数，明确不修改记忆）：从起始线索出发在图上扩散激活（`residual_push`——把线索质量沿图上关系传播的扩散算子），上下文路由与独立寻址路由各自读取后竞争合并；输出 `RecallItem`（一条补全召回项：节点 id、分数、来源标签、所属盆地）。
- 来源标签即命中路径：`sharp_completion`（尖锐补全命中）、`basin_direct`（盆地直命中）、`basin_completion`（盆地补全）、`relative_tail`（相对长尾），稠密通道另有 `direct_dense`（直接稠密命中）——调试时可以解释"这条候选为什么出现"。
- 多路合并与去重：稠密通道（至多 5 条）先选定，补全通道按稳定节点 id 对稠密通道去重后填充；同一条历史若被两路同时命中，以稠密通道条目呈现并置 `also_completed`（该条同时被补全命中的标记）。排名决定谁入选，时间顺序决定如何呈现。

#### 记忆图：存什么、关系怎么形成、命中后怎么扩展

- `DynamicMemoryGraph`（动态记忆图）：节点是完整历史 turn；`hub`（枢纽：一次已提交事件在学习中形成的记忆聚簇节点，"事件因子化的记忆痕迹"）通过成员边绑定一组共同激活的历史 turn；事件之间另有时序前向 / 后向边。一个枢纽及其成员构成一个可整体激活的"盆地"。
- 关系在学习阶段形成：`learn`（把一次提交事件写入图的图学习入口）把直接召回与补全召回合并成连续活动场，对被检索暴露的旧枢纽与时序关系做 Oja 式竞争性修整（共同激活的增强、长期不激活的抑制），再为当前事件创建枢纽、写入成员关系与时序关系；遗忘开关打开时，边的可及性随复发存活时间衰减。
- 命中后的扩展即上一节的模式补全：从起始线索激活所在盆地，再沿盆地间关系扩散到相关历史——所以图关联补全返回的是历史中的相关节点，不是第三个独立的搜索结果列表，也不是凭空生成。
- 代价：图结构随学习持续修整，重建与重放有真实成本（隔离重放口径：4,634 个枢纽、21,254 条关系、全量重放约 157～216 秒）；查询行为比单路检索复杂，必须保留来源标签才能解释候选。

#### 查询与学习分离

- 查询路径：`query`（引擎统一检索入口）先对查询文本做 embedding，再过 `commit_gate`（提交闸门：检索等待在途的学习提交完成，避免读到图结构中间状态），随后在共享读锁内执行只读的 `query_turn`（以当前查询为临时线索执行一次完整读取的入口）。读取全程不写图；有状态上下文查询只额外保留一张供观察的票据，效果标记为 `read_only` / `stateful`，不涉及记忆修改。
- 学习路径：`AFTER_TURN_COMMITTED`（交互提交完成事件）把已提交交互放进单消费者队列，由 `project_committed_turn`（把一次已提交交互投影进记忆的入口：消息校验、embedding、样本与图学习）异步处理。检索发生在 turn 内、学习发生在提交后，分离是结构性的，不靠约定。
- 检索范围只在历史：当前 turn 的查询线索以临时视图挂进证据池（不可追加、不落盘），当前尚未完成的回答不会被当成已学事实检索到。

#### 学习样本边界与隔离重放验证

- 中断占位排除：相邻消息配对中，助手消息内容精确等于 `[interrupted]`（系统标记执行中断的占位文本）的配对整体排除；4,800 对相邻 user / assistant 消息、6 个中断占位、4,794 个学习样本。
- 隔离迁移 / 重放验证（以下数字全部属此口径）：9,556 条必须存在的消息 embedding 全部有效、无补算；4,634 个枢纽、21,254 条关系，全量重放约 157～216 秒；两个不同 `PYTHONHASHSEED`（Python 解释器哈希随机化种子的环境变量）下，11 个冻结查询的 canonical logical state（标准逻辑状态：以确定性方式从重放结果导出的一致性比较基准）完全相同；物理文件哈希只用于确认正式 workspace 未被修改，不作为等价性标准。Docker Gate `AKV2-01`～`AKV2-06` 全部通过。
- 单查询显式召回数低于 40 条的舒适范围：说明注入规模受控，不能写成 token 节省率。
- 以上均不能称为记忆准确率或回答正确率；query 命中率、证据进入率、答案正确率的分层统计与稠密 / BM25 / 图补全消融未做。

#### 通用概念对照

- BM25（基于词频与逆文档频率的经典词法相关性打分，Elasticsearch 默认相似度）→ [Elastic Similarity settings 官方文档](https://www.elastic.co/docs/reference/elasticsearch/index-settings/similarity)
- 混合检索与 RRF（稠密与词法双路召回后按名次倒数融合候选的常见配置）→ [Elastic 混合检索文档](https://www.elastic.co/docs/solutions/search/hybrid-search)
- bi-encoder 检索与 cross-encoder 重排（独立编码可离线索引 vs 查询—候选联合评分在线精排，作用位置不同）→ [sbert retrieve-rerank](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)
- sparsemax（softmax 的稀疏替代，能输出精确零的概率归一化，本项目稀疏化选择的出处）→ [sparsemax 论文](https://arxiv.org/abs/1602.02068)
- LongMemEval / PersonaMem（长程对话记忆与个性化记忆的两个标准评测基准）：仅作后续评测计划，不是当前成果。

### 2.3 与主流替代方案对比

**长期记忆检索：长窗口硬扛 / 持续摘要画像 / 单路向量 / 混合检索＋重排 / 图增强检索（本项目＝多信号＋图补全＋分层取证）**

- **不建长期索引（长窗口硬扛）**：零检索基建，上下文全保真。对方更优的场景：单会话短任务、历史本身没有复用价值。代价：跨会话事实不可见，输入成本随历史线性涨，超窗即失败。
- **持续更新的摘要画像**：把历史滚动压成一段用户画像 / 摘要随请求注入，零检索轮次、零工具依赖。代价：失真随更新累积，细节与限定条件最先被磨掉，且没有来源，无法回查核实——正好丢掉本章要的两件事。
- **单路向量 top-k（经典 RAG 配置）**：实现与解释最简，语义相近措辞不同的历史能召回。代价：精确词法（文件名、命令、配置项）与关联历史覆盖弱；分数不带来源，来源链要另建。
- **混合检索＋重排（业界主流的最强形态）**：稠密与 BM25 双路召回，RRF 按名次融合候选，再按需用 cross-encoder 对查询—候选联合评分重排；bi-encoder 负责可离线索引的召回、cross-encoder 负责在线精排，是召回上限与排序质量的分工。对方更强的场景：语料大、查询措辞多变、对排序质量敏感。诚实边界：本项目没有采用 RRF 融合，也没有 cross-encoder 重排——证据组织走的是排名变换＋线索推断＋稀疏化＋图补全这条路线；两者是同一问题的不同实现，没有对照实验，不断言孰优。
- **图增强检索**：从命中实体或线索沿关系扩展，补的是"当前措辞直接覆盖不到的关联"。GraphRAG 一类多用于语料级多跳问答，图从文档抽取构建；本项目的图是个人交互历史：节点为完整 turn、枢纽由学习阶段的活动场形成、命中后经模式补全扩展。为什么可能比加大 top-k 或重排多找到信息：top-k 与重排仍以"查询与候选的直接匹配"为中心，图补全从已命中线索的二阶关联出发，能带回查询措辞完全没提到的历史；但噪声与维护代价真实存在（枢纽修整、重建与重放成本、候选必须可解释），且无消融实验支持"优于"结论。
- **本项目在谱系中的定位与叠加关系**：信号类型与混合检索同源（稠密＋BM25），组织方式不同（线索推断＋稀疏化＋图补全 vs 双路召回＋RRF＋重排）；图补全与候选层重排原则上可叠加，但项目未做，不声称已具备。与对话压缩（见工具与上下文章）正交互补：压缩把旧内容卸载出窗口，本章解决卸载之后"找得到、可核实"的取回问题。

**取证链路：检索即答案 / 全自动大预算注入 / 注入＋补搜 / 注入＋补搜＋原文取证＋引用（本项目）**

- **检索即答案（把召回摘要直接当结论）**：零额外轮次。代价：截断预览被当成事实、新旧事实冲突无从分辨——正是本项目最初的现象。
- **全自动大预算注入**：行为可预测、不依赖 Agent 判断。代价：token 与召回噪声随预算线性涨，模型倾向把未核实的候选直接用掉。
- **注入＋按需补搜**：常见问题走低成本路径，复杂问题可追加更具体的查询。代价：何时补搜成为对 Agent 判断能力的新依赖。
- **注入＋补搜＋原文取证＋强制引用（本项目）**：可核实、可引用、可审计——哪条结论用了哪条记忆是可检查的输出。代价：多一跳工具调用、来源身份在召回与回查之间的传递必须是闭环、Agent 需要判断证据何时充分。
- 行业相邻形态：web 检索增强生成中的 grounding / citation（检索结果带编号引用）与本项目的引用协议同类，差别在证据源是公开网页还是私有交互历史，以及本项目把"原文取证"做成独立工具层而不是把引用附在检索结果上就结束。

**记忆写入与一致性：即时写入 / 模型自编辑 / 提交后学习（本项目）/ 离线重放验证**

- **即时写入（每次交互立刻更新记忆，读写共享状态）**：记忆即时生效。代价：检索带副作用——多搜几次就改变后续结果，召回不可复现；未完成交互直接污染。
- **模型自编辑记忆（MemGPT / Letta 形态，模型用工具直接增删改记忆块）**：表达灵活、可即时纠错。代价：写入质量依赖模型当下判断，误编辑直接进入长期状态，同样面临复现与审计问题。
- **提交后学习（本项目）**：交互提交后才投影（消息校验、embedding、图学习），查询全程只读、经 `commit_gate` 与学习互斥；中断占位在学习边界处被识别排除。代价：当前 turn 不进记忆（检索只在历史范围）、记忆更新滞后一步。
- **离线重建 / 重放**：不是在线替代品，而是一致性验证手段——冻结查询、双 `PYTHONHASHSEED`、比较 canonical logical state，用于证明增量实现与全量重放等价；本项目以此口径完成验证（数字见机制详解）。

### 2.4 高概率追问与要点

1. **三种检索信号是固定权重融合吗？** 要点：不是。稠密与 BM25 的分数先经排名变换，同侧求和后过 sparsemax 稀疏化，查询与上下文之间的混合权重由延续证据动态推断；图补全在起始线索之后执行，最后还有稀疏化选择与跨通道去重。不要说成"三份列表加权相加"。
2. **为什么不用向量＋BM25＋RRF＋重排这套主流方案？** 要点：承认那是业界最强形态并说清它的分工（bi-encoder 召回、cross-encoder 精排、RRF 融合）；本项目的取舍是线索推断＋图补全服务于"个人交互历史的关联记忆"这一目标，且未做对照实验，不断言更优；候选层加重排原则上可叠加，项目未做。
3. **图里存了什么？比加大 top-k 多找到什么？** 要点：节点为完整 turn、枢纽为学习形成的聚簇、成员与时序两类边；图补全从已命中线索的二阶关联扩展，能带回查询措辞未覆盖的历史；代价是维护与可解释性要求；无消融实验，"多找到"是机制论证不是实测结论。
4. **自动注入和按需补搜有什么区别？** 要点：注入发生在请求渲染时、条数与字符双层预算受控、意图是低摩擦给线索；补搜发生在推理中、查询更具体、可带意图与时间过滤；三层是职责递进，不代表每轮都依次调用三个工具。
5. **有来源就等于回答正确吗？新旧事实冲突怎么办？** 要点：来源只给核验入口，不给正确性；先确认两条记录是否针对同一对象，再比较限定条件与时间，证据不足继续检索或直接问用户——系统不自动判定哪条冲突事实一定正确。
6. **查询和学习为什么要分开？** 要点：只读检索保证可复现（同查询同结果，不受检索次数影响）；学习挂在交互提交之后，经提交闸门与检索互斥；中断占位在样本边界排除。反面即"即时写入"形态的副作用。
7. **那组数字证明了什么？** 要点：全部是隔离迁移 / 重放口径——样本边界、embedding 完整性、双 hash seed 下的逻辑状态一致；它们不是记忆准确率或回答正确率，也不能合并成成绩；LongMemEval / PersonaMem 是后续计划。
8. **召回低于 40 条说明什么？** 要点：单查询显式召回规模的舒适范围，说明注入规模受控、候选有限；不是 token 节省率，也不是检索质量指标。

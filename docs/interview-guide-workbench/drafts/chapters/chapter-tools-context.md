## 一、口述层

> 段首加粗标签与括注字数仅为排练导航，口述时不读。全文第一人称，合计约 1,600 字（含英文词），对应 3～6 分钟。

**【背景与问题】**（约 250 字）

项目初期只有少量本地工具，全部 Schema 随每个请求下发，成本可以忽略。接入 MCP、注册工具增长到几十个之后，出现了两个直接问题：其一，工具定义与对话历史竞争同一个窗口，每轮都要为全部工具的名称、描述和参数结构支付 token；其二，provider 对单请求可携带的工具数有硬性上限，全量注入直接触碰限制。调试中还暴露出一个更隐蔽的缺陷：模型已经"知道"某工具存在并尝试调用，却因其 Schema 没有进入本轮请求而失败——系统把"注册过的工具"和"本轮可调用的工具"当成了同一件事。同期长对话历史也在累积：按固定消息条数裁剪会把一次发起的一批工具调用和对应结果拆开，恢复出的上下文在协议上不合法。

**【我的判断】**（约 280 字）

我的判断是，这两类问题都不该靠继续扩大上下文窗口解决，而是缺少一个显式的投影层：把能力的总量和单轮可见的范围分开管理。工具侧，注册表保持完整，每轮只携带一个受容量约束的可见集合；未进入集合的工具放进可搜索的目录，模型按需检索、当轮解锁后进入后续请求。解锁只解决可见性：真正执行还要单独过权限和状态检查——注册、可见、执行是三个独立的状态。历史侧是同一个原则：压缩的是给模型看的视图，不是事实来源，并且必须以完整的交互单元为边界。代价是多一次发现交互、跨请求的投影状态管理和摘要调用的失真风险。这个交换在工具规模大、单个任务只用其中一小部分的场景下成立；工具少而稳定的项目，全量注入仍是更简单的正确选择。

**【具体行动】**（约 470 字）

工具侧，我把本地和 MCP 工具统一注册，在注册集合之上维护未加载工具目录。初始请求只带三类工具：常驻工具（含 `tool_search`——按名称或关键词在目录中定位工具的元搜索工具，它自身必须常驻，否则发现入口不可达）；任务显式要求预加载的工具；会话内近期用过且允许预加载的工具。再按 `max_tool_schemas`——provider 对单个请求可携带工具数的硬上限——裁出可见投影。模型需要新能力时调用搜索：结果绑定注册表中的真实身份并登记进当前尝试；下一次请求重建投影，新解锁工具优先占用被淘汰工具的槽位。单次解锁以上限减一为界，给搜索工具本身留位；装不下的命中明确标为容量受限，而不是假装可用。

历史侧，请求按稳定指令、已提交历史或已有摘要、当前任务锚点、动态记忆、可见工具定义的顺序组装；动态记忆放在稳定历史之后，避免每轮变化的记忆内容把更长的稳定前缀打散。水位估算覆盖消息加工具定义的完整请求，超过历史实现采用的 0.74 倍窗口水位时，从较旧部分选出完整的 `CommittedContextUnit`——覆盖一次用户消息及其引发的整批工具调用与全部结果、压缩不可再分的最小交互单位——生成或更新摘要，按同套历史参数保留最近约 20,000 token 后重组校验；摘要记录代际与来源引用，原始历史仍在会话存储可回查。同时，每次模型调用的输入 token 和缓存命中都会被记录，用于开销分析。

**【结果与复盘】**（约 260 字）

这里没有端到端节省数字可引用，能讲清的是验证方式和边界。搜索解锁的修复附了一组回归测试：把 provider 上限设为 2，注册超过上限的工具，让一次搜索同时选中两个。断言落在下一轮真实请求携带的 Schema、目标工具恰好执行一次、超额工具被标容量受限且从未执行。这验证的是投影与执行边界的正确性，不能外推成任务成功率或 token 节省率。压缩侧同理：批次闭合后才允许提交，压缩切点不会停在调用和结果中间。0.74 和 20,000 都是历史实现采用的工程参数，为当前请求与 provider 开销留空间，不是对所有模型的最优值。输入 token 和缓存命中的记录已经在采集，口径是 token 加权；但命中率是否因分层调整而提升需要前后对照实验，记录本身不构成效果证明。

**【设计取舍、踩过的坑、怎么修的】**（约 340 字）

最有讲述价值的坑是"搜索解锁了，Schema 却没进请求"。现象：模型调用工具搜索，返回文本明确写着已解锁某工具，下一步调用却被判定 Schema 不可见。我最初的误判是怀疑模型没理解搜索结果；核对请求 payload 才发现，下一轮工具数并未超限，新工具却没有出现——投影重建时仍在优先保留旧的常驻和预加载工具，新工具被淘汰出了投影。根因是三件事没有闭环：搜索文本、解锁登记、下一轮实际携带的定义，三者各自维护、互不同步；背后是一个错误假设——结果里写出名字，下一轮就一定有 Schema。修复是让搜索命中绑定真实身份、解锁登记进当前尝试、投影重建时为新解锁工具显式释放槽位、超额命中标为容量受限。验证必须落到下一轮真实请求的内容与执行次数上——只断言搜索文本包含工具名，这个缺陷测不出来。另一个坑：动态记忆一度排在稳定历史之前，每轮变化的记忆内容截断了稳定前缀；修复只是调整分层顺序，把动态内容后置。

## 二、支撑层

### 2.1 关键机制详解

#### 三个状态集合：registered / visible / executable

- **registered（已注册集合）**：宿主已加载、能按真实身份找到定义与执行入口的工具。本地工具与 MCP 工具注册进同一个 `ToolRegistry`（统一工具注册表：同时维护工具实体、注册元数据和可搜索的目录文档），注册即获得与来源无关的统一身份。
- **visible（可见集合）**：当前 provider 请求实际携带 Schema、模型能够按名字选择调用的工具。
- **executable（可执行集合）**：在当前任务、权限与运行状态下真正允许产生效果的工具。
- 三者只正向递进、不反向豁免：搜索解锁改变的是可见性，不代替执行准入；反之，工具恰好在请求中可见，也不自动获得执行资格。

#### 未加载目录与初始投影

- `get_deferred_names`（构造未加载目录的方法：全量注册集合减去元工具与当前可见集合，按内置 / MCP 来源分组返回）。被 provider 上限挤出的常驻工具也保留在目录里，模型可以通过搜索重新加载，不会因为一次裁剪而永久丢失。
- `_initial_visible_tools`（构造每轮初始可见集合的函数）：常驻工具是运行时合同，显式预加载与近期预加载工具按序补位；总量超过 provider 上限时按顺序裁剪——常驻工具自身在上限过小的极端配置下也可能被裁掉，此时由目录兜底。
- `tool_search_enabled`（搜索功能开关）：关闭时全量暴露所有工具；此时若 Schema 总量超过上限，运行时直接报配置错误并提示开启搜索，不做静默裁剪。

#### 搜索、当轮解锁与容量闭环

- `ToolSearchTool`（目录搜索工具的实现）：支持 `select:工具名`（精确加载语法，支持逗号分隔一次选择多个）与关键词查询两种方式；搜索基于目录元数据打分，不是 embedding 语义检索。
- 搜索结果的三个字段分工：`matched`（仅供模型阅读的命中信息）、`unlocked`（运行时确认解锁的工具名，系统状态的唯一依据）、`capacity_limited`（因容量未进入本轮解锁的命中，对模型的明确提示是"尚未加载、不可直接调用"）。
- `grant_current_turn_search`（把真实解锁结果登记进当前尝试授权域的方法）：授权域由 `begin_turn_search_scope`（为一次 attempt 建立独立搜索授权域的方法）按 turn 与 attempt 划分，尝试结束即失效——解锁不永久修改全局权限。
- `max_unlocked`（单次搜索最多解锁的工具数）：由 provider 上限减一得出，给 `tool_search` 本身保留一个槽位；超出部分进入 `capacity_limited`。
- `requires_turn_search`（要求每个新 turn 重新搜索才能执行的注册标记）：带此标记的工具即使出现在历史摘要或预加载集合里，未经当轮搜索授权也不能执行，直接执行会被拒绝。
- 回归锚点（provider 上限为 2 的场景）：注册 `tool_search`（常驻）与多个常驻、需搜索的工具，模型用一次 `select:` 同时选中两个。断言结果：三次请求携带的 Schema 依次为「搜索 + 常驻工具」「搜索 + 选中工具」（连续两轮）；选中工具恰好执行一次；超额工具零执行并出现在容量受限集合；对它绕过搜索直接执行会因缺少当轮授权报错。

#### 会话级预加载（LRU）

- `ToolDiscoveryState`（会话级工具发现状态）：按会话以 LRU 顺序维护近期解锁的工具，历史实现每会话容量为 5、全局最多跟踪 1,024 个会话；更新时跳过常驻工具、`tool_search` 与标记 `preloadable=False`（不可自动预加载的注册标记）的工具。
- LRU 解决的是高频工具重复搜索的摩擦，不是授权：它只影响初始投影的候选顺序，不改变任何执行准入判断。

#### 请求分层与水位估算

- 组装顺序：稳定指令 → 已提交历史或已有摘要 → 当前请求锚点 → 动态记忆及其他运行材料 → 当前可见工具 Schema。动态记忆后置的原因：每轮变化的记忆内容若出现在稳定历史之前，会截断更长的稳定前缀，损害 provider 前缀缓存的复用（机制见通用概念对照的 Prompt caching 条目）。
- `estimate_context_tokens(messages, tools)`（provider 侧完整请求 token 估算接口）：水位估算同时计入消息与工具 Schema，不只统计文本历史；provider 返回精确用量后，同一 Schema 集合的后续轮次可用精确基数加新增内容估算。
- `SOFT_LIMIT_RATIO = 0.74`（软触发水位比例常量）与 `KEEP_RECENT_TOKENS = 20_000`（压缩后近期保留 token 数常量）：历史实现采用的工程参数，为当前请求、工具结果与 provider 包装开销留出空间，不是对所有模型的最优值。

#### 完整交互单元与摘要投影

- `CommittedContextUnit`（压缩最小完整交互单位的类型别名，底层即会话历史单元）：覆盖用户消息、assistant 发起的整批工具调用与全部对应结果；批次闭合前不可提交，压缩切点永远不会停在调用与结果的中间；仍在运行的 shell 会进一步限制切点不能越过其起始单元。
- 摘要元数据三件套：generation（当前摘要版本）、parent generation（它从哪个上一版本演进而来）、source ref（覆盖的原始范围引用）。摘要是可追溯的投影而非新的事实源；原始消息与执行记录仍由会话存储保留，可按引用回查。
- 摘要调用自身的约束：请求不带工具、关闭推理，摘要输入也受窗口约束——系统用 `SUMMARY_HEADINGS`（摘要必须严格匹配的固定 Markdown 标题结构，共九个标题，覆盖目标、约束、进度、关键决策与关键上下文）校验输出；输入超窗时在完整单元边界内二分收缩，宁可少摘要几个单元也不拆开单个单元；后续摘要以已有摘要为更新基底，不从全历史重新生成。

#### 容量错误的有限重试

- `ContextLengthError`（provider 明确报告的容量超限错误类型）：触发一次 `force=True`、`trigger="context_overflow"`（强制压缩与触发原因标记）的再压缩后重建请求重试，重试是同一次调用的第二个尝试；再失败则原样上抛。认证、限流、无效参数等服务错误不进入这条路径——它们不是容量问题，重复压缩只会放大延迟和成本。
- 未开启压缩能力时（默认门），容量错误不做重试直接暴露，由调用方处理。

#### 用量记录与缓存观测

- `ModelUsage`（把各模型驱动的用量字段归一化的记录结构）：包含输入、输出、`cached_input_tokens`（缓存命中的输入 token 数）等字段；每次调用的记录与闭合的执行单元关联，构成"记录输入 token 与缓存命中率用于开销分析"的数据来源。
- 缓存命中率口径是 token 加权（命中输入 token 总和除以输入 token 总和），不是逐次比例的平均。
- 配套的 observe 观测插件（见通用概念对照的链接）提供缓存效率视图与逐 Turn 明细；它与基线的版本兼容边界记录在事实包，不作为基线能力的证明。

#### 目录搜索的延迟量级

- `_score`（对工具文档按关键词集合打分的函数）与 `_explain`（生成命中解释列表的函数）：在 2,000 份目录文档、4 个关键词的局部工作负载中，`_score` 中位数约 5.00 降到 4.90 毫秒（约 −2%），`_explain` 中位数约 3.55 降到 2.67 微秒（约 −24.75%）；完整 search 流程的微基准受调度噪声影响，没有稳定收益。这组数字只说明目录搜索在当前规模不构成延迟瓶颈的量级，不是端到端优化效果。

| 支持工具扩展与长对话执行 | 目录解耦"能力总量"与"单轮可见性"，新工具注册即入目录、无需改请求编排；压缩替换模型视图而非事实来源，长对话可回查、可恢复 |
| 记录输入 token、缓存命中率用于开销分析 | `ModelUsage` 归一化各驱动用量字段（含 `cached_input_tokens`），与闭合执行单元关联；命中率按 token 加权口径聚合；observe 插件提供看板（版本边界见事实包） |

### 2.3 与主流替代方案对比

**工具暴露：全量注入 / 任务级子集 / 平台侧工具搜索 / 目录 + 当轮解锁（本项目）**

- 全量注入是多数客户端的默认做法：MCP 的 `tools/list` 返回什么就全量下发，模型一开始就拥有完整选择空间，零发现摩擦、零跨请求状态，实现最简。对方更优的场景：工具数量少（个位数到十余个）、定义短且稳定、几乎每轮任务都会用到大部分工具——此时目录、搜索和投影状态管理纯属额外复杂度。
- 任务级工具子集：编排层为每个任务或子代理显式绑定一个小工具集，是多智能体框架的常见做法。同样零发现轮次、行为静态可控；代价是子集划分靠人工维护，任务边界漂移时要么缺工具、要么越给越多，而且不解决 provider 上限本身。
- 平台侧工具搜索：Anthropic 的 API 与 Claude Code 已把"工具定义不进请求、由模型按需检索加载"做成官方能力，官方文档的定位就是支持成百上千个工具的按需发现。这说明该问题已被业界确认并产品化；差别在于平台方案主要解决"模型找得到"，本项目的当轮授权、容量裁剪与执行准入边界留在自己的执行层，是宿主自研的完整闭环。
- 本项目（目录 + 当轮解锁）更优的场景：工具增长到几十个、来源异构、单个任务只用其中小子集，provider 有硬性数量上限，且需要自己掌握授权与准入边界时。代价是一次发现交互的额外轮次、目录维护，以及搜索结果必须与真实工具身份可靠绑定的状态闭环要求。MCP 本身解决的是"宿主如何知道 server 有哪些工具"的发现问题，不解决"单轮请求如何裁剪"的暴露问题，两者在本项目中是上下游关系。

**工具检索：关键词目录搜索（本项目）/ 向量语义检索 / 混合检索 + 重排**

- 向量语义检索：把工具描述向量化，按查询语义相似度检索（工具检索方向的研究与评测如 ToolRet），适合工具数达数百上千、查询是自然语言描述、工具名与描述语义差距大的场景。
- 混合检索 + 重排：词法与向量双路召回，再用 cross-encoder 或 LLM 对候选联合评分重排——这也是 RAG 领域的主流配置。召回上限最高、对命名混乱最鲁棒；代价是 embedding 索引、重排延迟与维护都最重，在几十个工具的目录规模上发挥不出来。
- 本项目选择关键词 + `select:` 精确选择的理由：几十个工具的规模下打分路径已经足够快（见机制详解的微基准条目），避免了 embedding 索引的基建与维护；工具目录文档本身很短，语义检索的召回优势发挥不出来。
- 代价与边界：查询措辞与目录元数据措辞不一致时命中质量下降，模型需要靠 `select:` 精确兜底；工具规模再上量级时应优先考虑升级到混合检索 + 重排，而不是替换单路。

**对话压缩：六种主流形态（本项目＝模型摘要 + 近期保留 + 可回查投影）**

按"旧内容去哪了"排成一条谱系，各形态在触发条件、信息保留、失真风险与调用成本上各有取舍：

- **截断 / 滑动窗口**（丢弃最旧消息、保留最近 N 条或 N token，多数框架的第一道防御）：零额外调用、近期内容零失真、实现最简；窗口外信息彻底不可见。对方更优的场景：单轮任务为主的短对话，早期内容本来就不值得保留。
- **就地清理工具结果**（不删消息，把历史中超长的工具输出清空或替换为占位摘要；Anthropic 的 context editing 与各家编程 Agent CLI 的输出截断属于这一形态）：直接攻击上下文的大头——工具结果通常远大于对话文本，且保留消息协议结构。代价：被清掉的细节不可恢复，也不减少消息条数。与本项目正交，可以叠加。
- **滚动摘要**（超阈值后把旧消息压成一段摘要并滚动更新；Claude Code 的 /compact 与自动压缩、LangChain 的摘要缓冲记忆是代表）：旧信息以压缩形式在场，实现比"摘要 + 近期保留"更简单。代价：失真随滚动更新累积，长任务里的精确参数与约束最容易被磨掉——Claude Code 的官方说明也提示压缩可能丢失细节。
- **模型摘要 + 近期保留（本项目）**：较旧完整交互单元生成 / 更新摘要、近期内容保留原始形态、原始记录全程可回查。与滚动摘要的差别是近期窗口保真、摘要只是投影；与截断类形态的差别是早期约束仍以摘要形式在场。更优场景：跨多次会话的长任务，且需要事后按引用回查原文。
- **卸载到外置记忆、按需取回**（旧内容不进摘要而是搬进可检索存储、模型用工具取回；MemGPT/Letta 的主上下文 + 外置上下文架构与各家产品化记忆属于这一形态）：上下文最小、信息保留上限最高。代价："取回"变成新的检索问题——漏检时模型不知道自己不知道，工程量也最大。本项目的长期记忆检索（见记忆章）正是这一形态的检索侧，与压缩互补而非互斥。
- **不压缩：长窗口 + 前缀缓存**（靠窗口变大和缓存降价硬扛）：对当前模型最省工程。代价：窗口内注意力随长度退化、按 token 计价的输入成本仍在，超窗即失败且没有回退路径。
- 本项目的净代价与边界：每次压缩多一次摘要调用（输入受窗口约束、需二分收缩）、摘要可能遗漏或经多次更新累积失真、需要维护摘要代际。协议完整（批次闭合）只保证请求序列合法，不保证摘要语义无损——这两件事面试时必须分开讲。

**前缀缓存策略：不做分层 / 稳定前缀分层（本项目）/ 显式断点标记 / 自动前缀缓存**

- 不做分层：请求每次按当轮需要自由组装，表达最灵活；代价是请求前缀几乎每轮都变，provider 的前缀缓存无从命中，全部输入按未缓存计价。对方更优的场景：请求天然没有稳定前缀（例如每次都是全新上下文的独立任务），分层只会增加约束没有收益。
- 稳定前缀分层（本项目）：稳定指令与已提交历史放在前部、动态记忆与工具 Schema 后置，最大化不变前缀的长度。代价：注入位置的表达自由受分层顺序约束（动态材料只能后置）。
- 显式断点标记（Anthropic prompt caching 的 cache_control 一类：在请求内显式声明缓存断点、可设多个，放在易变内容之前分段保住多段前缀）：控制粒度比分层更细，能保护请求中段的稳定块；代价是断点策略要维护，且有缓存写入计费与 TTL 失效问题。
- 自动前缀缓存（OpenAI API 与 vLLM 等推理栈的前缀缓存：无需任何标记，前缀一致即命中降价）：零改造成本；但命中前提仍是前缀字节级一致——应用层不做分层时，命中率取决于请求组装方式的偶然性。
- 三者关系：本项目的分层与 provider 侧两种机制正交——分层保证"前缀真的稳定"，provider 的缓存机制（自动或显式断点）让"稳定的前缀真的便宜"。缓存是否命中、命中多少取决于 provider 实现与请求格式；本项目记录命中率用于分析，不声称分层已带来命中率提升（需要前后对照实验）。

### 2.4 高概率追问与要点

1. **为什么不把所有工具 Schema 都放进请求？** 要点：三个约束——上下文机会成本、provider 数量上限、大量相似工具增加选择噪声；再讲全量 vs 目录的适用边界（工具少且稳定 → 全量更简单），避免把按需暴露说成无条件更优。
2. **registered / visible / executable 有什么区别？** 要点：各自一句话定义（已加载可寻址 / 本轮请求携带 Schema / 通过权限与状态检查），再给两个推论：搜到不等于可见（坑案例），可见不等于放行（执行准入独立）。
3. **搜索结果已经告诉模型工具名了，为什么还调用失败？** 要点：自由文本 ≠ 结构化 Schema；模型可靠产生调用需要真实名称、参数结构与必填字段进入下一次请求 payload；这正是那个坑的根因。
4. **当轮解锁会不会永久改变权限？** 要点：不会——授权域按 turn + attempt 划分，尝试结束即失效；LRU 预加载也只是初始投影候选，不是授权；`preloadable=False` 与 `requires_turn_search` 是两类独立约束。
5. **为什么不能按固定消息条数裁剪历史？** 要点：条数不反映 token 大小（工具结果可能极大）；更关键的是协议边界——一次发起的多个 tool call 与全部 result 闭合才是完整单元，从中间切开破坏 provider 协议与恢复语义。
6. **有了摘要为什么还要保留原始历史？** 要点：摘要是面向模型的投影，可能遗漏精确参数与事实关系；generation / parent generation / source ref 支持版本追溯与回查；把摘要当唯一事实源会把压缩错误变成不可逆丢失。
7. **0.74 和 20,000 怎么定的？适用于所有模型吗？** 要点：历史实现采用的工程参数，水位估算的是完整 payload（含工具 Schema）；实际值应按 provider 窗口、工具序列化方式与任务分布校准；不主动说"最优"。
8. **缓存命中率怎么算的？提升了多少？** 要点：token 加权口径（命中输入 token 总和 / 输入 token 总和），不是逐次比例平均；分层调整的收益需要前后对照实验——目前有记录与看板，没有提升数字，不要现编。
9. **这套设计到底省了多少 token？** 要点：没有端到端节省数字；能给出的是机制边界（回归断言、批次闭合、容量重试上限）与已采集的用量数据；补消融实验的方向：同一任务集上比较全量 Schema 与按需暴露、有无压缩、不同分层顺序。
10. **业界已经有官方的工具搜索与上下文压缩（Anthropic 的 tool search、compaction、context editing），自研的意义是什么？** 要点：先承认平台化本身佐证了这个问题的真实性；再讲差别——平台能力解决"模型找得到、窗口装得下"，而三集合边界（当轮授权、容量裁剪、执行准入）、摘要代际与来源回查、跨 provider 一致的行为与参数仍要宿主执行层自己管，自研换来不绑定单一厂商 beta 能力与缓存语义的自由，外加自己的用量账本；最后给边界——只在单一 provider 上运行且平台能力够用时，直接用官方能力更省工程，自研的前提是宿主要完整掌握执行与观测闭环。

# 总述章：项目定位与统一 ReAct 地基

## 一、2～3 分钟项目介绍口述骨架

我做的项目是 akashic-agent，一个面向个人助手场景的开源 Agent。它围绕长期个性化交互，把历史事实、外部工具、主动行为和真实任务验证接进同一套执行系统。这里的重点不是增加一个聊天入口，而是把一次 Agent 执行中容易失控的几条边界明确下来：历史信息存在但不一定找得到，找到的摘要也不一定能核实；工具数量增长后，全部定义会和对话历史竞争上下文；系统在用户没有提问时开口，相关性不能直接等于打扰依据；模型说完成了，也不代表真实环境已经达到任务要求。

围绕这些问题，我做了四条能力。第一是长期记忆与证据检索：我接入并改造 Akasha，结合稠密向量、BM25 和图关联补全寻找历史线索，再用自动注入、按需补搜和原文取证逐步提高核验强度，避免把摘要直接当成事实。第二是 Agent 端到端评测：我接入 Terminal-Bench 2.1，在逐题隔离的容器中运行真实 Agent，用官方 Verifier 检查环境最终状态，并保留轨迹、支持断点续跑和失败归因；固定 89 题最终通过 59 题，通过率是 66.3%。第三是工具发现与上下文管理：我把本地工具和 MCP 工具统一注册，通过目录检索、当轮解锁和常用工具预加载按需暴露 Schema，同时按窗口水位压缩历史，保留完整交互单元和可回查的原始记录。第四是主动交互策略：我把推送决策拆成兴趣初筛、证据核验和显式发送或跳过，用事件版本去重、兴趣衰减和唤醒阈值控制是否触发，并把投递不确定性单独处理。

这四条能力共用的不是一套提示词，而是统一 ReAct 执行内核。一次执行可以从用户输入或主动事件开始：系统先读取会话约束，组织稳定指令、历史或摘要、动态记忆和当前可见的工具 Schema；模型提出回答或工具行动，宿主检查工具是否可见、是否有权限，再执行并把结果回填给下一轮判断，直到形成普通回答、主动发送或跳过等终态。记忆负责提供历史线索，工具与上下文层负责控制模型本轮能看到和调用什么，主动交互复用判断与工具执行但增加独立的候选准入、调查预算和发送授权，评测则把同一类真实执行放进隔离环境，由外部 Verifier 判断任务是否真的完成。这里的 ReAct 是四项能力共同复用的执行地基，不是第五项单独成绩；四个能力仍有不同的状态边界、工具集合、终态约束和验证标准。

## 二、统一执行链黄金样例

### 1. 用户询问历史事实

用户问：“我之前确定的配置是什么？”系统先读取当前会话约束，并把用户消息、受控的历史线索和本轮可见工具 Schema 组织成请求。模型判断已有线索是否足够；如果不足，就提出记忆补搜，宿主检查该工具的可见性和执行权限后运行，结果回填到下一轮判断。模型需要核对具体原话时，再提出原文取证，宿主返回带真实来源的消息内容。最后模型生成回答，并列出实际使用的历史引用。这个例子里，记忆能力负责找到线索和来源，ReAct 负责安排补搜与取证的顺序，上下文层控制每轮携带的材料和工具；摘要或召回预览都不能越过来源边界直接成为最终证据。

### 2. 系统主动发现事件

系统收到一个新的外部事件时，先用事件身份判断它是新版本还是重复到达，再结合兴趣分衰减和唤醒阈值判断是否值得启动模型。满足准入后，系统冻结候选批次，进入受限的 ReAct 回合。模型先做兴趣初筛，只保留需要进一步确认的候选；调查回合再按预算调用记忆回查或其他工具核验证据。证据不足或不适合打扰时，模型提交跳过终态；证据充分时，也必须提交带真实事件引用的发送终态，宿主校验通过后才进入投递结算。这个例子里，ReAct 复用了判断、工具执行和观察回填，但主动能力额外控制候选身份、调查预算、发送授权和投递不确定状态，普通生成正文不能直接触发外部发送。

## 三、四条能力与统一 ReAct 地基的关系

### 1. 长期记忆与证据检索

它复用 ReAct 的模型判断、工具调用和结果回填，但把历史记忆接在执行前和执行中两个位置。请求开始时自动注入受控的历史线索，证据不足时由 Agent 按需补搜，需要核对原话时再调用原文取证。它新增的边界是检索只读，学习在交互提交后发生，召回摘要和预览不能直接代替来源证据，系统也不自动替用户判定新旧冲突事实哪条一定正确。想深挖三路检索、来源闭环和查询学习分离，阅读《长期记忆与证据检索》章。

### 2. Agent 端到端评测

它复用同一条 Agent loop，让被测 Agent 通过真实工具在环境中完成任务，再把工具执行结果和最终状态交给评测链路。它新增的边界不是新的推理能力，而是逐题容器隔离、候选状态冻结、官方 Verifier 判定、轨迹留存和分层失败归因。Provider 没有形成有效回合，或 Verifier 基础设施失败，都不能直接算 Agent 做错；只有前置证据有效后的 Verifier 零分才进入有效 Agent 失败。想深挖评测闭环、断点续跑和 59/89 的统计口径，阅读《Agent 端到端评测》章。

### 3. 工具发现与上下文管理

它复用 ReAct 的工具执行循环，但在模型每次请求前增加一层可见性投影。工具可以已经注册，却不一定进入本轮 Schema；模型按需搜索并当轮解锁，宿主仍然独立检查权限和运行状态。历史同样不是简单删掉旧消息，而是把稳定指令、历史摘要、动态记忆和工具定义分层组织，在窗口接近上限时按完整交互单元压缩，原始事实保留在会话存储中。它新增的是注册、可见、可执行三种状态和上下文容量边界。想深挖工具搜索、Schema 解锁、完整交互单元和压缩策略，阅读《工具发现与上下文管理》章。

### 4. 主动交互策略

它复用 ReAct 的判断、工具执行和观察回填，但不复用普通回答的发送权限。程序先根据事件身份、兴趣衰减和唤醒条件决定是否值得花模型成本；模型再在受限回合中做兴趣初筛和证据调查，最后只能通过结构化发送或跳过终态改变主动任务状态。它新增的边界是候选批次、事件版本、调查预算、终态引用和投递结算。普通正文不等于发送授权，投递回执不确定时也不能盲目重发。想深挖两阶段决策、事件去重、发送授权和 durable delivery，阅读《主动交互策略》章。

## 四、总览级高概率追问与要点

### 1. 为什么自己搭统一执行内核，而不是直接使用现成 Agent 框架？

- 现成框架可以提供基础的模型调用和工具循环，但项目要统一处理记忆来源、工具可见性、上下文压缩、主动发送授权和端到端评测证据。
- 自建的收益是把模型建议、宿主执行、状态变化和结果观测放在同一条可检查的边界内，并能跨不同场景复用执行骨架。
- 代价是状态机、恢复、兼容性和测试成本由自己承担。工具少、没有主动副作用或只依赖单一平台能力时，直接使用成熟框架更省工程。

### 2. 四条能力中哪个最难，为什么？

- 如果按系统性风险看，最难的是把统一执行骨架接到不同的权限和终态边界上，尤其是主动交互和评测场景。
- 主动交互的难点是兴趣、证据、重复、授权和投递不确定性不能混成一次模型生成；端到端评测的难点是必须证明失败属于哪一层。
- 记忆和工具上下文也不是独立插件，它们都要求模型视图与真实事实分离，并保证来源、协议和状态可恢复。因此难点不是某一个算法，而是跨模块边界能否保持清楚。

### 3. ReAct 和四条能力是什么关系？为什么不把它算第五项能力？

- ReAct 在这里指共享的执行骨架：模型提出行动，宿主执行工具，观察结果回到下一轮判断，直到终态。
- 四条能力分别解决历史证据、上下文容量、主动授权和真实验证问题，复用这条骨架但增加不同的工具集合、准入规则、状态和终态。
- 因此 ReAct 解释了项目如何统一运行，不单独贡献一项与简历并列的业务能力；把它单列会掩盖四条能力各自的工程边界。

### 4. 这四条能力真的属于同一个项目吗？它们之间如何形成闭环？

- 共同入口是一次受控 Agent 执行：历史记忆提供线索，上下文层决定本轮携带的材料和工具，ReAct 内核完成判断与执行，主动场景按授权处理外部发送。
- 评测不是每次用户交互后必然执行的步骤，而是独立的真实任务验证场景。它复用同一执行能力，用隔离环境和官方 Verifier 检查 Agent 的实际完成情况。
- 运行轨迹、工具结果、状态和终态形成可观察边界，既支持恢复，也支持判断问题发生在 Agent、Provider 还是验证基础设施。

### 5. 项目最重要的工程取舍是什么？

- 核心取舍是把模型视图、程序状态和外部效果分开：历史可以被压缩但原始记录保留，工具可以被搜索但搜索不等于执行许可，模型可以建议发送但普通正文没有发送权限。
- 这样做增加了投影、授权、状态机和恢复逻辑，也会带来额外调用和延迟。
- 换来的不是未经验证的效果承诺，而是更清楚的协议边界、可回查证据和可归因的失败。具体收益与代价需要按记忆、工具上下文、评测和主动交互四章分别看。

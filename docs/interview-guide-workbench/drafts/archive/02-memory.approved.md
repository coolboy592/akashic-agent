# Akashic Agent 面试指导书：阶段 2

## 1. 30 秒入口

- 长期助手不能只依赖最近窗口，因为关键事实可能跨越多个会话，而摘要也可能遗漏原话、时间和限定条件。
- 我用稠密召回发现语义相关内容，用 BM25 补充专有名词和精确表达，再用图关联补全相关历史。
- 通过“自动注入—按需补搜—原文取证”，让 Agent 先低成本获得线索，证据不足时继续检索，并回到来源核实。

## 2. 2～3 分钟回答骨架

- **背景与卡点**：长期记忆不是把更多文本塞进上下文，而是让 Agent 找到跨会话事实并知道来源。最近窗口简单，但覆盖有限；摘要节省上下文，却可能丢失原话、时间和条件。

- **单一路径为什么不够**：向量相似度能覆盖语义相近的内容，但对专有名词、精确表达和隐含关联不一定充分。召回摘要也不等于已经确认原始消息，更不等于证据进入了回答。

- **三类信号如何协作**：稠密召回扩大语义覆盖，BM25 补足精确词法并参与线索判断，图关联补全则从命中线索扩展相关历史。它们不是三份结果做固定权重相加，而是共同组织有限证据。

- **三层证据链**：普通请求先自动注入少量历史；材料不足时，Agent 再主动组织更具体的查询补搜；需要核对原话、时间或条件时，根据来源回到原文。三层代表职责递进，不是固定的工具调用顺序。

- **我的核心判断**：我把查询和学习分开，查询只读现有记忆；完整且适合学习的交互在提交后才进入学习，避免多次搜索改变记忆关系，也避免未完成交互污染长期记忆。

- **结果与限制**：我还通过隔离重放检查了学习样本处理和逻辑结果的一致性；这类验证说明实现能够稳定重放，但最终回答效果仍需要分别评测检索命中、证据进入和答案正确。

## 3. 从历史线索到当前证据

“找到相关内容”只是检索命中，不能直接等同于当前回答拿到了证据。候选可能只是摘要或预览，来源也可能没有完整传递；即使进入检索结果，还要确认它是否真正进入模型上下文，以及原文是否支持要表达的结论。

```text
当前请求
    ↓
自动注入少量历史线索
    ↓
Agent 判断证据是否充分
    ├─ 充分 ───────────────┐
    │                      ↓
    └─ 不足 → 按需补搜 → 根据来源回到原文
                           ↓
                   形成有依据的回答
```

- **当前请求**：宿主 Agent 将用户当前问题和必要的会话范围组织成查询。Akasha 只在历史范围内检索，不把当前尚未完成的回答误当成已学习事实。

- **自动注入**：在模型开始处理任务前，系统提供受控数量的历史候选。它承担“低摩擦提供线索”的职责，不追求把所有历史都塞进上下文，也不保证第一次召回已经充分。

- **证据充分性判断**：Agent 根据问题需要判断当前摘要或候选是否足以回答。简单问题可能到此为止；涉及具体时间、原话、金额、配置或新旧事实时，通常需要更强证据。

- **按需补搜**：证据不足时，Agent 用更具体的查询继续寻找，例如补充专有名词、时间范围或事件条件。它是主动取证能力，不是自动注入的重复实现。

- **根据来源回到原文**：召回记录保留真实来源身份，系统可以读取对应的原始消息和必要上下文，核对摘要中可能被截断的内容。原文取证也可以发生在自动注入之后或显式补搜之后，取决于当前证据缺口。

- **形成有依据的回答**：最终回答区分“召回命中”“证据进入上下文”和“回答是否正确”。如果回答使用了具体记忆，应以实际读取到的原文为依据，而不是根据摘要预览补写细节。

## 4. Akasha 为什么不只是向量检索

我没有把长期记忆设计成一个普通向量数据库的 top-k 查询，因为不同证据类型解决的是不同问题。

稠密向量召回适合发现语义相近但措辞不同的历史。例如用户今天换了一种说法，仍然可能命中几个月前讨论过的同一件事。它提供较好的语义覆盖，但对精确名称、特殊关键词和限定表达不一定敏感。

BM25 补的是词法证据。专有名词、文件名、命令、配置项、错误信息这类内容，精确词面本身就很重要。BM25 不只是额外返回一份搜索列表，它还参与判断起始线索和证据特征，帮助系统识别“语义相近”是否同时有明确词法支撑。

图关联补全解决的是当前措辞无法直接覆盖的历史关系。系统从已经命中的线索出发，沿已学习的关联扩展相关历史，例如同一主题下的前后事件、共同出现的事实或被多次共同激活的内容。它返回的是历史中的相关节点，不是凭空生成记忆，也不是简单地对向量前几名逐个找邻居。

因此，三类信号不是平铺后的固定权重线性融合。系统先结合当前查询的稠密和词法证据形成起始线索，再在记忆图上做关联补全，最后通过稀疏化选择组织有限的证据集合，也就是抑制较弱的候选，只保留一组有限且更有支撑的材料，同时保留每条记录的来源和召回路径。这样做的收益是证据覆盖更完整，代价是查询行为更复杂，调试时必须解释候选为什么出现。

Akasha 引擎负责学习历史、维护关联关系、读取多类信号并产生带来源的候选；宿主 Agent 负责组织当前查询、限制自动注入规模、注册显式补搜和原文回查工具，并决定什么时候证据不足。我的工作重点是把引擎能力接入 Agent 的运行时闭环，而不是让引擎直接替代 Agent 的判断。

查询与学习必须分开。查询阶段只读当前记忆并生成候选；完整且适合学习的交互在提交后，学习流程才处理对应的问答样本。显式 recall 不会因为被调用而改变记忆图，否则模型多搜几次就可能改变后续结果，召回和故障都难以复现。

## 5. 三个关键取舍

**最近窗口与长期记忆**：最近窗口顺序自然、实现和解释都简单，但只能覆盖近期内容。引入长期记忆后，Agent 能跨会话找回历史事实，却要承担召回噪声、索引维护、来源保存和事实时效管理。我选择保留最近上下文作为低成本基础，再用长期记忆补足跨度，而不是让长期索引替代所有上下文。

**单路向量与多证据图补全**：单路向量检索容易实现，作为第一版也足够覆盖很多语义相似问题，但它对精确词法和隐含关联不充分。我加入 BM25 和图关联，让精确名称、关键词以及历史关系都有对应证据来源。代价是查询链路和调试复杂度增加，所以最终输出仍通过稀疏选择和去重控制规模，而不是无上限叠加结果。

**全自动注入与分阶段取证**：全量或全自动注入看起来省事，但会增加上下文噪声和 token 占用，也容易让模型把未经核实的摘要当成事实。我选择先自动提供少量线索，复杂问题再由 Agent 主动补搜并回原文。这样常见请求走低成本路径，严格取证的问题才增加成本，代价是 Agent 必须具备判断“当前证据是否足够”的能力。

## 6. 代表性踩坑：中断的交互被当成完整问答

一次具有代表性的工程问题是，学习流程按照相邻的 user/assistant 消息配对时，会把内容正好是精确 `[interrupted]` 的助手占位也当成一次正常回答。表面上看，这些消息已经写入存储，前后也能够组成一个相邻 pair，因此原来的判断把“消息在存储中相邻”当成了“这轮业务已经正常完成”。

但中断占位只说明这次交互的执行没有正常结束，它不是用户真正获得的回答，不应该成为长期记忆中的问答内容。如果把这样的未完成交互继续写入记忆，系统就可能让对应的 hub 和关系学习到并不存在的完整问答，后续召回也可能基于错误样本组织历史。

修复方式是在学习前识别精确的 `[interrupted]` 占位，并将这类 pair 从正常学习样本中排除；只有完整且适合学习的交互，才进入后续的 embedding、记忆学习和关系处理。验证时，在 4,800 个相邻 user/assistant pair 中识别并排除了 6 个中断占位，最终得到 4,794 个有效学习样本。这说明中断交互和正常问答已经在学习边界上被区分开。

## 7. 结果、取舍与不足

在学习样本验证中，中断占位已经被识别并排除，未完成交互不会直接作为正常问答进入长期记忆。这与前面的样本边界修复形成了闭环。

在两个不同 `PYTHONHASHSEED` 下，11 个冻结查询得到相同的 `canonical logical state`。这里比较的是记忆系统的逻辑状态，而不是数据库物理文件是否逐字节相同；同时，9,556 条所需 embedding 全部有效。

仍需分别测量 query 命中率、证据进入率和答案正确率，并对稠密召回、BM25 和图关联补全做消融，进一步判断各类信号对最终回答质量和上下文成本的实际贡献。

## 8. 高频追问

### 1. 为什么不用普通向量数据库直接 top-k？

**结论**：向量相似度只是证据链中的一部分，不能单独覆盖所有检索需求。

- 向量相似度主要解决语义相关性；
- 专有名词和精确表达需要词法信号补充；
- 关联历史需要图结构补充；
- 来源追踪需要系统在召回链路中另外保存，不能由相似度分数自动提供。

### 2. 三种检索信号是固定权重融合吗？

**结论**：不是三份列表按固定权重简单相加。

稠密和 BM25 先共同判断当前查询对应的起始线索，图结构再从这些线索扩展关联历史，最后通过稀疏化选择控制保留哪些证据。这样信号承担的是不同职责，而不是人为规定一个永远不变的比例。

### 3. 自动注入和按需补搜有什么区别？

**结论**：自动注入是低成本提供初始线索，按需补搜是 Agent 发现证据不足后的主动取证。

自动注入发生在任务开始时，数量受控，不保证覆盖全部历史。按需补搜发生在推理过程中，查询通常更具体，适合补充摘要遗漏、关键词缺失或新旧事实需要核对的部分。自动注入、按需补搜和原文取证是三层职责，不代表每次都要依次调用三个固定工具。

### 4. 有来源就能保证回答正确吗？

**结论**：不能。来源解决的是“能否核实”，不是“结论自动正确”。

还要确认来源是否对应当前使用的证据、证据是否真正进入上下文，以及原文是否支持当前结论。来源只能提供核验入口，不能替代 Agent 对条件和时间的判断。

### 5. 新旧事实冲突时怎样处理？

**结论**：不能简单假设最近的一条永远正确，而要结合对象、条件和时间判断适用范围。

先确认两条记录是不是针对同一个对象，再比较原文中的限定条件和发生时间。如果只是同一事实的更新，较新的证据可能更适用；如果条件不同，则应分别说明。证据仍不足时继续检索，或者直接向用户确认。

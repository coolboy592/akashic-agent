# 阶段 4：工具发现与上下文管理

## 4.1 30 秒入口

工具和历史持续增长后，核心问题不是给模型更多内容，而是决定本轮真正需要什么。我把两者都做成受限投影：工具统一注册，但只暴露常驻、有限预加载和本轮搜索解锁的 Schema；历史保留原始记录，只把摘要和近期完整交互单元放进模型视图。关键是区分 `registered`、`visible` 和 `executable`：搜到工具不等于 Schema 已可见，看见 Schema 也不等于程序允许执行。这样既控制完整 payload，又保持调用过程可恢复、可回查。

## 4.2 2～3 分钟回答骨架

可以按“问题 → 判断 → 行动 → 结果或复盘”来组织回答。

**问题。** 当工具从少量本地函数增长到本地工具和 MCP 工具时，全量注入 Schema 会持续占用上下文，也可能触碰 provider 对工具 Schema 数量或请求大小的限制。同时，长对话中的消息、工具调用和工具结果也会不断累积。如果只按消息条数裁剪，就可能切断一次完整的工具交互，导致模型无法正确恢复上下文。

**判断。** 工具和历史需要分别管理，但最终共同服务于同一个目标：构造本轮给模型的输入。工具侧控制当前可见的 Schema，历史侧控制当前携带的消息和摘要。搜索到一个工具的名称或说明，不代表模型已经获得它的调用结构；看到 Schema，也不代表程序一定授权执行。历史摘要也不能覆盖原始记录，它只能是面向模型的压缩投影。

**行动。** 工具先统一注册，形成完整的 `registered` 集合；在此基础上建立未加载工具目录。初始请求只携带常驻工具、会话级 LRU 预加载工具和显式预加载工具，再按照 `provider.max_tool_schemas` 形成当前 `visible` Schema 投影。模型调用 `tool_search` 后，搜索按工具元数据和关键词进行，可以用 `select:工具名` 精确选择，也可以用关键词搜索。搜索结果绑定真实工具 identity，并把当前 attempt 中实际解锁的工具登记下来。下一次请求重建投影时，优先为本次新解锁工具释放 Schema 槽位，同时保留工具搜索本身。工具最终执行前仍要经过程序侧的任务、权限和运行状态检查。

历史则按照稳定指令、已提交历史或已有摘要、当前请求锚点、动态记忆及其他运行材料、当前可见工具 Schema 的顺序组织。系统估算完整 provider payload，而不是只估算纯文本历史。达到历史实现中的 `0.74 × context window` 水位时，从较旧部分选择完整的 `CommittedContextUnit` 生成或更新摘要，同时保留最近约 `20,000 token`，再重新组装和校验请求。

**结果或复盘。** 这样既能避免全量 Schema 和完整历史共同挤占上下文，也能保证工具发现、真实 Schema 投影、程序执行和工具结果回填形成闭环。需要特别说明的是，`0.74` 和 `20,000 token` 都是历史实现中的工程参数，不是所有模型的最优值；当前能够证明的主要是机制边界、回归行为和输入输出可观测性，不能直接宣称已经获得某个端到端 token 节省率、工具成功率或长对话完成率提升。

## 4.3 从全部资源到当前可用工具

### 先统一注册，再做发现

工具来源可以不同，但在请求编排层应该有统一的工具 identity 和元数据描述。宿主已经加载的本地工具与 MCP 工具都进入统一注册集合。注册意味着系统能够根据真实 identity 找到工具定义、参数 Schema、来源和执行入口。它解决的是宿主侧的可寻址性，不代表这个工具已经进入当前模型请求。

在完整注册集合之上，可以形成工具目录。目录可以包含工具名、简短说明、来源、风险和是否允许预加载等筛选元数据；近期使用顺序由会话级 LRU 状态单独维护。目录的目的不是代替 Schema 让模型执行，而是让模型在 Schema 没有全部可见时，仍然知道如何寻找潜在工具。

因此，初始请求通常只携带三类工具：

- `always-on` 工具，例如工具搜索本身以及必须保持可用的基础工具；
- 会话级 LRU 预加载工具，也就是近期在当前会话频繁使用、且允许自动预加载的工具；
- 显式预加载工具，也就是任务或调用方明确要求优先提供的工具。

会话级 LRU 的价值是减少高频工具的重复搜索，但它不是无条件的自动授权。`preloadable=False` 的工具不会因为近期使用就自动进入预加载集合。一个工具是否能够被预加载，和它是否在当前任务中允许执行，是两个不同层次的问题。

### 按 provider 限制形成 Schema 投影

注册集合可以很大，当前请求能够携带的 Schema 却必须受 provider 能力约束。初始请求会优先保留 `tool_search`，再从 always-on、显式预加载和会话级 LRU 候选中，按 `provider.max_tool_schemas` 形成有限投影。这个投影就是当前请求真正携带的 `visible` 集合。

模型完成搜索后，投影规则会发生一次有目的的重排：保留工具搜索入口，同时优先让本次真实解锁的工具进入下一次请求；必要时淘汰原先可见的 always-on 或预加载工具。这里不存在“所有 always-on 永远可见”的保证，真正的不变量是投影不突破 provider 上限，并且成功标记为 `unlocked` 的工具确实进入下一次请求。

一次搜索匹配的工具也可能超过剩余容量，因此系统通过 `max_unlocked` 限制本次真正解锁的数量。进入下一次 Schema 投影的结果标记为 `unlocked`；其余结果明确标记为 `capacity_limited`，不能被模型或系统误认为已经可调用。

这种投影使“注册过的工具”和“模型当前能调用的工具”保持清晰边界。工具目录可以引用一个已经注册但暂时不可见的工具；模型只有在下一次请求真正收到其 Schema 后，才具备正常提出该工具调用的条件。

### 搜索是目录发现，不是语义执行

`tool_search` 的搜索基于工具元数据和关键词，而不是 embedding 向量语义检索。它支持两种容易解释的方式：

- `select:工具名`：按照工具名精确选择；
- 关键词搜索：在工具名称、说明等目录元数据中查找匹配项。

搜索结果必须返回真实工具 identity 和足以帮助判断的 Schema 信息，而不能只返回一段“你可以调用某工具”的自由文本。真实 identity 是后续状态更新和 Schema 投影的连接点：系统需要知道到底是哪一个已注册工具被选择，下一次请求也必须根据同一个 identity 找到完整定义。

搜索结果进入下一步时，系统调用 `grant_current_turn_search` 一类的机制，只在当前 attempt 内登记真实解锁结果。这里的“解锁”是当前 attempt 内的请求编排状态：在容量允许且被标记为 `unlocked` 时，系统保证对应工具进入下一次模型请求；它不是永久修改全局权限，也不是把工具加入所有后续会话。

一次搜索可能选择多个工具，因此必须有 `max_unlocked` 控制单次最多解锁多少工具。这个限制有两个作用：防止一次搜索把太多工具带入下一轮，也防止搜索结果和常驻工具一起突破 provider 的 Schema 上限。被选择但无法进入投影的工具，应明确标记为 `capacity_limited`，不能误写成 `unlocked` 或可调用。

### 解锁之后仍然要重新请求

工具发现完成后，不应期待模型仅凭上一条搜索文本就可靠地产生结构化调用。正确的数据流是：

统一注册本地工具与 MCP 工具，形成完整注册集合；从中形成未加载工具目录；初始请求只带有限工具 Schema；模型调用 `tool_search`；搜索返回真实 identity；系统在当前 attempt 登记解锁结果；投影层根据容量释放 Schema 槽位；下一次 ReAct 模型请求携带新工具的真实 Schema；模型随后可以直接提出该工具调用，不需要再次搜索。

这一步的重点是“下一次模型请求”。搜索结果本身是发现信息，真实 Schema 投影才是可调用接口。只有 Schema 进入 provider payload，模型才真正获得工具的参数结构、必填字段和调用名称。

工具进入 `visible` 后，程序侧仍然要执行准入检查。系统可以检查工具是否属于当前任务允许的范围、调用参数是否通过校验、当前用户或会话是否有权限、运行状态是否满足条件，以及执行是否会产生需要确认的外部效果。工具发现和执行权限分开后，模型不能通过搜索绕过授权，也不能因为某个工具恰好在当前请求中可见，就自动获得产生效果的资格。

工具结果完成后回填模型，并和输入、assistant 的工具调用、工具结果以及最终输出一起进入可观察执行记录。这里可以观察 ReAct 链路是否完整，但“调用过工具”仍不等于外部任务成功。外部任务是否成功，仍然需要任务自身的结果判断或独立验证。

## 4.4 历史、摘要与工具 Schema 如何共同进入请求

### 当前请求是多个来源的组合

工具选择和历史压缩不是两个互不相干的优化模块。它们共同决定 provider 本轮收到的完整 payload。一个较稳定的组织顺序是：

稳定指令  
+ 已提交历史或已有摘要  
+ 当前请求锚点  
+ 动态记忆和其他运行材料  
+ 当前可见工具 Schema

其中，稳定指令放在前面，动态 Akasha 记忆放在稳定历史之后。这样安排的原因是让更长的稳定 Prompt 前缀有机会复用缓存，而不是让每轮变化的记忆内容把前缀不断打散。系统记录输入 token 和缓存命中信息，可以为后续开销分析提供事实基础，但这些记录本身不能被夸张地解释为已经证明获得了某个端到端节省比例。

当前请求锚点用于说明本轮用户任务、当前执行状态以及需要模型继续处理的重点。动态记忆和运行材料可以帮助模型恢复相关事实，但不能取代可回查的原始会话记录。当前可见工具 Schema 则由工具投影层单独决定，不能因为历史摘要中提到过某工具，就默认该工具在本轮可调用。

### 按完整 payload 判断水位

上下文水位必须估算完整 provider payload，包括消息、摘要、稳定指令、动态材料以及工具 Schema。只统计纯文本历史会低估实际请求大小，因为工具描述、参数对象和 provider 的工具包装同样占用上下文容量。

历史实现中，在估算结果超过 `0.74 × context window` 时触发压缩。这个比例是一个工程阈值，用来给当前请求、工具结果和 provider 额外开销留下空间，并不是所有模型或所有 provider 的最优值。真正的实现应当以 provider 的上下文窗口、工具编码方式、消息格式和运行时误差为依据进行校准。

压缩时，目标不是删除最早的若干条消息，而是从较旧部分选择完整的逻辑交互单元。一个 `CommittedContextUnit` 可以包含用户请求、assistant 的判断、assistant 发起的一批 tool call、全部对应的 tool result，以及必要的后续状态。尤其是 assistant 一次发起多个工具调用时，必须等全部对应结果闭合后，才能把这一批作为已提交单元记录。

不能从一次工具调用批次中间切开。例如，不能保留 assistant 发出的两个调用而只保留其中一个工具结果，也不能只保留工具结果而删除发起调用的 assistant 消息。这样的裁剪会破坏 provider 对 assistant tool call 与 tool result 的协议边界，也会让恢复后的模型误以为某个工具已经返回、尚未返回，或者调用根本不存在。

### 摘要是模型视图，不是历史删除

系统从较旧的完整交互单元生成或更新摘要，并保留最近约 `20,000 token` 的内容作为近期上下文目标。这个数字同样是历史实现中的工程参数，实际值需要根据模型能力、任务类型和工具结果长度调整。

摘要需要维护 `generation`、`parent generation` 和 `source ref`。`generation` 表示当前摘要版本，`parent generation` 表示它从哪一个上一版本演进而来，`source ref` 表示它覆盖了哪些原始来源。这样做可以说明摘要究竟覆盖了哪段历史、如何从旧摘要更新，以及在需要回查时如何定位原始消息和工具记录。

摘要面向模型，是压缩后的可读投影；原始消息、工具调用、工具结果和执行状态仍然保留在会话存储中。模型日常推理使用摘要和近期消息，调试、恢复、争议排查或需要精确事实时，系统仍可以根据来源引用回查原文。把摘要当成新的唯一事实源，会让压缩错误变成不可逆的数据丢失；把原始历史全部重新塞回每次请求，又会失去压缩的意义。

因此，压缩后的请求应当重新组装并校验：摘要和近期单元的边界要合法，消息协议要闭合，工具 Schema 数量要在 provider 上限内，当前请求锚点和必要运行材料不能丢失。若 provider 仍然报告容量错误，可以进行有上限的重试，例如重新压缩或进一步减少可变材料，但必须区分真正的 context overflow 与认证、限流、无效参数或 provider 服务错误。不能把所有 provider 错误都误判成上下文过大，也不能无限重试。

## 4.5 代表性踩坑：搜索返回了工具，但 Schema 没有真正进入可见投影

### 现象

在 provider 限制可见工具 Schema 数量时，模型调用 `tool_search`，文本结果明确告诉它已经找到或解锁了某个工具。模型根据这个结果，在下一步尝试调用刚搜索到的工具，但系统又判定该工具的 Schema 不可见，调用无法按预期进入执行流程。

这类问题很容易被误解为模型没有理解搜索结果。实际观察请求 payload 后可能发现，下一次请求的 Schema 数量并没有超限，但新工具仍然没有出现。比如 `tool_search` 必须常驻，另外有多个 `always-on` 工具；投影逻辑在重建时继续优先保留原有常驻工具，于是本次新搜索到的工具被挤出去了。模型看到的是“搜索已经成功”，provider 实际收到的却仍然没有该工具的可调用 Schema。

### 根因

根因是三个事实没有形成一致闭环：

1. 搜索结果记录了一个工具名称或说明；
2. 当前 attempt 记录了哪些工具被解锁；
3. 下一次 provider 请求实际携带了哪些工具 Schema。

旧逻辑隐含了一个错误假设：搜索结果里写出工具名称，就等于模型下一轮一定获得这个工具的 Schema。这个假设忽略了 Schema 投影阶段还会受到 `max_tool_schemas`、常驻工具、预加载工具和排序策略的共同影响。于是系统内部认为工具已找到，模型也认为工具可用，但 provider 请求中的 `visible` 集合并不包含它。

这也说明“发现”和“可调用”不是同一个状态。搜索文本可以提供发现信息，但不能代替下一轮请求里的结构化工具定义。

### 修复

修复首先让搜索结果绑定真实工具 identity。系统不再只返回自由文本提示，而是把搜索命中的工具和注册集合中的真实定义关联起来。这样，后续解锁、投影和执行都针对同一个 identity 操作，避免名称展示和实际工具对象脱节。

其次，把真实解锁结果登记到当前 attempt。这个登记表示本轮搜索确实选择了哪些工具，并作为下一次投影重建的输入。它不是永久修改全局工具集合，也不是修改用户权限；attempt 结束后，解锁状态按本轮生命周期处理。

第三，用 `max_unlocked` 限制一次搜索能够解锁的工具数量，再和 `provider.max_tool_schemas` 一起控制投影容量。重建可见投影时，必须优先为本次新解锁工具释放槽位，同时保证 `tool_search` 等必要工具仍然可用。这样，搜索行为才会对下一次请求产生确定的 Schema 结果，而不是只改变一段说明文字。

第四，明确区分 `unlocked` 和 `capacity_limited`。搜索同时选中多个工具时，能够进入下一次 Schema 投影的工具标记为 `unlocked`；因为容量不足没有进入投影的工具标记为 `capacity_limited`。后者不能被模型或系统误认为已经可调用。下一次模型请求必须真正携带已解锁工具的 Schema。

最后，Schema 进入请求仍然不代表执行自动放行。模型提出调用以后，程序继续做参数校验、任务范围判断、权限检查和运行状态检查；只有通过执行准入，才调用真实工具并回填结果。

### 验证

回归测试构造了一个 `max_tool_schemas=2` 的 provider。场景中，`tool_search` 必须常驻，另外注册了两个 always-on 工具；搜索同时选择 `selected_tool` 和 `overflow_tool`。

初始请求实际携带 `tool_search` 和 `always_a`。搜索后，下一次模型请求携带的 Schema 变为 `tool_search` 和 `selected_tool`。随后测试确认：

- `selected_tool` 的真实 Schema 进入下一次 provider 请求，并被真实执行一次；
- `overflow_tool` 没有执行，并明确出现在 `capacity_limited` 中；
- 搜索、真实工具调用、结果回填和最终回答的 ReAct 链路能够继续完成。

这同时验证了三个边界：新工具真的进入了 Schema 投影，容量上限没有被突破，超额结果没有被误写成可调用。若只断言搜索文本包含工具名，仍然发现不了这个问题；验证必须落到下一次真实 provider payload、执行次数和容量受限集合。

## 4.6 结果、取舍与不足

全量 Schema 的优点是模型一开始就拥有完整工具选择空间，实现直观；代价是工具数量增长会持续消耗上下文，并可能触碰 provider 的工具数量限制。目录加按轮解锁把初始请求控制在较小范围内，但增加了发现状态、投影状态和跨请求一致性的管理复杂度。对于低数量、低变化的工具集合，全量注入可能足够；对于大量异构工具，按需暴露更能控制请求边界。

每轮只放最少工具可以降低 Schema 开销和模型选择噪声，但过度收缩会增加搜索轮次。会话级 LRU 预加载是中间方案：它利用当前会话的使用局部性，减少高频工具重复搜索，同时仍受 `preloadable` 和容量限制约束。它不是全局永久缓存，也不应该替代当前任务的执行权限判断。

删除旧消息看起来简单，但会损害恢复和原文回查，并可能破坏 assistant tool call 与 tool result 的协议边界。保留原始历史、只压缩模型视图，需要维护摘要版本和来源引用，工程上更复杂，但能够把“推理所需的短上下文”和“系统保留的完整记录”分开。固定消息条数裁剪也无法准确反映消息长度、工具结果大小和 provider 包装开销，因此应以完整逻辑交互单元和完整 payload 估算为基础。

稳定 Prompt 前缀与动态记忆之间也存在取舍。把动态记忆放在稳定历史之后，可以让较长的稳定前缀有机会复用缓存；但缓存是否命中以及能节省多少，仍取决于 provider 的实现、请求格式和实际任务分布。系统记录输入 token 和缓存命中信息，是为了支持后续分析，而不是端到端收益的证明。

容量错误重试能够提升恢复价值，尤其是在估算误差或 provider 实际序列化开销超出预期时。但重试必须有上限，并且只针对明确判断为容量问题的错误。无限重试会放大延迟和成本；把限流、认证失败或无效请求误判为容量错误，则会让系统在错误方向上反复压缩。

目前可以自信表达的结果是三个机制边界：搜索解锁的工具能够在 provider 容量内进入下一次真实 Schema 投影；历史压缩不会拆开已提交的工具调用批次，原始记录仍可回查；系统也记录输入 token 和缓存命中信息，为后续成本分析提供基础。

这套设计已经解决了“工具是否真正可见”和“压缩后协议是否完整”的正确性问题，但端到端收益仍需要在同一任务集上比较全量 Schema、按需发现、不同预加载策略和不同压缩阈值。现阶段不把可观测数据直接包装成 token 节省率、缓存提升或任务成功率。

## 4.7 高频追问

**1. 为什么不把所有工具 Schema 都放进请求？**

工具少时，全量注入最简单，模型也能直接选择。但工具增长后，Schema 会持续占用上下文，还可能超过 provider 的工具数量限制；大量相似工具也会增加选择噪声。因此我把目录发现和可调用 Schema 分开：初始只携带必要工具，其他工具通过搜索进入受限投影。代价是系统要维护发现状态和跨请求一致性，收益是请求边界更可控。

**2. 搜索结果已经告诉模型工具名了，为什么还要下一次请求？**

工具名和说明只是发现信息，不能代替 provider 使用的结构化 Schema。模型要可靠地产生工具调用，需要看到真实名称、参数结构和字段约束。因此搜索结果必须绑定注册表中的真实 identity，并让对应 Schema 进入下一次模型请求。

**3. `registered`、`visible` 和 `executable` 有什么区别？**

`registered` 表示宿主能够找到工具及其真实定义；`visible` 表示当前 provider 请求实际携带其 Schema；`executable` 表示它在当前任务、权限和运行状态下真正允许产生效果。注册过不代表本轮可见，可见也不代表程序一定放行执行。

**4. `max_unlocked` 和会话级 LRU 分别解决什么问题？**

`max_unlocked` 控制一次搜索最多让多少新工具进入后续投影，避免突破本次 provider 容量。LRU 利用会话内的使用局部性，让近期常用且允许预加载的工具减少重复搜索。前者控制单次发现，后者优化跨请求体验；二者都不等于执行授权，`preloadable=False` 的工具也不会自动进入 LRU 预加载。

**5. 为什么不能按固定消息条数裁剪历史？**

消息条数不能准确反映 token 大小，更重要的是工具交互有协议边界。assistant 可能一次发起多个 tool call，只有全部对应 result 都返回后，这一批才是完整的已提交单元。从中间切开会留下不闭合的调用或结果，破坏 provider 协议和恢复语义，因此压缩必须以完整 `CommittedContextUnit` 为边界。

**6. 已经有摘要了，为什么还要保留原始历史？**

摘要是给模型使用的压缩投影，可能省略精确参数、原话和执行顺序，不适合作为唯一事实源。原始消息和工具记录继续保存在会话存储中；摘要通过 generation、parent generation 和 source ref 标明版本演进与来源范围，需要核对时仍能回到原文。

**7. `0.74 × context window`、最近约 `20,000 token` 和容量重试是否适用于所有模型？**

不适用。它们是历史实现中的工程参数，需要根据 provider 的窗口、工具序列化方式和任务分布校准。系统估算的是完整 payload；若 provider 仍明确报告容量错误，可以有限重试和重新压缩，但不能把认证、限流或服务错误一律当成 context overflow。

**8. 这一设计已经证明节省了多少 token 或提升了多少成功率？**

目前确认的是正确性边界：受容量限制的 Schema 投影能够工作，新搜索工具能真正进入下一次请求，压缩不会破坏完整工具批次，输入 token 和缓存信息也能够记录。端到端 token、缓存和任务成功率收益仍需要在统一任务集上做消融比较，不能从机制成立直接推出效果数字。

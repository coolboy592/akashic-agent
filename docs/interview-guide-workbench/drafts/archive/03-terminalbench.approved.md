# 阶段 3：Terminal-Bench 2.1 端到端评测与故障归因

## 3.1 30 秒入口

我做这项评测时，首先解决的是“模型说完成了”和“任务真的完成了”之间的差别。终端任务的结果不在回答文本里，而在真实隔离环境的文件、进程、配置和测试状态中，所以必须让真实 Agent 通过真实工具执行，再由任务官方 Verifier 检查最终状态。基于固定的 Terminal-Bench 2.1 89 题、DeepSeek V4 Flash 和 `reasoning_effort=max` 配置，最终官方 Verifier `reward=1` 的是 59 题，通过率为 `59/89 = 66.3%`。同时，我保留了 Provider 和 Verifier 的执行证据，因此可以把 Agent、Provider 和 Verifier 故障分开，而不是把所有 0 分都算成 Agent 答错。

## 3.2 2～3 分钟回答骨架

### 问题

这套评测要解决的问题是，传统的文本结果无法证明终端任务已经完成。模型可能输出“已经修复”，也可能调用过几个工具，但目标文件内容不正确、测试没有通过、后台进程没有按要求运行，或者整个模型回合根本没有有效形成。若只看最终文本或一个 reward，无法判断失败发生在 Agent 策略、模型供应链还是验证基础设施。

### 判断

我的判断是，Terminal-Bench 这类任务必须以真实环境的最终状态作为评价对象，以官方 Verifier 作为成功标准，并把执行过程和环境状态作为归因依据。统一的 ReAct 执行只是让 Agent 能够在任务中读取信息、判断下一步并调用工具；它本身不等于任务成功。成功必须同时满足两个条件：一是形成了有效的 Agent 执行回合，二是该执行产生的候选状态通过了外部 Verifier。

### 行动

我主导设计并落地的是一条逐题、可恢复的端到端闭环。每道题都会读取任务定义和官方时限，创建独立 Trial、Docker project 和 workspace，并检查挂载、网络、volume、在线进程以及凭据边界。随后启动 Akashic runtime，让真实 Agent 使用真实工具执行任务。

Agent 结束，或者达到 Agent 自身时限后，系统先清理 Agent 生命周期，再冻结候选状态。这里的“结束”不等于“成功”，也不意味着可以跳过验证。候选状态冻结后，系统准备并运行官方 Verifier，记录 reward、可观察执行 trace、stdout、资源状态、候选 artifact digest 和最终 manifest。完整 outcome 追加到 campaign WAL，再由 accepted 事件原子生成 `accepted-results.json` 这样的结果投影。

### 结果与复盘

正式结果是 59 题 `reward=1`，26 题有效 `reward=0`，3 题 Provider fallback，1 题 Verifier 基础设施依赖失败，合计固定的 89 题。这里的 26 个才是有效的 Agent 失败，其中包括真实 Agent timeout；3 个 Provider fallback 没有形成可评价的有效 Agent 回合；1 个 Verifier 基础设施失败则没有真正进入测试正文。

最重要的复盘是，我发现不能把“runtime 返回了最终内容”当成“Provider 形成了有效模型回合”。曾经有 Provider fallback 被当成 `reward=0`，污染了 Agent 失败统计。修复后，接受 Agent 结果前必须检查真实 turn、trace 和 Provider 终态，fallback 被单独归为 Provider 故障。

## 3.3 为什么文本完成不等于任务完成

终端任务的目标通常是改变某种外部状态，而不是生成一段看起来合理的文字。例如，任务可能要求修改配置、生成文件、安装依赖、启动服务、修复测试，或者让某个进程以指定参数持续运行。最终答案只描述了模型认为自己做了什么，不能直接证明这些状态已经存在。

模型自评有三个天然限制。

第一，模型看到的是自己的操作上下文，而不是一个独立、可信的最终状态判定。它可能根据工具返回的局部信息推断成功，却没有验证所有约束。例如命令返回了 0，但写入路径错误；文件被创建了，但内容格式不符合要求；服务启动了，但端口没有监听；测试执行了，但实际运行的不是任务要求的测试集。

第二，文本 Judge 评价的是可读性和表面合理性。它可以判断回答是否像一个正确的解释，却很难可靠检查容器里最终留下了什么。对于文件权限、进程生命周期、依赖版本、端口状态、目录结构等条件，外部环境通常才是事实来源。

第三，“调用过工具”只说明 Agent 发出过动作，不说明动作产生了正确结果。工具调用可能失败、作用于错误对象、被后续操作覆盖，或者只完成了任务的一部分。即使所有工具都正常返回，任务仍可能没有满足官方测试的完整条件。

因此，评测对象不是“模型有没有说出正确答案”，而是 Akashic Agent 能否理解终端任务，在隔离环境中通过真实工具形成正确的状态，并通过任务官方 Verifier。官方 Verifier 关注的是最终候选状态，而不是模型对自身表现的描述。它也让不同 Agent 的结果落在同一个外部标准上，减少“模型评模型”带来的主观漂移。

这并不意味着要保存模型不可观察的内部思维过程。可归因的证据应当是系统实际能够观测和复现的内容：输入、模型回合状态、工具调用、工具结果、最终输出、stdout、资源状态、候选产物摘要以及环境 manifest。证据的作用是重建发生了什么，而不是声称掌握模型完整的内部思考。

## 3.4 从真实执行到官方 Verifier 的评测闭环

单题的数据流可以概括为：

```text
读取任务与官方时限
        |
        v
创建独立 Trial、Docker project、workspace
        |
        v
校验挂载、网络、volume、进程、凭据边界
        |
        v
启动真实 Agent，通过真实工具执行
        |
        v
Agent 结束或达到自身时限
        |
        v
清理 Agent 生命周期，冻结候选状态
        |
        v
准备并运行官方 Verifier
        |
        v
记录 reward、trace、资源证据、artifact digest、manifest
        |
        v
将完整 outcome 追加 campaign WAL
        |
        v
从 accepted 事件原子生成结果投影
```

这条链路的关键不在于组件数量，而在于每个控制点解决了不同的问题。

### 逐题隔离保证结果有明确边界

每道题使用独立 Trial，可以避免前一道题留下的文件、进程、端口、volume 或凭据影响后一题。共享环境下，即使 Agent 没有完成任务，也可能因为前一题安装过依赖、启动过服务或修改过目录而得到异常高分；反过来，后台进程或错误配置也可能污染后续题目。

隔离还解决了产物归属问题。某个文件、进程状态或容器快照必须能够明确回答“它属于哪一道题、哪个 Trial、哪个候选状态”。只有 owner 清楚，后续的 Verifier 结果、artifact digest 和故障归因才不会混在一起。

### Agent 截止时间不等于 Trial 结束

Agent 达到自身截止时间，只表示模型与工具交互阶段结束，不能直接决定 reward，也不能跳过后续验证。系统需要先终止并清理属于该 Trial 的 Agent 进程，确认它不会继续修改候选环境，再冻结状态并运行官方 Verifier。

因此，timeout 的责任分类要等 Provider 有效性和 Verifier 结果都确认后再下结论。本次正式结果中的真实 Agent timeout 落在 26 个有效 `reward=0` 中；一般情况下，如果 Agent 在超时前已经形成正确状态，Verifier 仍然有可能给出 `reward=1`。

### Verifier 准备不能修改候选答案

官方 Verifier 可能需要准备依赖、启动验证进程或设置自己的运行环境。这个阶段必须证明它没有修改 `/app` 中由 Agent 形成的候选答案，否则验证结果就不再是对 Agent 产物的判断，而是对“候选答案加验证准备脚本”共同作用结果的判断。

因此，准备验证环境时需要把候选 workspace 和 Verifier 自身依赖边界分开，并通过冻结状态、digest 或其他资源证据确认候选内容保持一致。Verifier 的依赖可以放在它自己的环境中准备，但不能为了让测试运行而偷偷改变待测目录。

### Trial 完整与通过是两个维度

一个 Trial 可以拥有完整的生命周期和可信的执行证据，却得到 `reward=0`。这表示系统完整记录了任务输入、Agent 执行、候选终态和官方验证结果，但 Agent 没有满足任务条件。反过来，如果 Provider fallback 或 Verifier 依赖失败，Trial 可能有部分记录，却不能把它当成有效的 Agent 成败结果。

所以结果统计不能只依赖“有没有一条结果记录”，也不能只依赖 reward。必须同时判断 Provider 是否形成有效回合、候选状态是否完成冻结、Verifier 是否进入有效测试正文，以及相关证据是否完整一致。

### WAL 是恢复事实源，结果文件是投影

campaign WAL 采用 append-only 方式记录完整 outcome。它保留了评测过程中已经确认的事实，适合在中断后恢复，也能避免直接覆盖结果文件造成部分写入或状态倒退。

`accepted-results.json` 是从 accepted 事件生成的结果投影，方便查询和展示，但它不是原始事实源。投影可以重建，WAL 中已经追加的事件则用于判断某个 Trial 到了哪一步、是否已经被接受以及恢复时是否需要继续处理。一次 campaign 的中断与恢复仍然属于同一次评测，不应被统计成多次独立评测。

### 接受结果需要满足一致性条件

一个 accepted 结果不能只带一个数字。至少要能关联到完整 trace、有效的外部 Verifier、容器终态以及一致的 owner。这样结果投影中的一行数据，才能回到具体 Trial，进一步回到具体工具调用和候选 artifact。

这也是为什么要保存 digest 和 manifest。它们不一定解释 Agent 为什么做出某个决定，但可以帮助确认 Verifier 看见的候选状态是否就是 Agent 结束后冻结的那一个状态。

## 3.5 评测结果与故障分布

本次评测固定使用 Terminal-Bench 2.1 的 89 道题，被测模型为 DeepSeek V4 Flash，推理配置为 `reasoning_effort=max`。评测对象是 Akashic Agent 在真实隔离终端环境中的执行能力，以及它能否通过每道任务的官方 Verifier。

正式结果如下：

- 官方 Verifier `reward=1`：59 题。
- 有效 `reward=0`：26 题，其中包括真实 Agent timeout。
- Provider fallback：3 题。
- Verifier 基础设施依赖失败：1 题。
- 固定 89 题上的最终通过率：`59/89 = 66.3%`。

59、26、3、1 加起来是 89，但它们不是同一种责任结果。26 个有效 `reward=0` 可以进入 Agent 失败分析；3 个 Provider fallback 没有形成可评价的有效 Agent 回合，不能说明 Agent 的任务策略失败；1 个 Verifier 基础设施依赖失败没有真正进入测试正文，也不能被伪装成有效的 `reward=0`。

因此，固定任务集中的 30 个非通过项，应理解为 26 个有效 Agent 失败、3 个 Provider 故障和 1 个 Verifier 基础设施故障，而不是“30 个 Agent 失败”。这种拆分直接影响后续行动：Agent 失败需要分析工具使用、任务理解和终态构造；Provider 故障需要检查模型供应链和 runtime 回合状态；Verifier 故障需要修复验证环境或依赖准备。

这里的 `66.3%` 是当前模型、当前推理配置和固定 Terminal-Bench 2.1 任务集上的端到端通过率。它可以用于比较同一评测口径下的改动，也可以帮助定位当前系统的有效任务能力，但不能外推为模型的通用能力、线上业务效果或用户规模。

### 三类故障的责任边界

**Agent 故障**：Provider 已经形成有效模型回合，Agent 实际执行了任务，官方 Verifier 也有效运行，但最终得到 `reward=0`。真实 Agent timeout 也属于这一类有效失败，因为它反映的是 Agent 在规定执行边界内没有形成通过验证的最终状态。

**Provider 故障**：模型供应链没有形成可评价的有效 Agent 回合，例如 runtime 返回 fallback。它可能在结果表面上出现 0 分，但没有足够依据说明 Agent 已经真正执行并失败，因此应单独统计为 Provider 故障。

**Verifier 故障**：候选状态已经形成，但官方验证阶段因为验证器自身环境或依赖问题，没有进入有效测试正文。这类问题不能算作 Agent 答错，也不能伪装成有效 `reward=0`。

这套边界的工程价值在于，失败会回到正确的优化对象。把 Provider fallback 当成 Agent 策略失败，会让团队去调整提示词、工具策略或模型推理，却无法解决模型回合根本没有形成的问题。

## 3.6 代表性踩坑：Provider fallback 污染失败归因

### 现象

结果文件中出现了 0 分，表面上看像是 Agent 已经执行了任务，只是任务结果错误。按照这种表面理解，失败似乎应该进入 Agent 策略分析，例如检查它是否误读了题目、调用了错误工具或遗漏了最后一步。

### 根因

实际检查真实 turn、trace 和 Provider 终态后发现，其中一部分并不是有效的 Agent 回合，而是 runtime 返回的 Provider fallback。fallback 内容被后续流程当成了 completed model turn，accepted projection 在接收结果前没有先检查 Provider 是否真的形成了有效终态。

于是系统把“Provider 没有提供有效模型执行”转换成了“Agent 执行完成但官方验证失败”。最终文件里的 reward 可能看起来合理，但它所表达的责任含义已经错了。

### 原先不成立的假设

原实现默认，只要 runtime 返回了最终正文或 completed 状态，就代表形成了有效模型回合，后续的 `reward=0` 可以归因给 Agent。

这个假设忽略了两种状态之间的区别：

- runtime 返回了某些内容；
- Provider 成功形成了可评价的模型回合，并让 Agent 完成了自己的执行流程。

fallback 文本可能有正文，也可能带有类似完成状态的外观，但它并不等于真实模型执行结果。若不检查 Provider 终态，结果管道就会把内容存在性误当成执行有效性。

### 修复

修复时回到真实 turn 和 trace，先检查 Provider 终态，再决定是否接受 Agent 结果。Provider 有效终态成为接受 Agent 结果的前置条件。

只有在 Provider 已形成有效模型回合、Agent 执行过程可评价、候选状态完成冻结，并且外部 Verifier 有效运行的情况下，Verifier 的 `reward=0` 才能进入有效 Agent 失败统计。fallback 正文不能作为有效 Agent 回合进入 Agent 成败统计，而应单独归为 Provider 故障。

这不是简单增加一个分类字段，而是修正了结果管道的因果顺序：先确认“谁真正执行了什么”，再解释最终 reward。接受结果时必须检查相关证据是否一致，而不能只看 runtime 的表面返回值。

### 验证

重新按照真实 turn、trace 和 Provider 终态分类后，识别出 3 个 Provider fallback。最终形成完整分布：

- 59 个官方 Verifier `reward=1`；
- 26 个有效 `reward=0`；
- 3 个 Provider fallback；
- 1 个 Verifier 基础设施失败。

这次修复带来的核心变化不是总题数变化，而是失败含义变得可信。Agent 失败统计不再混入没有有效模型回合的 Provider 故障，后续对 Agent 策略的分析才有正确输入。

Verifier 依赖下载、timeout 子进程生命周期和 campaign 恢复，都是同一条边界上的进一步问题：验证准备不能改写候选答案，Agent timeout 后要完成清理和冻结，campaign 中断后要依据 WAL 恢复已确认事实。但它们都服务于同一个原则，即在统计之前先确认每个阶段确实发生过，并且证据能够对应到正确的 owner。

## 3.7 结果、取舍与不足

### 文本 Judge 与官方 Verifier

文本 Judge 成本低、反馈快，适合评价解释质量、回答格式或开放式内容；但 Terminal-Bench 的核心目标是环境状态，文本 Judge 无法替代官方 Verifier。我的选择是把官方 Verifier 作为最终通过标准，把文本和执行 trace 用于诊断，而不是让模型对自己的任务结果进行最终裁决。

获得的是更明确的成功定义和更强的跨题一致性，代价是必须维护真实容器、验证依赖和更复杂的执行流程。

### 共享环境与逐题隔离

共享环境可以减少容器创建和依赖准备的时间，但污染风险很高：文件、进程、端口、volume 和凭据都可能跨题残留。逐题隔离会增加启动、清理和存储成本，但它让每道题的输入、执行和产物拥有清晰边界，也使失败重放和结果归因更可靠。

对于端到端评测，隔离不是额外的工程装饰，而是保证分数含义成立的前提。

### 只保存最终分数与保存完整冷证据

只保存 reward 的实现简单、存储成本低，但出现异常时几乎无法回答：Agent 是否真的执行过、Verifier 看见了什么、Provider 是否有效、候选状态有没有被修改、某个结果属于哪个 Trial。

保存 trace、stdout、资源状态、artifact digest 和 manifest 会增加存储和实现复杂度，也会要求系统处理隐私和凭据边界，但换来的是可恢复、可归因和可复查的结果。这里保存的是可观察执行证据，不是模型完整内部思维过程。

### 直接覆盖结果文件与 WAL 加投影

直接覆盖结果文件容易实现，但中断时可能留下半写入状态，也无法清楚区分“已经确认的结果”和“正在处理的 Trial”。WAL 加投影需要更多状态设计，但 append-only 的 WAL 可以作为恢复事实源，结果投影则可以按 accepted 事件原子重建。

这套设计的成本是实现复杂度和额外磁盘空间，收益是 campaign 中断后可以继续恢复，并且不会把一次评测的恢复片段误算成多次独立评测。

### 结果边界与限制

`66.3%` 只代表当前 DeepSeek V4 Flash、`reasoning_effort=max` 和固定 Terminal-Bench 2.1 任务集上的结果。它不代表模型在其他任务集上的通用能力，也不代表线上业务效果。

Provider 和 Verifier 故障必须单列，因为它们对应不同的改进对象。外部 Verifier 比模型自评更可信，但验证器自身仍可能有依赖和基础设施问题，因此“使用官方 Verifier”并不等于验证阶段永远不会失败。

这套评测的运行成本主要来自逐题隔离、真实工具执行、容器生命周期、Verifier 依赖准备和证据存储。选择它，是因为这些成本换来了一个更有工程意义的答案：Agent 是否真的在目标环境中完成了任务，以及一次失败究竟应该由哪个层级负责。

## 3.8 高频追问

### 1. 为什么不能相信模型说“完成了”？

因为模型的最终文本只是自我描述，终端任务的事实存在于环境状态中。模型可能误判命令结果、遗漏约束，或者在错误路径上完成了看似合理的操作。只有把候选状态交给官方 Verifier，才能判断任务要求是否真正满足。

### 2. 为什么调用过工具仍不能算成功？

工具调用只证明 Agent 发出了动作，不证明动作成功改变了正确状态。调用可能返回错误、作用于错误文件、被后续操作覆盖，或者只完成了任务的一部分。成功标准应当是最终状态通过 Verifier，而不是调用次数或调用存在性。

### 3. 为什么选择官方 Verifier，而不是再让一个模型打分？

因为这类任务的标准通常是文件、进程、配置、依赖和测试状态，官方 Verifier 可以直接检查这些外部状态。另一个模型仍然主要根据文本和有限上下文判断，容易受到表达方式影响，也不能可靠替代实际测试。模型评分可以作为诊断信号，但不应取代任务官方验证。

### 4. 如何避免不同题目之间互相污染？

每道题创建独立 Trial、Docker project 和 workspace，并检查挂载、网络、volume、在线进程和凭据边界。Agent 结束后还要清理生命周期，确认没有残留进程继续修改环境。这样每道题的候选状态和产物都有明确 owner，不会继承前一道题的文件或服务。

### 5. Agent timeout 后为什么还要运行 Verifier？

timeout 只表示 Agent 工作阶段超过了规定时限，不代表候选状态一定没有价值。Agent 可能在超时前已经完成了全部必要修改。清理 Agent 生命周期并冻结候选状态后，Verifier 仍可以判断这个最终状态是否满足任务要求。这样 timeout 仍然是一个可评价的 Agent 结果，而不是被执行器直接吞掉。

### 6. 为什么不能把所有 reward 0 都记为 Agent 失败？

因为 reward 只描述验证结果，不单独描述 Provider 是否形成了有效回合，也不描述 Verifier 是否真正进入了有效测试正文。Provider fallback 可能导致表面上的 0 分，但 Agent 根本没有完成可评价的模型回合；Verifier 依赖失败则可能没有进行有效测试。两者都不能归因给 Agent。

### 7. 如何判断是 Provider、Agent 还是 Verifier 的问题？

先看 Provider 是否形成了有效模型回合，再看 Agent 是否实际执行并形成了可冻结的候选状态，最后看官方 Verifier 是否在自身依赖正常的情况下进入有效测试正文。若 Provider 有效、Agent 执行有效、Verifier 有效运行但 reward 为 0，归为 Agent 故障；若没有有效模型回合，归为 Provider 故障；若候选已形成但验证阶段因自身环境或依赖失败，归为 Verifier 故障。

### 8. WAL 和结果投影分别解决什么问题？

WAL 是 append-only 的事实记录，用来保存完整 outcome，并支持 campaign 中断后的恢复。结果投影是从 accepted 事件生成的查询视图，便于查看最终结果，但可以重建，不能替代 WAL。这样既保留了恢复依据，也避免直接覆盖结果文件造成不一致。

### 9. `66.3%` 能说明什么，不能说明什么？

它说明在固定的 Terminal-Bench 2.1 89 题、DeepSeek V4 Flash 和 `reasoning_effort=max` 配置下，官方 Verifier 判定通过的比例是 `59/89`。它可以用于这一评测口径内的比较。它不能直接说明模型的通用能力、线上业务成功率、用户规模或其他任务集上的表现；同时，Provider 和 Verifier 故障也不能被隐藏在 Agent 能力结论中。

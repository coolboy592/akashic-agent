## 二、项目定位与统一 ReAct 共同地基

### 1. 30 秒项目定位骨架

- Akashic Agent 是我面向长期个性化交互设计并落地的 Agent 运行时。
- 我重点解决历史信息难找、工具和上下文持续增长、主动行为缺少依据，以及任务结果难以真实验证的问题。
- 统一 ReAct 是共同执行基础，把模型判断、工具执行、结果回填和最终回答连接起来，支撑长期记忆、上下文管理、主动交互和端到端评测。

### 2. 90 秒项目介绍骨架

- 这个项目面向个人助手场景，我主导设计并落地了一套面向长期个性化交互的 Agent 运行时。它关注的不是让模型偶尔调用几个工具，而是让系统能够在持续运行中利用历史、执行任务，并控制对用户的影响。
- 长期运行主要带来四个问题：当前问题可能依赖很久以前的事实，工具和上下文会不断增长，用户没有提问时的主动行为需要充分依据，模型说完成也不等于真实任务已经完成。
- 我的总体判断是，不能简单把更多历史和工具交给模型，而要分别处理历史证据、当前材料、程序执行和外部结果。
- 在执行层，我用统一 ReAct 把这些环节连接起来：系统准备当前需要的历史和工具，模型判断直接回答还是调用工具，程序确认并执行工具，再把结果返回给模型继续判断，直到形成最终回答或后续处理结果。
- 这套设计的价值是让长期交互更容易追溯和恢复，也让主动行为经过单独判断，让评测能够基于真实执行结果区分 Agent、Provider 和 Verifier 的问题。

### 3. 为什么它不只是“对话模型加工具”

长期运行中的第一个问题是，当前问题可能依赖很久以前的信息，而最近几轮对话并不能直接提供足够依据。我的判断是，历史需要被重新检索，证据不足时还要继续补搜，并且能够回到真实来源。这样记忆就不只是给模型更多文字，而是为当前回答提供可核对的依据，这也是长期记忆与证据检索章节要解决的问题。

第二个问题是，工具和历史会不断增长。如果每轮都把所有工具定义和所有消息交给模型，真正有用的内容反而可能被挤出去。我的判断是，系统需要根据当前任务选择工具和历史材料，同时保持工具调用与结果的完整记录。这引出了工具发现与上下文管理章节。

第三个问题是，用户没有在本轮提问时，系统不能因为生成了一段看似相关的内容就直接打扰用户。我的判断是，主动行为要经过兴趣判断、证据调查、重复控制和发送授权，普通回答不能自动变成主动发送。这引出了主动交互策略章节。

第四个问题是，模型说“完成了”并不代表真实环境中的任务已经完成。我的判断是，要让真实 Agent 执行任务，再由外部 Verifier 判断结果，并根据证据区分 Agent、Provider 和 Verifier 的故障。这引出了 Terminal-Bench 2.1 端到端评测章节。

### 4. 统一 ReAct 的正常执行链

一次需要工具的被动请求，会先由系统准备当前需要的历史和工具，再交给模型判断。模型可以直接回答，也可以提出工具调用；但模型提出调用只是建议，真正的工具执行由程序负责确认和完成。工具执行结果会返回模型，作为下一轮判断的依据，系统继续循环，直到模型形成最终回答。系统记录输入、工具调用、工具结果和最终输出等可观察信息，不保存模型完整的内部思维过程。

```text
用户提出任务
    ↓
系统准备当前需要的历史与工具
    ↓
模型判断：直接回答，还是调用工具
    ├─ 直接回答
    │      ↓
    │   形成最终回答
    │
    └─ 调用工具
           ↓
       程序确认并执行工具
           ↓
       工具结果返回模型
           └────────→ 继续判断
```

这条链路把模型的判断和程序的执行分开，也让工具结果能够回到下一轮判断。主动任务复用判断、工具执行和观察回填，但拥有独立的准入、工具范围和发送终态。

### 5. 三个关键设计判断

#### 5.1 原始事实与模型本轮看到的内容分开

长期运行需要保留原始消息、工具调用和工具结果，但模型不需要每轮看到全部历史。因此我把可恢复的原始事实和模型本轮看到的内容分开：事实持续保存，当前请求只选择与任务相关的历史、摘要、动态材料和工具。这样可以避免把不可追溯的摘要直接当成最终依据，也保留后续恢复和核对的可能；代价是需要额外维护历史选择和当前请求组织。

#### 5.2 模型负责提出行动，程序负责确认和执行

模型可以根据当前材料提出工具调用，但它看到工具不代表已经获得执行权限。因此我让模型负责提出行动建议，由程序确认是否适合当前请求，再执行工具并记录结果。这样可以把模型想做什么和系统实际做了什么分开，也避免工具发现只停留在文字提示层；代价是执行链更长，程序需要维护校验、状态和异常处理。

#### 5.3 被动回答和主动任务共用 ReAct，但主动发送需要额外授权

被动回答和主动任务都需要判断、工具执行和结果回填，复用统一 ReAct 可以减少重复建设。但主动任务发生在用户没有发起本轮提问时，普通模型回答不能直接变成发送动作。因此我让两类任务共用执行基础，同时为主动任务增加单独的准入、工具范围和发送决定。这样可以复用执行能力，又避免普通正文越过主动发送授权；代价是主动任务需要额外的判断和发送控制。

### 6. 四项能力在整体架构中的位置

```text
用户输入 / 主动事件
        ↓
长期记忆：提供历史线索与来源
        ↓
上下文层：选择当前需要的历史、动态材料与工具
        ↓
统一 ReAct：判断 → 工具 → 观察 → 最终结果
        ↓
被动回答，或经过授权的主动发送
        ↓
保存执行记录、结果与回执
        ├─ 支持恢复
        └─ 支持评测和故障诊断
```

- **长期记忆**提供历史线索和来源，让当前任务能够利用较早的信息。
- **工具与上下文**决定本轮给模型什么材料和哪些工具，同时保持调用结果的完整记录。
- **主动交互**复用统一执行能力，但额外负责兴趣判断、主动准入和发送决定。
- **Terminal-Bench**让真实 Agent 执行任务，再由外部 Verifier 判断任务是否完成。

### 7. 高频追问

#### 7.1 为什么它不只是聊天 Agent 加插件？

因为项目解决的不是单纯的工具调用问题，而是长期运行中的历史利用、上下文增长、主动授权和真实结果验证。工具只是执行链中的一个动作，系统还要决定模型看到什么、程序实际执行什么，以及任务结果如何被确认。

#### 7.2 统一 ReAct 是不是第五项成果？

不是。统一 ReAct 是长期记忆、工具与上下文、主动交互和端到端评测共享的执行基础，不是并列的第五项成果。四项能力分别在历史材料、当前工具、主动发送和外部验证这些位置接入这条执行链。

#### 7.3 为什么不能让模型直接执行工具或直接发送？

因为模型只能提出行动建议，程序才负责确认和执行。工具调用需要经过程序判断，主动发送还需要额外授权；否则模型生成的内容就会被误认为已经执行或已经送达。

### 8. 面试时怎么把握

- 统一 ReAct 要讲成四项能力共享的共同地基，不单独包装成第五项成果。
- 项目结果要基于真实执行和已有验证来表达，不补充尚未测量的业务数字。

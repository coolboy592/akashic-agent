# Akashic Agent 面试指导书：规则入口

> 2026-09-14 重建。本文件是唯一规则入口。旧规则文件（00-workflow-and-state、01-source-of-truth、03-terminology-and-claim-rules）已废弃并移入 `drafts/archive/`；任何旧稿或事实包中的旧写作要求不能覆盖本文件。用户最新明确指令始终优先。

## 1. 目标与定位

在 Agent 开发实习岗位的 30～60 分钟技术面试中，把本项目讲清楚。读者双重：面试官听口述层，用户本人用全书复习与排练。

讲解主线为 `F:/agent/agent简历.md` 的四条能力：长期记忆与证据检索、Agent 端到端评测、工具发现与上下文管理、主动交互策略。统一 ReAct 是共同地基，不另造第五项成绩。

文档定位是技术文档：好阅读与技术含量统一。全书不使用生活化比喻；可读性靠结构与因果叙述达成，不靠口语化。

## 3. 口述层（每能力章第一部分）

第一人称、五段模板，句式完整、可直接口述：

1. **背景与问题**：当时卡在哪——现象与代价，不先堆架构。
2. **我的判断**：为什么这样选择——对比过什么、放弃了什么、依据是什么。
3. **具体行动**：亲手做了什么——按因果串成行动序列，不是功能清单。
4. **结果与复盘**：结果与边界——有数字讲数字并说明口径；没有数字讲验证方式与边界，不编数字。
5. **设计取舍、踩过的坑、怎么修的**：现象→误判→根因→修复→验证，选 1～2 个最有讲述价值的案例。

硬性标准：

- 篇幅 3～6 分钟（约 1000～1600 字）。
- 代码符号（函数/参数/常量名）每章至多 3 个，首次出现括注一句作用；其余用精确中文名。
- 不放链接、不放 commit 号。
- 支撑层的机制描述用第三人称（本项目/系统）。

## 4. 支撑层（每能力章第二部分）

四个固定板块：

1. **关键机制详解**：口述层每个论断落到实现。项目内符号（函数/类/参数/常量）可以使用，每个符号首次出现必须紧跟一句作用说明；无解释的符号视为违规。
2. **简历效果 ↔ 实现技术对照表**：简历每句主张在左，实现它的具体技术在右。
3. **与主流替代方案对比**：公平比较——说明本项目的选择、付出的代价、其他方案更优的场景，不弱化对手。每组对比覆盖该问题的主流方法谱系，不止"本项目 vs 单一对手"的二元对照；谱系起点见 `01-fact-boundaries.md` §6，可按章节事实与业界现状扩展；替代方案以最强形态出场，本项目在谱系中定位，并说明与相邻形态的正交或叠加关系（例：对话压缩不止滑动窗口 vs 摘要，还应覆盖工具结果就地清理、滚动摘要、外置记忆取回、长窗口不压缩等形态）。
4. **高概率追问与要点**：从口述层论断自然引出，给要点与方向，不写成逐字稿。

链接政策（链接只出现在支撑层与对照表，口述层纯文本）：

- 通用概念优先链 [learnagent.wiki](https://learnagent.wiki/agent) 中文条目；
- 无条目的概念（如 BM25、KV cache）链官方一手文档（modelcontextprotocol.io、Elastic、sbert、模型厂商文档）；
- 两者皆无时正文一句话界定，不强行附链。

硬性标准：

- 读者读完任一条目，能说出"这个名字是干嘛的"。
- 版本兼容性审计、证据核查过程等内部工作内容不进正文，留在事实包。

## 5. 黄金样例（风格锚点）

### 口述层（工具与上下文章·节选）

> 项目初期只有少量本地工具，全部工具 Schema 随每个请求下发，成本可以忽略。接入 MCP、注册工具增长到几十个之后，出现两个直接问题：其一，工具定义与对话历史竞争同一个上下文窗口，每轮请求都要为全部工具的名称、描述和参数结构支付 token；其二，provider 对单个请求可携带的工具数有硬性上限，全量注入直接触碰限制。调试中还暴露出一个更隐蔽的缺陷：模型已经"知道"某个工具存在并尝试调用，却因为该工具的 Schema 没有进入本轮请求而调用失败——系统把"注册过的工具"和"本轮可调用的工具"当成了同一件事。
>
> 我的判断是，这不该靠继续扩大上下文窗口解决，而是缺少一个显式的投影层：注册表保持完整，每轮请求只携带一个受容量约束的可见工具集合；未进入集合的工具放进可搜索的目录，模型按需检索、当轮解锁后进入后续请求。这把"能力总量"与"单轮可见性"解耦，代价是引入一次工具发现交互和跨请求的投影状态管理。这个交换在工具规模大、单任务只使用其中小部分的场景下成立；工具少且稳定的项目，全量注入仍是更简单的正确选择。

### 支撑层·关键机制详解（条目格式）

> - `tool_search`——注册表内的元搜索工具：模型用名称或关键词在工具目录中定位工具；自身必须常驻可见集合，否则发现入口不可达。
> - `max_tool_schemas`——provider 对单请求工具数的硬上限：可见投影据此裁剪，当轮解锁的新工具优先占用被淘汰的旧预加载工具的槽位。
> - `CommittedContextUnit`（已提交上下文单元）——压缩的最小完整交互单位：覆盖用户消息、assistant 发起的整批工具调用与全部对应结果，批次闭合前不可提交，保证压缩不会从协议中间切断。

### 支撑层·通用概念对照（链接格式）

> - ReAct → learnagent.wiki「ReAct（推理与行动协同）」
> - MCP → modelcontextprotocol.io 官方规范
> - 混合检索与重排 → Elastic 混合检索 / sbert retrieve-rerank

## 7. 写作流程

一章一任务：读本文件 + `01-fact-boundaries.md` + 对应 packet（`drafts/archive/` 旧稿可作素材，不继承结构与结论）→ 产出 `drafts/chapters/chapter-*.md` → 用户以"口述层能否直接讲出来"验收 → 定点返修。各章在新 ZCode 会话中的启动 prompt、验收要点与返修模板见 `02-execution-playbook.md`；编写顺序为能力章先行（tools-context 打样 → memory → terminalbench → proactive），总述与对比附录最后。

不做：阶段任务契约、verify 仪式、跨文件状态同步。全书完成后由用户决定是否更新正式文件 `docs/interview-guide.md`。

Git 提交由用户决定；未经请求不暂存、提交或推送。

[akashic-plugins](https://github.com/akashic-plugins) 中的相关实现属于研究范围，但不按插件数量增加章节或简历亮点。沿当前问题检查实现位置和主仓库衔接，记录采用的插件提交或版本；当前页面、更新时间或“兼容”标签不能单独证明历史基线已具备某项能力。

### 1.2 材料不足不等于功能缺失

## 2. 项目定位

允许表述：

> Akashic Agent 是面向长期个性化交互的 Agent 运行时。它以统一 ReAct 内核承载被动问答和主动任务，在同一执行闭环中处理长期记忆、工具发现、上下文治理、主动发送和端到端验证。

项目围绕以下四个持续运行问题组织设计；这不是对所有其他 Agent 能力的断言，也不是全书固定叙事：

- 历史事实需要被重新检索、补搜和回源，而不是只依赖最近对话。
- 工具和历史持续增长时，需要控制 Schema 与消息占用，同时保持工具调用链完整。
- 主动行为需要独立的证据和发送授权，普通模型回复不能直接等价为推送。
- 真实任务是否完成需要由外部 Verifier 判定，并能够区分 Agent、Provider 和 Verifier 故障。

## 3. 简历四项能力及事实边界

### 3.1 长期记忆与证据检索

核心事实：

- 集成并改造 Akasha 记忆引擎。
- 简历采用“稠密向量语义召回、BM25 词法检索与图关联补全”的能力描述。
- 指导书必须进一步说明：三者并非简单的三个平铺结果列表；BM25 也参与图/证据特征，图关联用于从命中线索补全相关历史。
- 面向 Agent 的使用链路是“自动注入—按需补搜—原文取证”。
- 必须区分“查询命中”“进入模型上下文”“最终回答正确”三件事。
- 新旧事实冲突时强调来源、时间与原文核验，不能声称系统已经自动解决所有事实冲突。
- 查询与学习需要分开：只读召回不能意外改变记忆状态，完成交互后再持久化学习。

后续学习层还需按实际问题补足记忆写入单元、图节点与关系、候选形成及筛选方式；具体对比向量＋BM25＋RRF、bi-encoder 与 cross-encoder/重排，不只与单路向量比较。这些是研究方向，不预设项目使用了所有技术或已经证明图补全更优。

可使用的隔离验证：

- 4,800 个相邻 user/assistant pair。
- 其中 6 个为精确 `[interrupted]` 占位，得到 4,794 个学习样本。
- 9,556 条必须存在的 message embedding 全部有效，没有补算向量。
- 全量重放得到 4,634 个 hub、21,254 条关系，单次约 157～216 秒。
- 两个不同 `PYTHONHASHSEED` 下，11 个冻结 query 的 canonical logical state 相同。
- 11 个 query 的召回数量均低于 40 条上下文舒适范围。
- Docker Gate `AKV2-01` 至 `AKV2-06` 全部通过。

上述数据证明迁移/重放的一致性和运行边界，不是记忆问答准确率。

重要踩坑：

- 在线路径执行完整 SQLite integrity scan，导致请求成本不合理；修复为将重检查移出在线热路径。
- 增量后缀处理与停机全量 replay 可能产生不同逻辑状态；修复时以 canonical logical state 而不是 SQLite 物理页摘要判等。
- 中断占位不能当成正常学习样本，否则会污染 hub 和关系。
- 记忆命中如果没有真实 source identity，只能给模型一段不可追溯摘要，无法完成原文取证。

主要证据：

- `docs/design/akasha-v2-runtime-migration.md`
- 历史基线中的 `plugins/akasha/`
- 现有指导书第 7 章及附录 B，仅作索引

### 3.2 Agent 端到端评测

允许进入主叙事的正式结果：

- Terminal-Bench 2.1 固定 89 题。
- DeepSeek V4 Flash，`reasoning_effort=max`。
- 最终通过 59 题，`59/89 = 66.3%`。
- 结果构成为：59 个官方 verifier reward `1`；26 个有效 reward `0`，包含真实 Agent timeout；3 个 Provider fallback；1 个 Verifier 依赖下载失败。
- 历史 High 轨道 `63/89 = 70.8%` 仅作内部核查线索，不能与当前结果合并或替代简历数字；未核对配置、轨道和样本条件，不能作直接优劣比较或推断“审计导致降分”。面试官没有默认获知该历史成绩，不将两组数字的选择设计成独立核心题。

闭环能力：

- 每题使用隔离的 Docker runtime/workspace。
- Agent 真实执行工具，由官方 Verifier 评分。
- 记录执行轨迹、Verifier 输出、artifact manifest 和 campaign WAL。
- 支持断点恢复和 accepted projection。
- 能够区分 Agent 失败、Provider fallback 和 Verifier 基础设施失败。

重要踩坑：

- Provider fallback 曾被当作有效 reward `0`，污染失败归因。
- Verifier 依赖下载会消耗任务时限，但没有进入测试正文。
- timeout 后子进程生命周期可能与下一任务重叠，需要明确清理和隔离。
- 多个 campaign 的恢复结果不能被误当成多次独立 benchmark。
- credential/provider 配置不一致会表现为 Agent 失败，但根因在运行基础设施。

主要证据：

- `docs/benchmark/terminalbench-2.1-run-audit-2026-08-05.md`
- `docs/benchmark/terminalbench-2.1-case-results-2026-08-05.csv`
- `docs/benchmark/v4flash-harness-experiment-ledger.md`
- `docs/benchmark/v4flash-terminalbench-89-case-diagnostics.md`

LongMemEval、PersonaMem 只能写入未来测评计划，不得作为当前成果。

### 3.3 工具发现与上下文管理

核心事实：

- 本地工具与 MCP 工具进入统一注册表。
- 需要区分 registered、visible、executable：已经注册不代表每轮都向模型暴露，也不代表模型得到自由执行权限。
- 工具目录负责发现；搜索命中的工具通过真实 identity 在当前执行 attempt 内进入后续实际模型请求的受限 Schema 投影，不是永久授权，也不保证所有命中工具同时可见。
- 常用/近期工具可以预加载，但必须受模型 Schema 上限约束。
- 历史压缩按逻辑交互单元工作，不能拆开 assistant tool call 与对应 tool result。
- 压缩保留最近约 20,000 tokens，历史软阈值比例为 0.74；这些是历史实现参数，不是通用最佳值。
- 稳定指令、稳定历史和动态记忆分层编排，动态材料应放在稳定缓存边界之后。
- 原始消息不应因压缩而被删除；摘要是投影，不是唯一事实副本。

学习层不能只解释调用链完整性：还需讲清较旧完整交互生成/更新模型摘要与近期保留怎样配合。摘要模型、提示词、更新策略和 token 估算等细节要按历史实现补足；协议完整不能证明摘要语义无损。

重要踩坑：

- 搜索结果曾以自由文本方式“解锁”，模型看到名称却没有可执行 Schema；修复为带真实 identity 的受限投影。
- 历史裁剪曾直接破坏原消息；修复为保留原始消息并生成独立压缩投影。
- 容量重试可能切断 tool call/result 边界；修复为以完整逻辑交互为最小处理单元。
- 摘要可能重复当前任务或突破输出上限，需要单独校验摘要输入与输出预算。
- 动态 Akasha 内容放在稳定历史之前会破坏 prompt cache 前缀。

可使用的局部微基准：

- 2,000 docs / 4 keywords 工作负载中，`_score` 中位数 `5.000025 → 4.898831 ms`，约 `-2.02%`。
- `_explain` 中位数 `3.551934 → 2.672931 µs`，约 `-24.75%`。
- 完整 search 微基准受调度噪声影响，没有形成稳定收益；不得声称端到端搜索延迟提升。

简历已包含输入 token 与缓存命中记录能力，相关实现还应查 `observe`。目前工作台未收录可直接支持端到端 token 节省率或缓存命中提升比例的同条件对比数据；不能据此判断观测功能未实现或项目没有任何缓存统计。

主要证据：

- 历史基线中的 `agent/tools/`、`plugins/compaction/`
- `docs/refactor/clean-code-ledger.md`
- [observe 插件](https://github.com/akashic-plugins/observe)：对应历史版本、采集与聚合路径在后续阶段核对
- 现有指导书第 8 章及附录 C，仅作索引

### 3.4 主动交互策略

核心事实：

- 主动推送不是一次自由生成，而是“兴趣初筛—证据调查—发送/跳过”的受限决策链。
- Content 事件保留 `source_id/item_id/revision`，以事件身份和版本去重，而不是只比较标题文本。
- 初始兴趣只入池一次，兴趣随时间衰减；历史实现使用约 36 小时内容质量半衰期、0.02 floor、池阈值大于 1.0。
- 新 revision 才能重新产生唤醒依据，旧内容不能反复触发。
- 初筛限定一步，最多选择 1～8 条候选；每条候选记录初始兴趣判断和下一步待确认问题。调查最多消费 20 个 ReAct 输出，可使用 `recall_memory`、`web_fetch` 等工具核验证据。
- 最终只有明确的发送动作拥有发送授权；普通模型 final text 不能直接视为推送。
- 发送内容最多引用 1～5 个事件项；只有确认 delivered 后才能安全结算。
- Content、Alert、Context、Drift 的语义不同，不应共用一套触发和结算规则。

重要踩坑：

- 主动输出出现缺少来源支撑的“幻觉式推荐”，因此增加证据调查阶段。
- 跨会话重复推送相似主题，因此将最近主动历史纳入决策上下文。
- 普通模型 final text 曾可能越过发送授权边界；修复为终态动作控制发送。
- 旧内容可能反复唤醒；修复为衰减池、新 revision 约束和事件身份去重。
- UTC 与本地时间混用会改变衰减和阈值判断。
- delivery 状态未知时盲目重发会造成重复打扰。

目前工作台未收录可用于声称用户级发送率、采纳率、误打扰率的正式统计；列待补项前还应检查相关插件及已有记录，不能将未收录写成没有采集能力。

主要证据：

- 历史基线中的 `plugins/eventmail/`、`plugins/wake/`、`plugins/drift/`
- 现有指导书第 10 章及附录 E，仅作索引

## 4. 研究缺口与面试前准备

以下是需核实已有材料后再细化的统计或实验方向，不是统一的“尚未实现”功能清单。说明缺少的是实现解释、已有数据整理还是新实验；只保留与简历主张和实际技术疑问有关的项目，不把整张准备清单转成面试题。

- 记忆：query 命中率、证据进入率、答案正确率的分层评测；稠密/BM25/图补全的消融。
- 上下文：先查输入 token 与缓存观测的已有实现和日志，再整理同任务在有无工具按需暴露、有无压缩条件下的使用量、缓存命中和完成率；命中率观测与优化提升的对照实验分开。
- 主动交互：候选进入率、发送率、重复拦截率、用户采纳率和误打扰率。
- 评测：三类故障归因已经实现；需要时从现有记录选择能解释具体问题的失败案例，不把已完成归因重新列成待开发功能。
- LongMemEval、PersonaMem：完成可复现评测后再决定是否恢复到简历。

尚未完成的统计与实验写成准备计划或针对具体主张的下一步；已存在的实现按事实解释，不因缺少效果数据而统一改成未来时态。消融围绕明确假设选择变量、可比基线和指标，不默认另设“时间有限优先做什么”的泛化核心题。

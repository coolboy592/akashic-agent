# 面试指导书工作区：Review 与重建方案

> 2026-09-14。本文档是工作区诊断与重建方案；诊断、重建方案与 packets"先 diff 后落盘"方式已获用户确认，执行状态见文末第 5 节。
> 已确认的方向（2026-09-14 用户答复）：
> 1. 目标产物 = 口述层（白话讲解）+ 支撑层（把问题讲清楚；函数名可以出现，但必须说明作用，不能让读者一头雾水）的强化版两层结构；
> 2. 五段模板（背景卡点→我的判断→具体行动→结果复盘→取舍与坑修复）为章节主线，覆盖旧规则中与之冲突的条款；
> 3. 资产处置大方向：事实包保留、规则重写、旧稿降级为素材。

> 2026-09-14 二次确认（用户修改意见）：文档定位为技术文档——口述层保留五段模板与第一人称，但语感为"好阅读＋技术含量高"，全书不用生活化比喻；通用概念优先链 learnagent.wiki 条目、官方文档兜底，链接只放支撑层；口述层每章至多 3 个代码符号并随文括注。黄金样例已按此定稿并嵌入 `00-README.md` §5；产物定义以 `00-README.md` 为准，本方案 §2.1 的样例为历史草案。

## 0. 结论摘要

**定界结论：问题不在执行 Agent 的研究质量，也不在事实包——而在工作区从未把"面试可口述"定义为目标产物。** 现行规则把产物定义为"面向复习者的设计学习文档"（00 文件 §1、§3.1），并在任务契约中明令"取消口播入口和回答骨架"（`drafts/stage4-execution/task.md:7`）。新 Stage 4 候选稿正是一份忠实执行了错误规格的产物：机制研究扎实、事实密度高，但它是审计式专著，不是面试文档。

**深浅摆动的机制：** "不够深"的反馈 → 规则要求"讲透"实现细节 → 没有"面试讲解粒度"的标尺 → 深度滑向函数名与版本号堆砌 → "过深"。两端之间缺的不是更多约束，而是**两层产物的定义**：深度放进支撑层（允许符号、必须带作用解释），口述层保持白话。

**规则生长方式决定了"继续修"不会收敛：** 现行规则约 500+ 行、三文件职权重叠，每次返修追加一条"禁止项"（不恢复已删草稿、不合并两组分数、不把 X 写成 Y……），却从头到尾没有一个"好章节长什么样"的正向样例。禁止项越堆越多，产出越来越防御性——这与 00 文件 §3.4 自己定的"不写防御性的审计报告"直接矛盾。

**重建方向：** 用一份 ~150 行的新入口文件（产物定义 + 五段模板 + 深度标尺 + 黄金样例片段）+ 一份 ~100 行的事实边界文件，替换现行三件规则；事实包保留并清理其中的写作指令；旧稿归档为素材；删除执行残骸。写作流程从"五阶段 + YAML 契约"简化为"一章一任务 + 用户验收"。

## 1. 诊断：问题定界

### 1.1 定界总览

| 层 | 问题 | 权重 | 是否根因 |
| --- | --- | --- | --- |
| 目标定义层 | 产物从未被定义为"面试可口述"，被定义为"设计学习文档" | ★★★ | **是（根因一）** |
| 深度标尺层 | 没有定义口述粒度与查证粒度的分层，"讲透"不可操作 | ★★★ | **是（根因二）** |
| 规则体系层 | 以禁止项方式生长、职权重叠、自相矛盾、无正向样例 | ★★☆ | **是（根因三，结构性）** |
| 流程层 | 五阶段 + 任务契约 + 状态机，仪式重于产出 | ★★☆ | 放大因素 |
| 工作区卫生 | 三代产物共存、执行残骸、编号断档 | ★☆☆ | 次要 |

**明确不在问题范围内的部分**（这些是工作区的真实资产，重建时保留）：

- `packets/` 六个事实包：事实提炼质量高，含验证数据、带提交号的踩坑、边界声明，是多次研究的结晶；
- `drafts/stage4-execution/research-and-self-review.md`：版本钉死（d565 基线、Observe commit）、来源清单、未决问题记录，研究纪律是好的；
- 事实边界的纪律本身（不夸大数字、区分实现/观测/实验）——必须完整迁入新规则。

### 1.2 根因一：目标定义错位

证据链：

- `00-workflow-and-state.md:7`——读者定义为"掌握 Agent 基础、遗忘项目细节"的复习者；验收是"理解设计与局限"。
- `00-workflow-and-state.md:54`（§3.1）——"取消各能力的 30 秒入口、90 秒介绍和 2～3 分钟口述任务"，口述层被明令移除。
- `00-workflow-and-state.md:61`（§3.2）——"问题→判断→行动→结果……只是可用思路，不是固定模板"，五段模板被降级。
- `drafts/stage4-execution/task.md:7`——"采用连贯的设计学习表达。可以重构旧稿，取消口播入口和回答骨架。"

执行 Agent 拿到的规格就是"写一篇机制专著、不要口述结构"，产出的 candidate 完全符合规格。**用户不满意，说明规格错了，而不是执行错了。** 这是本工作区最重要的一条定界：继续在这套规格上要求"更适合面试讲解"，等于要求 Agent 违反明文规则。

### 1.3 根因二：深度标尺缺失

新旧 Stage 4 对比：

- 旧 approved（201 行）：有骨架、有踩坑、有追问，但机制细节薄（压缩只讲"完整交互单元"，不讲触发、预算、摘要策略）→ 用户判"不够深入"；
- 新 candidate（71 行，密度约为旧版三倍）：机制讲透了，但 `get_deferred_names`、`SOFT_LIMIT_RATIO = 0.74`、`KEEP_RECENT_TOKENS = 20_000`、`estimate_context_tokens`、Observe commit `8913be0e...`、manifest `2.0.0`、token 加权命中率公式、1.2.0 与 2.0.0 的兼容性审计……全部进入正文 → 用户判"过深、函数名太多、不适合面试讲解"。

规则文件里唯一相关的条款是"不以函数数量或术语密度判断完整性"（00:56）和"不堆叠路径与函数清单"（03:66）——这是**禁止**，不是**标尺**。Agent 无从知道：哪个深度的内容、以什么形式、放在产物的哪个位置。"讲透"和"可口述"被当成了同一件事，实际是两个层次。

真正需要的是用户本次已确认的两层定义：口述层白话（符号几乎不出现），支撑层把问题讲清楚（符号可以出现，但**每个符号首次出现必须用一句话说明作用**）。这一条"符号必须随文解释"是新增的硬规则，现行规则里没有。

### 1.4 根因三：规则以禁止项生长，且自相矛盾

- **体量与重叠：** 00（流程 + 内容规则 + 状态 + 契约，203 行）、01（事实边界，194 行）、03（术语 + 题目设计 + 技术比较，110 行）。同一件事在多处出现：写作标准在 00 §3 和 03 §5 各一份；"不把观测写成效果"在 00 §3.4、01 §1.2、03 §7.3 至少三处。执行 Agent 的上下文和注意力被合规检查消耗。
- **生长方式：** 逐条检视可以发现大量条款是历次返修的化石——"gpt-5.6 草稿已删除、不恢复、不读取历史副本"（00:89、00:201 两处）、"历史 63/89 与当前 59/89 不得合并"（01:89、03:54）、03 §6 整张"之前的问题→后续设计要求"纠偏表。每轮失败追加禁止项，规则只增不减，目标却始终缺席。
- **自相矛盾：** 00:78 要求"不写防御性的审计报告"，而 §5.2 验收门槛要求结果边界、证据等级、适用范围逐项交代——candidate 正是按后者写成的防御性审计。03:66 说"不堆叠路径与函数清单"，而 task.md:25-28 要求正文覆盖"摘要模型和提示词、生成与更新策略、统计口径、兼容性依据"。Agent 夹在中间，怎么写都违规。
- **无正向样例：** 全工作区没有任何一段"合格的口述层长什么样"的文字。规则告诉了 Agent 几十件不能做的事，没给它一件能做的事。

### 1.5 放大因素：流程仪式

scope/plan/execute/verify/revise 五阶段、YAML 任务契约、标准返回值（status/artifacts/evidence/…）、状态同步义务（00 §9、§10）——这套机制解决的是"多 Agent 交接不丢信息"。但本次暴露的质量问题没有一个出在交接上：研究做了、版本钉了、产物交了。产出不合适的原因是规格错误（1.2～1.4），流程仪式只是让每次"修改规则→重跑→再修"的周期变长、规则文件变厚。质量关卡真正需要的是用户在**章节颗粒度**上验收，而不是 Agent 在**流程阶段**上互验。

### 1.6 卫生问题

- 三代产物并存且标识误导：`docs/interview-guide.md`（1106 行，最早一代，问答+口播风格）、`drafts/stages/*.approved.md`（第一代工作台产物，"不够深"）、`drafts/stages/04-tools-context.candidate.md`（第二代，"过深"）。`.approved.md` 后缀实际含义是"旧标准已通过、新标准待复核"，文件名在撒谎。
- 执行残骸：`drafts/stage4-execution/observe-research/`（整仓 git clone）、约 1MB 的 `draft.events.jsonl`、空日志、`protected-files.before.json`。
- 编号断档：存在 00、01、03，没有 02；规则里还挂着对已删除文件的"不恢复"条款。

### 1.7 为什么"继续修规则"不会收敛

修改循环的真实动力学：产物不满意 → 用户反馈（"不够深"/"太深"）→ 规则追加禁止项或要求项 → 规则更长、更防御 → 下一次执行更保守、更面面俱到 → 产物离"可口述的个人叙事"更远。这个循环里缺的输入从来不是更精确的禁令，而是**目标产物的正样本**。只要工作区的第一定义还是"设计学习文档"，无论怎么追加"要适合面试讲解"的补丁，两个目标都会继续互相挤压。因此处置是**重建规格**，不是**续修条款**。

## 2. 重建方案

### 2.1 目标产物定义（新规则的核心）

全书 = 1 个总述章 + 4 个能力章（对应简历四条）+ 1 个跨章技术对比附录。

**总述章**（项目定位 + 统一 ReAct 地基）：2～3 分钟口述骨架，回答"这是个什么项目、四条能力怎么挂在同一个执行闭环上"。

**每个能力章两层：**

**口述层**——第一人称白话讲述，按五段模板：

1. 背景与问题：当时卡在哪（现象、代价，不要一上来堆架构）
2. 我的判断：为什么这样选择（对比过什么、放弃了什么、依据是什么）
3. 具体行动：亲手做了什么（做的事按因果串成故事，不是功能清单）
4. 结果与复盘：结果与边界（有数字讲数字并说明口径；没有数字就讲怎么验证的、边界在哪，不编数字）
5. 设计取舍、踩过的坑、怎么修的（现象→误判→根因→修复→验证，挑最有讲述价值的 1～2 个）

口述层硬性标准：每章 3～5 分钟（约 900～1400 字）；函数名、参数名、commit 号一律不出现；允许至多 3 个锚点概念（如"受限投影""逻辑交互单元"），且首次出现必须当场用一句白话解释。

**支撑层**——按需取用的深挖弹药，四个固定板块：

1. **关键机制详解**：把口述层每个论断落到实现。函数/类/参数/常量**可以出现**，但每个符号首次出现必须紧跟一句话说明它的作用（例："`max_tool_schemas`——provider 侧对单请求工具数的硬上限，投影层据此裁剪"）。无解释的符号视为违规。
2. **简历效果 ↔ 实现技术对照表**：简历每句话在左，实现它的具体技术在右（服务"简历效果是以什么技术实现的"这一目的）。
3. **与主流替代方案对比**：公平对比（向量+BM25+RRF vs 三路+图补全；滑动窗口 vs 模型摘要 vs 组合；全量 Schema vs 按需发现；外部 Verifier vs LLM 自评），说明本项目选了什么、什么场景下另一种更优。
4. **高概率追问与要点**：从口述层的论断自然引出，答案给要点和方向，不写成逐字稿。

支撑层硬性标准：读者读完任何一个符号条目，都能说出"这个名字是干嘛的"；版本兼容性审计、证据等级核查等内部工作过程性内容**不进**支撑层，留在事实包。

**黄金样例片段**（草案，将嵌入新 00-README，供用户验收时一并确认）：

> **【口述层样例：背景与卡点 → 我的判断（工具与上下文章开篇）】**
>
> 我的 Agent 一开始工具很少，把全部工具的 Schema 直接塞进每个请求也没问题。但接入 MCP、工具涨到几十个之后，光工具定义就吃掉一大块上下文；长对话再一压缩，问题更明显——模型经常"知道有这个工具"，真去调用时却失败。这里我的判断是：问题的本质是把"系统里注册了多少工具"和"这一轮模型真正能调用哪些工具"混为一谈。我把这两层拆开：注册表保持完整，但每轮请求只携带一个受容量约束的"可见集合"——就像工具库有个前台，货架上只摆这一轮要用的，其余的进了仓库目录，需要时搜出来、当轮解锁。
>
> **【支撑层"机制详解"条目样例】**
>
> - `tool_search`（工具搜索工具本身）：模型调用它、按名称或关键词在工具目录里找工具。它必须常驻可见——否则模型连"去找工具"的入口都没有。
> - `max_tool_schemas`（每轮工具数硬上限）：provider 对单请求工具数的限制；投影层据此裁剪，新解锁的工具优先占用被挤出去的旧工具的槽位。

### 2.3 新 00-README 骨架

1. **目标**：一段话——面试中把项目讲清楚；读者 = 面试官（听）+ 用户本人（复习与排练）。
2. **产物定义**：2.1 节内容（两层、五段模板、各层硬性标准）。
3. **黄金样例**：上述片段（正式版可再打磨）。
4. **事实边界**：指向 `01-fact-boundaries.md` 与对应 packet，一句话原则——事实取自 packet 与历史基线 `d565ca...`，冲突时交用户裁决，不编数字。
5. **写作流程**（极简）：一章一任务 → 读 00 + 01 + 对应 packet（archive 素材可选）→ 产出 chapter 草稿 → 用户以"口述层能不能直接讲出来"验收 → 定点返修。废除：YAML 任务契约、verify 阶段、标准返回值、跨文件状态同步。
6. **进度表**：一张表（章节 / 状态 / 备注），替代旧 00 的全部状态管理职能。

### 2.5 packets 清理方式

六个事实包**事实内容原样保留**，只做一类清理：移除指令性段落（各包 §1"章节任务"、§12 类"后续研究与解释重点"等面向旧流程的指示），避免它们继续以旧标准指挥写作 Agent。踩坑、数据、提交号、源码锚点、禁止推导全部保留。逐包 diff 式清理，清理前后各留一份对照（执行时先输出 diff 给用户过目再落盘）。

## 3. 风险与开放问题

1. **黄金样例的定稿**：2.1 中的样例是我的草案。建议在重建执行时先定稿样例、再铺开章节——样例是整本新规格的锚点，值得用户逐句认可。
2. **口述层第一人称**：口述层以"我"叙述（用户本人口吻）。若用户希望保持"本项目"的第三人称口吻，需在验收样例时提出——这会影响全部章节的语感。
3. **结果段的空窗**：四条能力中有几条（工具/上下文、主动交互）缺少端到端效果数字。五段模板第 4 段允许"讲验证方式与边界"替代数字，但这会让叙事强度弱于有数字的评测章——面试策略上可用"我知道缺什么数据、打算怎么补"作为诚实加分项，此取舍在首章验收时确认。
4. **写作执行者**：新流程面向任意执行 Agent（包括我在后续会话中逐章编写）。00-README 不绑定具体模型或产品，保持这一性质。
5. **正式文件 `docs/interview-guide.md` 的最终去留**：本方案不动它；全书完成后建议以 `drafts/chapters/` 的新稿整体替换，届时另行确认。

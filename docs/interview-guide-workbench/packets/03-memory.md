## 1. 章节任务

解释本项目怎样形成、检索和使用长期记忆，以及 Akasha 如何与自动注入、按需补搜和原文回查配合。既讲来源，也讲索引、候选、图关系与筛选机制；与常见混合检索及重排作具体比较，不把单次向量相似度检索当作 RAG 的完整对手。

## 2. 对应简历

> 长期记忆与证据检索：集成并改造 Akasha 记忆引擎，融合稠密向量语义召回、BM25 词法检索与图关联补全，保留来源并对多路召回结果去重；设计“自动注入—按需补搜—原文取证”链路，使 Agent 可在摘要遗漏细节或新旧事实冲突时回源核实，支持基于历史证据回答。

## 3. 已有机制与设计动机

### 背景与卡点

- 最近对话窗口覆盖不了跨会话事实。
- 压缩摘要可能遗漏原话、时间、限定条件和低频细节，不能作为完整历史的替代品。
- 单路向量在精确词法和需要关联历史的场景中可能漏检；混合检索和重排也是应认真比较的替代方案，不能预设它们均无法解决问题。
- 找到候选摘要仍不代表模型能够核实它来自哪条真实消息。

### 判断

将记忆拆成三层使用方式：

1. 自动注入承担低摩擦默认召回，只放受控数量的候选。
2. `recall_memory` 允许 Agent 在当前证据不足时主动补搜。
3. `search_messages/fetch_messages` 或等价来源接口根据真实 source identity 回查原文。

设计目标不是一次检索包办所有问题，而是让 Agent 能根据不确定性逐步增加取证成本。

### Akasha 内部信号

- `FeaturePool.dense_scores` 计算稠密相似信号。
- `FeaturePool.bm25_scores` 与 `bm25_document_score` 提供词法证据。
- `BurstAwareFeaturePool` 将 query/context 的 dense 与 BM25 证据用于 seed 推断。
- `_mix_sources` 使用稀疏化选择组合证据，不要写成固定权重的线性融合。
- `domain/readout.py` 对准备好的记忆图执行 pattern completion；`RecallItem` 携带 `sources`。
- 图关联补全根据关系扩展完整历史 turn，不是第三个独立搜索 API。

### 宿主集成

- Akasha 引擎负责学习、图结构、readout 和诊断。
- 宿主插件把当前 turn 转成 query、控制注入预算、注册工具并发布来源。
- 工具层提供显式补搜和消息回查。
- 查询阶段与学习阶段分开，避免只读检索改变记忆状态。

## 4. 关键取舍

### 最近窗口 vs 长期记忆

最近窗口简单且保持原始顺序，但覆盖范围有限；长期记忆扩大范围，却引入召回噪声、索引维护和来源管理。两者是互补关系。

### 单路向量检索 vs 多证据图补全

单路向量检索容易实现和解释；加入词法与关系信号可以覆盖精确实体和关联历史，但调试更复杂，需要区分命中线索、图扩展和最终呈现。

### 混合检索、重排与图扩展

还需比较向量＋BM25＋RRF 形成候选和排序的方案，以及 bi-encoder 检索、cross-encoder 重排各自作用的位置。图扩展能否补出初始候选未包含的历史、增加 top-k 或查询改写能否达到类似效果，需要结合本项目图结构和查询过程解释；没有实验不能断言图方案胜出，也不能假称项目已使用上述全部技术。

### 全自动注入 vs 分阶段取证

全自动注入使用简单，却会增加噪声和 token；分阶段链路让常见问题成本低、复杂问题可以继续取证，代价是 Agent 需要正确判断何时补搜。

### 物理摘要相同 vs 逻辑状态相同

SQLite 物理页会受运行细节影响；迁移验证以 canonical logical state 作为一致性标准，物理文件哈希只用于确认正式 workspace 未被修改。

## 5. 踩坑候选

### 在线执行完整 SQLite 扫描

- 表象：每次记忆使用都承担与数据库规模相关的完整检查。
- 根因：把迁移/修复级别的完整性验证放进在线请求热路径。
- 修复：移除在线全库扫描，将重检查放到离线 Gate 和维护流程。
- 提交：`f7acedd7`。
- 边界：可以说减少不必要的热路径工作，不能补造端到端延迟数字。

### 增量处理与全量 replay 的等价性

- 表象：优化增量后缀或串行重放后，速度可能变化，但逻辑结果也可能漂移。
- 根因：只比较物理数据库或只跑单个 query，无法证明完整逻辑状态等价。
- 修复：冻结 query、使用两个 `PYTHONHASHSEED`、比较 canonical logical state，并保持正式 workspace 不变。
- 提交：`67a3e560`；验证记录见迁移文档。

### 中断占位污染学习样本

- 相邻消息不等于完整交互；`[interrupted]` 必须识别为未完成 turn。
- 4,800 对消息中排除 6 个中断占位，得到 4,794 个学习样本。

### 有召回内容但来源交接不完整

- 召回展示、工具结果和来源发布需要绑定同一个 turn/真实 source identity。
- 相关演进：`9d8c97e0`、`c5c76c24`。
- 不要在没有更细证据时扩写为跨用户数据泄露事故。

## 6. 已验证结果

均为隔离迁移/重放验证：

- 4,800 个相邻 user/assistant pair；6 个中断占位；4,794 个学习样本。
- 9,556 条必须存在的 message embedding 全部有效，无补算。
- 4,634 个 hub、21,254 条关系；全量重放约 157～216 秒。
- 两个不同 `PYTHONHASHSEED` 下，11 个冻结 query 的 canonical logical state 相同。
- 每个 query 的显式召回数低于 40 条舒适范围。
- Docker Gate `AKV2-01`～`AKV2-06` 全部通过。

这些结果不能被称为记忆准确率或回答正确率。

## 10. 后续研究与解释重点

这些问题用于补足理解，不是已经验收的 Stage 6 题纲，也不要求逐条问答：

- 写入与索引的单元是什么，原始消息、完整问答、hub 和关系之间如何对应；节点与边在什么时机、依据什么形成。
- 查询怎样形成，dense 与 BM25 信号在哪里参与 seed 推断，图 readout 如何扩展，去重与稀疏选择怎样决定最终材料；不要只列四个源码符号。
- 用能说明关系的例子追踪一次召回，解释图多找到了什么、可能引入什么噪声，并公平比较扩大候选、重排等方案。构造示例不冒充实际测试结果。
- 自动注入不足时 Agent 怎样补搜，来源怎样回到原文，新旧偏好或事实冲突为什么仍需判断；有引用不等于检索充分、引用相关或结论正确。
- 学习在何时触发，未完成交互为什么排除；检索、摘要和长期存储分别承担什么。把真实完整链路讲清，不强制所有请求按同一工具顺序执行。

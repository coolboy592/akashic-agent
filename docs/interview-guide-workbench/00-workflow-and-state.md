# Akashic Agent 面试指导书：工作流与当前状态

> 本文件是后续 Codex 对话的唯一入口。新对话先完整读取，再按“下一阶段”加载必要材料。2026-09-13 按用户决断修订：以设计学习为主，恢复执行端的独立分析职责，取消用户手动搬运。旧稿、事实包中的旧写作要求不能覆盖本文件；用户最新明确指令始终优先。

## 1. 目标、读者与本轮范围

完成面向 Agent 开发实习岗位、能够支撑 30～60 分钟技术深挖的项目理解与复习指导书。读者掌握 Agent 基础知识，但不了解或遗忘本项目细节；阅读后应能围绕简历解释自己的项目亮点、具体实现、设计理由、替代方案和局限。

简历主线为 `F:/agent/agent简历.md` 中的长期记忆、端到端评测、工具发现与上下文管理、主动交互。统一 ReAct 是共同地基，不另造第五项成绩。基础概念只在理解本项目或比较具体技术时补充，不扩写成通用 Agent 教程。

质量优先体现为技术解释完整、项目理解充分、问题合理、事实准确。双执行的目的同时包括提高效率、减少订阅侧重复研究和额度消耗，不以压低执行端的分析自主性换取表面上的流程可控。

2026-09-13 本次交付只修订工作台的规则、材料说明和状态，不运行第三方模型、不改配置、不复核或改写章节正文、不修改正式文件 `docs/interview-guide.md`。这是本次修订的交付边界，不限制后续经用户确认的阶段执行；也不代表任何章节已按新标准通过或某章试修已获授权。

## 2. 分工与自动执行边界

### 2.1 角色职责

- 用户是最高决策者：确认目标、重要取舍、阶段范围和阶段验收；不负责选择命令、启动执行端、复制 Prompt 或搬运结果。
- 当前 Codex 使用订阅会话承担总体设计、阶段定界、任务编排、自动调用、成果读取、审核与返修组织。只在关键证据缺失、论证存疑或冲突时补查，不默认把执行端的研究完整重做一遍。
- 第三方执行端承担实质性的源码与插件阅读、机制分析、方案比较、旧稿诊断、正文编写、自查和修订。它可以自主选择范围内的材料、提出结构调整、质疑事实包；不是只扩写预设结论的写手。
- 同源模型不构成事实保证，也不等于真正独立的证据。双方都要用实现与运行材料检验判断，而不是相互认可就视为通过。
- 只有用户明确验收，才能固化新版通过稿；只有用户明确批准最终组装，才能修改正式指导书。

### 2.2 执行载体与就绪状态

首选现有 OpenCode 命令行作为第三方执行端，载体由 Codex 根据可直接调用、可读取结果、可继续修订的能力选择，无需用户充当操作员。

已通过本机帮助确认：`opencode run` 支持非交互调用，`--format json` 返回事件，`--session` 可续接指定会话，`--dir` 可指定工作目录。参考 [OpenCode CLI](https://opencode.ai/docs/cli/#run)。当前仅确认接口能力，第三方服务、模型配置、认证可用性和端到端执行尚未验证；不得写成已经接入成功。

后续阶段范围确认后，由 Codex 完成必要的配置核对和最小联通验证，再自动调度、读取产物、发送审核意见。使用明确的会话 ID，避免续接用户其他任务；不得将第三方执行失败静默切换成订阅侧大规模代写或更换模型。需要改变执行方案时说明影响，不把人工搬运当作默认降级方式。

费用由用户自行掌握，不反复询问预算、不把未设预算视为阻塞条件；仍避免无效重试。仅向已确认的执行服务提供授权范围内材料，密钥不进入 Prompt、文档或日志。执行端只写阶段约定的草稿范围，不修改项目业务代码、简历、正式指导书或已验收原稿，不自行提交、推送、公开分享。

### 2.3 何时交回用户

任务意图、事实基线、重要技术主张或阶段范围存在歧义时，暂停受影响的推进并与用户交互，不用假设越过决策。材料中暂时缺少的实现细节，由执行端先在已授权范围内研究；内部研究选点和正常修订无需逐项请示。反复修订仍不能解决实质分歧时报告原因，不无限循环，也不以进程退出或模型自报完成代替验收。

## 3. 内容和表达规则

### 3.1 设计学习层为主体

仅“项目简短介绍”保留 2～3 分钟回答骨架，帮助建立整体定位；取消各能力的 30 秒入口、90 秒介绍和 2～3 分钟口述任务。项目介绍之外，包括 ReAct、各技术章及 Stage 6，均以理解设计的完整解释为目标。

正文应让读者知道项目实际采用什么、怎样工作、为何这样选择、遇到重要情况如何处理。答案连贯阐述，不压成背诵要点，也不拆成机械逐问逐答。完整性由问题是否讲透判断，不以篇幅、函数数量或术语密度判断。

### 3.2 组织方式服从具体技术

- 不把全部内容串成“事实、投影、执行、验证”。这一总结可用于项目复盘，不能掩盖图补全、压缩、工具发现等模块各自值得解释的机制。
- “问题 → 判断 → 行动 → 结果”和“采用什么方法 → 怎样工作 → 为什么选择 → 特定情况”都只是可用思路，不是所有章节和题目的固定模板。允许先解释方法，再讨论理由。
- 不要求每章恰好一个踩坑。只选择有助于理解的真实案例，讲清现象、原因、处理与已有验证；证据不够时不要把设计风险编成发生过的事故，也不为凑完整结构补造经历。
- 图表只在能明显解释关系时使用，采用最小有用形式；不要求每章有图，也不机械限定一张图。
- 类名、状态、参数和代码片段在解释机制确有帮助时可以使用；路径和提交号集中回查，不用符号清单代替分析。

### 3.3 面试问题与内部核查分离

问题从简历的技术主张、常见替代方案和回答中自然出现的疑点产生。按实习生标准考察实现理解、因果推理和合理取舍，不要求面试官预先知道内部记录，不把有限面试时间用于低信息量的流程审计。

二级追问沿着当前答案深入，可以讨论方法选择、实现细节、失败场景和验证思路；不固定数量、不照填四格，不强行给每题附加个人贡献、踩坑和消融。内部版本核对、来源核查和结果筛选保留在工作台，必要的结论自然进入正文。

具体反例与技术解释要求见 `03-terminology-and-claim-rules.md`。此前提出的题目数量、编号和问题集合均不是已验收题纲，不得直接继承。

### 3.4 比较、结果与语气

- 比较真实可行的方案，不把 RAG 简化成一个很弱的向量检索对手，也不把“向量＋BM25＋RRF”纠正为术语争论。应具体解释混合检索、bi-encoder、cross-encoder/重排与本项目机制的关系，清楚区分已采用与可替代。
- 不预设复杂方案一定更优；说明收益可能出现的场景、额外成本，以及现有证据能支持到哪里。
- 使用清晰、自信的设计解释，不写防御性的审计报告。不虚构个人贡献、用户规模、数据和事故，不将机制上的合理性写成已测出的效果。
- 正文自然说明结果适用范围，不强制展示内部证据等级。既不能夸大成果，也不能因未整理数据而把已有实现写成未来计划。

## 4. 事实范围与研究规则

- 主仓库固定为历史完整基线 `d565ca44356b5d52fe8d00f8cb008c14fff56c0b`。通过该版本读取源码与测试，不混入当前主干迁移状态、迁移欠账或新版本接口，不新增迁移附录。
- 简历决定讲解重点；源码、测试与运行记录支撑相应实现和结果事实。事实包和旧稿是可复用的研究起点，不是完整事实清单；材料未提及不等于项目未实现。发现与简历或已确认结果冲突的证据，交用户裁决，不擅自迎合或改写。
- [akashic-plugins](https://github.com/akashic-plugins) 属于相关材料范围。只沿当前技术问题阅读与基线对应或兼容的实现，记录所用版本及与主仓库的衔接；不能仅因当前 README 列出某功能就把后续能力倒灌到历史项目。版本无法确定的部分保持待核，不当作已核验细节。
- 插件用于补足真实实现和使用场景，不按插件数量扩张章节，不自动增加简历亮点。例如缓存观测应查 [observe](https://github.com/akashic-plugins/observe)，不能只在主仓库找不到就建议“补做缓存命中率采集”。
- 区分已有采集/展示、已有运行统计、已有对照实验。附录中的待补项先查相关插件和记录，再准确写明缺少哪一层；不在本书写作任务中擅自实现功能或运行新的评测。
- 执行端可以为当前问题主动扩展阅读到调用方、相关插件与测试，不受预列文件清单封闭限制；不要求全仓扫描或阅读配额。有充分依据可以复用，无关键机制依据则必须补查或明确问题，不能用“避免过度工程化”跳过理解。
- `drafts/gpt-5.6-sol-full-draft.md` 仅作为失败样例保留，默认不读取、不继承目录或写法。
- LongMemEval、PersonaMem 只能作为未来规划。Terminal-Bench 2.1 固定结果仍为 `59/89 = 66.3%`，其余为 26 个有效 `reward=0`、3 个 Provider fallback、1 个 Verifier 基础设施依赖失败。已有隔离验证和微基准数据可以保留，但不能改称用户效果。

## 5. 阶段工作流、任务交接与验收

保留“定界—编写—审核—用户验收—固化—下一阶段”的阶段工作方式，调整执行责任和质量标准，不另建一套与工作台并行的流程。

1. Codex 复核状态，说明本阶段的简历主张、学习目标、产物及读写范围；用户确认阶段范围。任务理解不清时先交互。
2. Codex 生成裁剪后的任务 Prompt 并自动调度执行端。执行端结合事实包、旧稿、历史源码和相关插件，区分表达缺口与理解缺口，自主分析并形成成果。
3. 执行端回交正文/诊断、关键依据与版本定位、材料新增或冲突、必要的不确定项。无需回传全部源码或内部推理过程；这些审查材料不混入面试正文。
4. Codex 直接读取输出和文件，审核论证、学习价值、问题合理性与事实；需要时定点核查，并在同一范围内组织返修。局部缺口局部改，结构失当可以重写，不默认保护旧结构，也不因小问题全章重跑。
5. Codex 将审核后的成果与重要判断交用户验收。用户通过后，固化对应新版、同步事实包和本文件状态；只有按新标准通过的章节才可参加最终组装。用户再确认下一阶段。

### 5.1 阶段 Prompt 的最小构成

- 阶段作用、读者定位、简历主线与本次产物；区分研究/诊断、题纲设计、正文改写等实际任务。
- 已确认约束、结果与入口材料；明确事实包可补充，旧稿结构和推理可以被质疑。
- 当前值得解释的问题和已知缺口；允许执行端从相关源码、插件、测试与必要的技术一手资料补足，不预填所有答案。
- 历史版本、可写路径、禁止外部操作，以及发现重要冲突时的处理方式。
- 设计学习层与合理追问要求、验收标准、关键依据的回交方式，以及确有必要的前文接口。

Prompt 应在任务上自包含、在材料上按需引用：不给执行端复制整本工作台，不让它重建无关项目背景，也不强制每段措辞、固定字数、案例配额或题目数量。工具和模型的选择由 Codex 处理，不再次交给用户搬运。

### 5.2 新标准验收门槛

- 熟悉 Agent 基础但遗忘项目细节的读者，能够理解本项目采用的方法及关键实现，说明设计选择与重要局限。
- 解释围绕简历、有机制和因果；具体常见替代方案比较公平，不靠术语堆叠或通用知识替代项目分析。
- 问题具有面试中自然出现的前提，追问有技术信息量、符合实习生考察；答案连贯完整，不是口播提纲或内部审核表。
- 实现、方案推断、运行观测和实验结果不混淆；相关插件没有因仓库边界被遗漏，也没有被扩大成无关主线。
- 所用基线、数据流与术语一致；已知数字保持真实范围。案例有依据，不把测试覆盖写成真实事故或线上收益。
- 章节各有重点；必要复述用于让答案独立成立，不靠大段复制，也不以“参见前文”省去关键解释。
- 仅项目简短介绍检查 2～3 分钟骨架，其余章节按设计学习质量验收。Codex 审核通过不等于用户验收通过。

## 7. Stage 6 的定位与后续整体安排

Stage 6 是指导书重点，负责从面试官视角组织综合追问和完整解释，不再只是跨模块一致性检查或准备清单。既可以深入单项技术，也可以讨论能力配合；重点来自简历和真实技术疑问，不来自内部审计步骤。

前面各技术章按能力帮助理解，Stage 6 按问题重新组织重点，允许为完整回答作必要复述。涉及前文未讲透的机制，应同步补足对应材料或章节，不能只在 Stage 6 掩盖前面缺口。

第 6 章独立通过后，再处理附录 A（指标、消融与面试前准备）和附录 B（源码与证据索引）。核实已有能力后才列待补内容，不把附录写成面试官会逐项询问的清单。Stage 7 仍是全文一致性审查与最终组装，必须经用户明确批准后才写正式文件。
